القسم 13.1: Applications وlibraries

Applications وlibraries وقت التشغيل

  • طريقة نشرك لـ applications وlibraries بتأثر على visibility الموارد وقت التشغيل
  • الـ applications بتدي encapsulation وisolation: ممكن تعبي applications متعددة في BAR واحد، وتنشرها كلها على integration server واحد. الـ visibility لأي مورد محصورة في الـ application اللي فيها. الـ static libraries بتتنشر جوه الـ applications
  • الـ shared وstatic libraries بتسهل إعادة الاستخدام وإدارة الموارد: الـ static بتتعبى كجزء من الـ application في BAR، والـ shared بتتنشر منفصلة قبل الـ applications اللي بتشير لها

في ACE بتخزن الـ development artifacts في containers اسمها applications وlibraries. الـ application بتدي runtime isolation. الـ libraries static أو shared. الـ static بتتعبى مع الـ application، والـ shared بتتنشر وتتدار منفصلة.

على الـ integration node

  • كل application هي container مستقل جوه الـ integration server
  • الـ static libraries بتظهر كـ child للـ application container اللي بتشير لها
  • الـ shared libraries بتتنشر وتتدار منفصلة
  • كل الـ applications والـ libraries بتتخزن كملفات غير معدلة على work path بتاع الـ integration node

الـ applications والـ libraries هي containers قابلة للنشر فيها موارد زي message flows وsubflows وmessage models (DFDL وXSD) وملفات JAR وXSL stylesheets. تقدر تنشر applications متعددة على integration server، وممكن فيها static libraries.

عزل الموارد بالـ applications

  • استخدم applications لتجميع الـ flows والموارد الداعمة عشان تحديث مجموعة ما يأثرش على مجموعة تانية
  • لما application أو أكتر تشير لـ static library، نسخة من الـ library بتتنشر في كل application container بيشير لها، وده بيدي مستوى عزل
  • لما تنشر تحديث لـ static library على application، التحديث بيتحرك جوه منطقة الـ application المتأثرة بس

Shared libraries وقت التشغيل

  • الـ applications ممكن تشير لـ shared library أو أكتر
  • لو عملت deploy لـ application ومحتاجة shared library مش منشورة أو مش بتتنشر دلوقتي، الـ deployment يفشل
  • الـ applications اللي بتشير للـ shared library بتتعرف تلقائيًا على التحديثات
  • ما ينفعش تشيل shared library من الـ integration node لو في applications منشورة بتشير لها
  • الـ shared libraries بتتشاف في الـ ACE web user interface تحت مجلد Shared Libraries

الـ shared library ممكن تتنشر مباشرة على integration server، وأي application تقدر تشير لمواردها. لو اتحدثت، كل الـ applications المشيرة ليها بتتعرف على التغيير. لازم تنشر الـ shared library مع أو قبل الـ application اللي بتشير لها. لو بتسحب الموارد على integration server: انشر الـ shared library الأول. لو بتضيفها في BAR file: ضيف أي shared libraries بتشير لها الـ application.

نشر تحديثات الـ shared libraries

لما تنشر تحديث لـ shared library شغالة مع applications، التأثير فوري على الـ applications:

  1. في بداية الـ deployment، كل الـ flows في كل الـ applications اللي بتستخدم الـ shared libraries بتتقفل وما بتقدرش تعالج رسايل
  2. موارد الـ shared library بتتحدث على الـ integration node
  3. الـ applications بتتفحص (validate) عشان تتأكد إن تحديث الـ library ما كسرهاش. لو application فشلت: الـ deployment للـ library بيتعمل rollback ويترفض. لو عدت: كل الـ flows المقفولة بتتفتح وبتستخدم فورًا الموارد المحدثة

لعرض الـ applications اللي بتشير لـ library استخدم mqsilist بالخيار -y. مثال الكتاب:

mqsilist ACENODE -e default -y ShareLib1

القسم 13.2: إنشاء BAR files

تقدر تنشئ BAR file بتلات طرق: ACE Toolkit، أو الأمر mqsipackagebar، أو الأمر mqsicreatebar.

الأمر mqsipackagebar

  • بيركز على packaging الـ BAR مش الـ compile: بتنشر أصول ACE كـ source
  • بتحدد applications وlibraries وملفات تتضاف للـ BAR
  • لازم تعمل compile لأي message sets أو كود Java قبل ما تنشئ الـ BAR
  • بيكمل الـ Toolkit والـ Integration API في النشر
  • على z/OS: خصص وسلّم BIPPACK
  • متاح على كل hardware وأنظمة تشغيل الـ integration node
mqsipackagebar -a MY.BAR -o my.msgflow my.dfdl my.esql

في بيئة التطوير بتستخدم الـ Toolkit. في بيئة تشغيل ممكن الـ Toolkit مش متاح، فبتستخدم الأمر ده على servers مفيهاش Toolkit. الموارد اللي بتضيفها بـ mqsipackagebar ما بتتعملهاش compile وقت الإضافة، ولازم تضيف موارد قابلة للنشر. مثلًا Java لازم تعمل لها compile الأول. لو بتستخدم repository لتخزين الـ flows والـ models ممكن تكتب سكربتات deployment بأدوات الـ repository.

الأمر mqsicreatebar

  • بينشئ BAR files قابلة للنشر فيها message flows وdictionaries
  • تحدد projects وapplications وlibraries
  • على Linux: الـ user ID لازم له write access على workspace (-data) ومجلد الـ BAR (-b)
mqsicreatebar -data C:\Workspace -b C:\Bars\app1.bar -a app1

المثال بينشئ app1.bar في C:\Bars ويشمل application اسمها app1 من C:\Workspace.

القسم 13.3: Environmentally aware message flows

خصائص الـ integration node

  • كل integration node بيحتفظ بمجموعة attributes تصفه: متعلقة بالـ node (NodeLabel وTransaction وDataSource)، وبالـ flow (MessageFlowLabel وAdditionalInstances)، وبالـ integration server (IntegrationServerName وIntegrationNodeName وFamily)
  • مفيد في الـ runtime إن يبقى عندك وصول real-time لتفاصيل node أو flow أو integration
  • بتوصل لبعضها من ESQL وMapping node وJava. طرق ESQL وJava بتستخدم NULL للقيم غير المضبوطة
  • مجموعة فرعية متاحة من JavaCompute nodes عبر classes: MbExecutionGroup (integration server) وMbNode وMbBroker (integration node)

الـ flow بيتسمى environmentally aware لو بيستفيد من خصائص الـ integration node. مثلًا يوجه الرسايل بشكل مختلف في production عن development. الخصائص دي ثوابت وقت التشغيل: ما تقدرش تعمل لها SET، ولو حاولت تيجي الرسالة Cannot assign to a symbolic constant. لو في ESQL عندك متغير بنفس اسم property، متغيرك بياخد الأولوية ويحجب الـ attribute. للوصول للـ attribute استخدم الصيغة SQL.<broker_attribute_name>، مثلًا:

SQL.BrokerName

الضبط للـ production

الـ deployment descriptor شبه environment variables: من غير تغيير في الكود، بتخصص databases وأسماء queues للنظام الهدف (development أو test أو production). مثال الكتاب: في التطوير Data source=TestDB، وفي META-INF/broker.xml بتحط Data source=ProductionDB لتتخطى القيمة، فالـ flow بيستخدم قيمة الـ deployer بدل قيمة المطور.

Development
بيتطور ويتجرب في بيئة معزولة. مصادر ووجهات البيانات (queues وdatabases) محدودة وغالبًا فيها subset من البيانات. الـ flow بيستخدم الموارد المضبوطة في node properties. ممكن رقم version يتتبع الكود (من source code management system أو mqsicreatebar). بديل: خاصية Version للـ flows والـ models
Test
الـ flow يتنشر على نظام نسخة مطابقة للـ production. تستخدم بيانات حقيقية لتحديد الأداء (throughput وعدد instances). الـ flow يشير لموارد Test
Production
الـ flow بيستخدم موارد production اللي بتتخطى اللي اتحددت في التطوير. القيم بتتحدد في BAR file editor أو وقت النشر بالأمر mqsiapplybaroverride

Node properties وUDPs

Node properties
بتضبطها في Message Flow editor، وممكن تتعمل promote لـ subflow. الـ BAR editor يقدر يتخطى بعض الـ environment-dependent properties. وقت التشغيل القيمة الفعلية متاحة من ESQL أو Java بـ ACE attributes
User-defined properties (UDP)
بتعلن القيمة الابتدائية (default) في Message Flow properties وفي ESQL (EXTERNAL variables) أو Java. الـ BAR editor يتخطاها. وقت التشغيل القيمة متاحة من ESQL variables أو JavaCompute node (getUserDefinedAttribute method)

الـ node properties أو الـ UDPs ممكن تحمل بيانات ضبط. تقدر تضبط الـ flow لنظام تشغيل أو مهمة أو بيئة وقت النشر من غير تغيير التنفيذ. استخدم UDPs لما ACE attributes ما بتدي المعلومة دي. استخدامات نموذجية: بيانات ضبط أو معلومات version. الـ UDP ثابت (constant) معرّف من المستخدم تستخدمه في ESQL أو Java، وممكن تدي له قيمة ابتدائية يعدلها المطور وقت التصميم أو الـ deployer وقت النشر. وقت التشغيل تقدر تسأل عن قيمته لكن ما تعدلهاش بعد الإعلان.

  • تعرّف UDP في: كود ESQL، أو Message Flow editor، أو BAR file override قبل النشر، أو الـ Integration API
أولوية التخطي
تخطي في BAR file أقوى من تغيير في Message Flow editor. وتغيير Message Flow editor أقوى من تغيير كود ESQL للـ UDPs.

مثال UDP

  1. تعلن UDP اسمه myProperty في الـ message flow
  2. في ESQL في الـ Filter node بتعلن EXTERNAL variable بنفس الاسم myProperty عشان تقابل الـ UDP
  3. زي كل UDPs، myProperty متاح في BAR file. قبل النشر تعدله في BAR file editor

Promoted properties

  • خاصية node في الـ message flow بتتعمل promote لمستوى الـ flow اللي هي فيه
  • في الـ subflow: promote properties. خصائص متوافقة من أكتر من node ممكن تتعمل promote لنفس الـ promoted property
  • في الـ main flow: ضبط الـ promoted properties كـ node properties للـ subflow

مثال الكتاب: الـ subflow فيه Compute nodes اتنين لكل واحد Data source (DEV1) وDatabase node. الـ main flow اللي بينادي الـ subflow له Data source كمان. لما تعمل promote لـ Data source في الـ subflow لمستوى الـ flow، أي تغيير للـ data source في الـ main flow بيتنقل للـ subflow. يعني لما تضبط Data source = PRODUCTION في الـ main flow، نفس القيمة بتروح للـ subflow حتى لو كانت DEV1. ولما تعمل promote لخاصية ما تقدرش تغير قيمتها في أدنى مستوى إعلان (في المثال، في الـ subflow).

خطوات Promote Property

  1. افتح الـ message flow في Toolkit Application Development perspective
  2. كليك يمين على الـ node واختار Promote Property. الـ Available node properties pane بيعرض كل الخصائص المتاحة لكل nodes الـ flow، وخصائص الـ node اللي ضغطت عليه مفتوحة
  3. اختار الخاصية أو الخصائص (Ctrl لتحديد أكتر من واحدة)
  4. اضغط Promote. يفتح Target Selection dialog box بالأهداف الصالحة
  5. اختار المجموعة أو الخاصية الهدف
  6. OK للتأكيد

معلومات Version وقت التشغيل

  • ممكن تحدد version ومفاتيح (keywords) أثناء تطوير message set: Version افتراضي في Version tag في message set preferences، وkeywords في Documentation property
  • وقت النشر BAR file فيه معلومات version
  • بتظهر في Toolkit وتطبيقات Integration API

وقت النشر بيتخزن لكل ملف جوه الـ BAR: وقت نشر الـ object، وآخر وقت حفظ في الـ BAR، واسم الـ BAR file اللي نشره، وVersion keyword من المستخدم، وkeywords تانية من المستخدم وقيمها (في مثال الكتاب: ErrorHandler Author وErrorHandler Version).

تضمين version في الـ flows

  • Version خاصية في الـ message flow
  • لمعلومات أكتر: ضمّن $MQSI..MQSI$ في حقول مش مستخدمة
  • في الـ main flows: في Long description
  • في ESQL comments أو strings
  • في الـ subflows: استخدم String field في Passthrough node، وكل subflow بـ version keyword مختلف
-- Long description of a main flow:
$MQSI Control flow version = v1.2 MQSI$
$MQSI Processing subflow version = v1.9 MQSI$
$MQSI Database subflow version = v1.8 MQSI$

-- ESQL comment or string:
-- $MQSI Compiled by = Pat MQSI$
Set target = '$MQSI target = production only MQSI$'

الـ Toolkit بيضمن Version keyword تلقائيًا في الـ flows والـ dictionaries لو دخلت version property في BAR File editor. بما إن في Version keyword واحد للـ main flow، لازم تضيف user keywords لو عايز تظهر versions الـ subflows.

تضمين keywords في أنواع الملفات

XML files
الـ keyword بيتضمن في الملف: $MQSI keyword = value MQSI$. تشمل: compiled message flows (.cmf)، message dictionaries (.dictionary)، XSL stylesheets (.xsl وxslt وxml)
ZIP files
الـ keyword بيتضمن في ZIP entry (META-INF\keywords.txt). تشمل: Java archives (.jar)، XSD archives (.xsdzip)، inbound adapter configuration (.inadapter)، outbound adapter configuration (.outadapter)

مش كل editors فيها دعم معلومات version بتاع ACE. تقدر تعرّف custom keywords وقيمها، وACE بيعتبرها معلومات إضافية بتظهر في properties view. لازم تتبع قواعد معينة عشان تتعمل parse.

الربط مع version control systems

  • كتير من الأنظمة زي CVS بتستخدم keyword systems بتتوسع لمعلومات لما تعمل check out
  • CVS أو RCS: $Revision: $ بتتوسع لـ $Revision: 1.3 $
  • SCCS: %I% بتتوسع لـ 1.3
$MQSI Version = %I% MQSI$
$MQSI Revision = $Revision: $ MQSI$

لما الملفات اللي فيها الـ strings دي تتعمل check out، نظام الـ version control بيحل قيمها. تقدر تاخد version numbers من الـ repository وتربطها بالـ flows وقت النشر، فتعرض في الـ Toolkit أنهي version منشورة. بديل: تحدد version في الـ Toolkit لما تنشئ الـ flow.

القسم 13.4: Message flow statistics

Accounting وstatistics

  • بتتضبط على مستوى integration server أو message flow
  • معلومات real-time عن استخدام flow وnode وterminal وthread
  • المستوى الافتراضي (message flow) تأثيره على الأداء قليل جدًا. مستوى terminal بيولد حجم بيانات كبير ويزود استخدام المعالج
  • snapshot قصير الفترة (حوالي 20 ثانية) وarchive collection لفترة أطول
  • التحكم بأوامر integration node غير تدخلي
  • الكتابة لوجهات مختلفة: published بـ XML تحت topic لو publication of events مفعّل وpublish/subscribe مضبوط مع IBM MQ أو MQTT، وUserTrace وSMF (System Management Facilities)

ACE فيه event monitoring وauditing بيدوك insight في الرسايل أثناء معالجتها. بيانات accounting وstatistics بتجمع معلومات ديناميكية عن سلوك الـ flow وقت التشغيل: كام رسالة اتعالجت وحجمها، واستخدام المعالج، وأوقات المعالجة. المشغّل ممكن يلتقط محتوى أي رسالة أو جزء منها في أي وقت في الـ flow من غير تغييره.

تفاصيل بيانات الـ statistics

Message flow
integration server name وintegration node name وflow name، وsample time وstart وend، وهل "Archive" أو "Snapshot"، وحجم (MMA: Minimum وMaximum وAverage) وعدد وbytes الرسايل المعالجة، وأوقات (MMA) elapsed وCPU وwait، وزمن الانتظار للإدخال، وthreads (total أو high water count)، وcommit أو backout count
Threads
رقم thread عشوائي، Message: Total processed، Total Times: Elapsed وCPU وWait وInput Wait، Min وMax input size
Nodes
Label name وType، أوقات (MMA) elapsed وCPU وwait، invocation count، Message: size (MMA) وعدد وbytes، وterminal labels وcounts

بيانات accounting وstatistics مرتبطة بـ accounting origin. لو عايز تتبع سلوك flow معين، حدد accounting origin فريد له وحلل نشاطه خلال فترة، بضبط الحقل Environment.Broker.Accounting.Origin في الـ flow في Compute أو Database أو Filter node. مثال: لو integration node بيستضيف flows لعميل معين في integration server واحد، تضبط قيمة origin معينة لكل الـ flows دي وتحلل الاستخدام (حتى تحاسب العميل أو القسم).

Statistics في ACE

  • ابدأ وأوقف جمع البيانات بالأمر mqsichangeflowstats أو ACE web user interface
  • طلب snapshot data collection من الـ web UI. أو snapshot أو archive أو الاتنين بالأمر mqsichangeflowstats
  • المستوى الافتراضي (message flow) تأثيره minimal
  • شوف الـ statistics لحظة توليدها من تبويب Statistics في IBM Integration web user interface
  • تقدر تضبط الجمع كمان بملف .yaml

القسم 13.5: Performance monitoring

دعم الـ monitoring في ACE

  • الـ events بتتنشر على well-known topic عبر IBM MQ أو MQTT لعدة consumers في نفس الوقت
  • صيغة الـ event هي XML: بتسمح بالتكامل مع تطبيقات monitoring تانية، وبتسمح بتسجيل الرسالة كلها في database للـ audit
  • الـ events اختياريًا بتتولد في نفس syncpoint للأداء الأمثل
  • تكامل مع IBM Business Monitor: متابعة وتحليل key performance indicators (KPIs)، وتوليد monitor model تلقائيًا، وفيه sample شامل مدمج

بعد إنشاء الـ monitoring profile ممكن يتنشر مع flow موجود أو على flow شغال، وتفعله أو توقفه بأمر تغيير flow monitoring. الـ events بتتنشر على topic محدد باسم integration node وintegration server واسم الـ event. ممكن تولد event وقت التصميم أو تشغيليًا في أي نقطة في الـ flow فيه الـ payload كله أو جزء منه. message driven bean بيلتقط الـ publication ويدفعه لـ common event infrastructure للتكامل مع IBM Business Monitor، اللي ممكن يحلل الاتجاهات مثلًا حجم التغييرات أو التقسيم حسب المنطقة.

توليد monitoring events في الـ Toolkit

  • كل node فيه Monitoring tab لتوليد events
  • بداية الـ transaction ونهايتها والـ rollback بتتبعت من input nodes، ومن أي terminal على أي node
  • تضبط payload data وcontent style وidentity وcorrelation وsequencing
  • طبيعته غير تدخلية فممكن تطبق monitoring profile على flows موجودة
  • Event filters لتحديد شروط إنشاء الـ event بالضبط، مثلًا: msg.Price>100

مثال: ممكن تحتاج تلتقط أول 3 حقول من رسالة إدخال في نقطة معينة، أو الـ payload الكامل لرسالة الإخراج. بتحدد المتطلبات في Monitoring tab في node properties بتعليم check box بجانب الـ event (Transaction start أو Transaction end). في مثال الكتاب MQInput node متفعل عليه: Transaction start وTransaction end وTransaction rollback وOut terminal. وفيه sequencing وcorrelating information وشكل الـ payload. والـ event filters بتولد events بس لما شرط معين يتحقق.

ضبط event monitoring بالأوامر

mqsichangeflowmonitoring -c active
mqsichangeflowmonitoring -i enable
mqsireportflowmonitoring
  • الأمر الأول يفعّل monitoring للـ flow، والتاني يفعّل event sources، والتالت للتأكد إن event sources مفعّلة
  • monitoring profile configurable service بيتخطى monitoring properties للـ flow
  • الـ monitoring profile ممكن يتستخدم لتخصيص events من غير إعادة نشر الـ flow
  • الأمر mqsicreateconfigurableservice يرحل configurable services لـ policies
تنبيه إصدار
الكتاب بيقول mqsicreateconfigurableservice بينشئ policy مكافئ لـ configurable service من IBM Integration Bus 10، وهو deprecated في ACE ومتوفر كأداة ترحيل. زي ما اتقال في Unit 10.

القسم 13.6: Record and replay

  • تسجيل وتعديل وإعادة تشغيل (replay) البيانات أثناء المرور (in-flight data)

  1. يحصل trigger event يسبب وضع تفاصيل الرسالة في queue. مثلًا خطأ معالجة في الـ flow

نسخ متعددة من الـ message flow

More integration servers

More integration nodes

instance إضافية (جوه integration server) معناها thread إضافي. في بعض الحالات instances أكتر ما بتدي فصل كفاية. integration servers مختلفة بتدي فصل على مستوى process أو address space، وده بيفرضه نظام التشغيل، وهو أقصى فصل وأغلى في الموارد. إضافة instances شغل قليل (بتغير عدد النسخ بس). لو في integration servers كتير، إدارتها في الـ Toolkit ممكن تبقى مشكلة. إنشاء integration nodes متعددة أكتر حاجة بتأثر: كل queue manager لازم يتوصل بالـ topology الموجود، وبتحتاج ذاكرة ومعالج وdisk أكتر.

  • لما تحتاج نسخ أكتر: استخدم more instances الأول لزيادة throughput
  • لو مش ممكن: جرب multiple integration servers لاستخدام السيرفر قدر الإمكان
  • لو لسه محتاج زيادة: استخدم multiple integration nodes
  • حدد أفضل استخدام للـ instances والـ integration servers قبل ما تكرر الـ integration node
  • متطلبات الأعمال ممكن تحتم إن flows معينة ما تشتغلش في نفس integration server
  • flow ثقيل الموارد (معالج أو ذاكرة كتير): خصصه لعدد محدود من integration servers عشان تحصر تأثيره (high water mark كبير للذاكرة الافتراضية ممكن يسبب paging أو swapping)

لتحديد عدد النسخ لازم تعرف أو تقدر معدل الرسايل المستهدف وتقارنه بالمعدل مع نسخة واحدة، وتقيس. وحدد هدف إجمالي: معدل رسايل معين أو استخدام معالج معين أو أكفأ تشغيل (مش دايمًا أقصى معدل). شغّل نسخة واحدة برسالة واقعية. لو الـ flow بيعالج أنواع رسايل متعددة، حطها كلها بنسبها الصح. حمّل input queues باستمرار للوصول لحالة steady state. قس throughput بأدوات زي vmstat لتحديد حالة النظام. من القياسات دي تعرف هل المعالج أو I/O هو الحد، وممكن تحتاج تغيير الـ hardware.

Scaling لـ message throughput

  • القدرة على التوسع بتعتمد على: موارد كافية (معالج وذاكرة وأقراص)، وإمكانية جدولة أعمال متعددة بالتوازي، وتطبيق مناسب (من غير contention)
  • الـ hardware مسألة تخطيط
  • الـ integration node يقدر يشغل نسخ متعددة من الـ flow
  • الـ contention مسألة تصميم التطبيق. بتأثر فيها: message type، ومستوى الوصول للـ queue، وطبيعة معالجة الـ database (insert-delete-update مقابل read-only)

صعب تتنبأ بدقة بفايدة نسخ متعددة لأنها بتعتمد على تصميم الـ flow. لكن لازم يكون في خصائص عشان الـ flow يتوسع كويس: مستويات I/O قليلة (queue أو database) لأن I/O بتحط حد أقصى أقل لمعدل الرسايل من حد المعالج، ووصول قليل للـ queues، وinsert وdelete وupdate قليلة على database لأن القراءة أكتر scalability بكتير. لما تضيف نسخ، هدفك توازن بين throughput والموارد. غالبًا بتوصل لحد مورد معين (مثلًا سرعة إدخال الرسايل في database)، فالتحسن بيقل وتوصل لـ plateau.

الأساسيات لزيادة throughput في أي transaction أو messaging software: موارد فيزيائية (معالج وذاكرة وأقراص)، وإمكانية جدولة أعمال متزامنة (multiprogramming)، وأقل contention في التطبيق. مثال: لو كل عنصر معالجة يحتاج سجل تحكم مركزي، ده نقطة contention تحد من الاستفادة. الـ contention بين flows مش متوقع: بيعتمد على كتابتها والبيانات اللي بتشير لها. انتبه لمستويات وصول عالية لـ queues قليلة ومعالجة database. لو الرسايل موزعة على input queues متعددة، فرصة contention أقل. الـ persistent messages بتتقفل وقت أطول من nonpersistent لأن I/O بيحصل في الـ log، وأقصى معدل أقل. في معالجة database: تجنب control records تستخدمها flows متعددة. insert وdelete وupdate أثقل من القراءة لأن التغييرات لازم تتسجل في log.

Tuning الـ integration node

  • لما تتصل بـ IBM MQ: شغّل كـ trusted application لتحسين الاتصال بالـ queue manager
  • Traces وtrace nodes: integration node trace بيستهلك معالج كتير. عطل Trace node output من web UI أو بالأمر mqsichangetrace -n
  • أوقف كل user وservice level traces جوه الـ integration node

mqsichangetrace بيمنع output الـ Trace node من غير ما تمسح الـ Trace nodes من الـ flow، والـ Trace nodes المعطلة ما بتتكلفش معالجة إضافية.

Tuning الـ IBM MQ queue manager

  • افحص أداء الـ queue managers المتصلة وتأكد من ضبطها الأمثل
  • شغّل queue manager channels وlistener كـ trusted applications لتقليل استهلاك المعالج وزيادة throughput
  • Logging: مع الرسايل persistent، راجع log buffer settings وسرعة الجهاز اللي عليه log الـ queue manager. الـ overhead بيختلف حسب hardware ونظام التشغيل والـ flow. قلل أزمنة I/O

لو الـ flows بتعالج رسايل IBM MQ، خلي الـ integration node أقرب ما يمكن للرسايل المعالجة. لو الرسايل الخارجة لازم تتنقل لـ queue manager بعيد، التكلفة بتزيد مع الـ persistent، لأن كل رسالة بتتسجل أكتر من مرة وهي بتنتقل من queue manager لتاني. مع persistent، الـ queue manager لازم يكتب بشكل synchronous في الـ log وقت commit قبل ما تكتمل الـ unit of work، والـ write ده ممكن يزود الموارد بشكل ملحوظ (وده واضح لما تقارن معدلات persistent وnonpersistent). لما تظبط logging فكر كمان في log buffer وextent size: extents كبيرة معناها تبديل أقل بين extents. في نظام queue managers فيه مترابطة، الاتنين لازم يتضبطوا لـ logging كفء لأن log الاتنين بيتستخدم لما الرسايل بتتحرك عبر الـ channel.

Tuning الـ databases

  • الاستخدام بيتغير حسب تركيبة الـ flow
  • Dynamic caching: ممكن يدي مكاسب كبيرة، راقب فعاليته
  • عدد database connections: لكل integration node، connection واحد لكل thread (ODBC-DSN). اضبط MAXAPPLS للـ database (DB2). الـ connections بتتحمل لحد ما الـ integration node يقف
  • قلل وقت log وdata I/O
  • أوقف trace (database وODBC)

لو مفيش وصول لـ database مفيش tuning. استخدام البيانات من read-only لـ update-insert-delete، ونوع المعالجة بيحدد فين تركز مجهود الـ tuning. اتأكد إن database trace وODBC trace مطفيين (ODBC tracing بيتحكم فيه بشكل مختلف على كل نوع hardware ونظام). لو الـ flows بتوصل لـ database كتير، caching الـ dynamic SQL بيدي فايدة كبيرة: من غيره كل وصول لازم يتعمل له SQL PREPARE وبعدين SQL EXECUTE، والـ compilation مكلف نسبيًا والهدف تقليل عدد مرات حصوله. الـ connection من الـ flow لـ database manager بيتعمل أول طلب database في الـ flow. حسب عدد الـ connections المعرفة وعدد instances الـ flow، مش كل الطلبات هتتوصل، وده بيقلل الـ throughput. افحص توزيع data وindex buffers وتأكد من buffer hit ratios كويسة. فكر في read-only view للجداول اللي نادرًا بتتحدث: بيقلل locking ويحسن القراءة. insert وdelete وupdate بتحتاج synchronous write في log الـ database manager، فخلي الـ log على جهاز سريع. والـ BLOB المكتوب في database بيتكتب على disk فورًا (مش buffered)، فلو BLOB I/O متكرر، حط data portion على جهاز سريع.

اكتشاف وإزالة العوائق

  • اختبار أداء الـ flows ضروري، منفردة وكلها مع بعض: شغّل كل flow بـ 1 و2 و4 integration nodes (حسب الكتاب)، واخلط الـ flows في integration server، وقس وقس وقس (measure, measure, measure)
  • حاكي بيئة production: نفس hardware ونظام التشغيل ونفس الضبط
  • شغّل أكتر بكتير من المتطلبات الحالية
  • جرب لإيجاد أفضل ضبط للبيئة
  • ابدأ بنوع الرسالة المطلوب للـ production: اتأكد إنك تقدر تستخدم الـ hardware بالكامل، وحاول تلاقي العائق
  • لو النظام I/O bound، جرب تزود عدد الـ flows
  • اختبر ببيانات سيئة للتأكد من error handling صح

ممكن تلاقي إن كل حاجة تمام مع نسخ قليلة، والوضع بيتغير مع نسخ أكتر، ولازم تكتشف ده قبل production. لو الـ flow بيعالج رسايل IBM MQ، اختبر بـ nonpersistent الأول حتى لو هتستخدم persistent في production، لأنه بيشيل حد I/O ويكشف عائق ممكن ما يظهرش. اختبر ببيئة تعكس production، وغالبًا فيه تدفق مستمر للرسايل مش دفعات: غالبًا في الاختبار بيتحمل عدد رسايل كبير على queue وبعدين تتعالج، وده بيدي نتائج مختلفة عن إعادة تعبئة input queues باستمرار.

If messages are located over multiple input queues, there is less chance of contention than if a single queue is used for all message processing. • Message type is also a factor. In addition, the maximum message rate that is achieved with persistent messages is lower than messages as there is an obvious I/O limitation. • Consider carefully any database processing. Avoid control records that multiple message flows use. Realize that insert, delete, and update processing is more intensive than read processing. With insert, delete, and update activity, changes must be logged.

The type of processing that takes place determines where you must place your tuning effort. • Ensure that both database and ODBC trace are turned off. ODBC tracing is controlled differently on each of the different hardware and operating system types. • Where message flows frequently access a database, a significant performance benefit can be obtained by caching the dynamic SQL, which is generated when access occurs. Without such caching, each data access must be compiled by using an SQL PREPARE statement and then run by using an SQL EXECUTE statement. The compilation is relatively expensive. The aim is to significantly reduce the number of times it takes place. • Ensure that each database is configured with sufficient connections. The connection from the message flow to the database manager is made on the first database request in the flow. Depending on the number of connections that are defined within the database manager and the number of instances of the message flow, not all requests can be connected, which obviously reduces the throughput potential. • Examine the allocation of data and index buffers, and ensure that there are enough to meet your needs. Also, verify that good buffer hit ratios are obtained. • Consider creating a read-only view of those tables, which are rarely, if ever, updated. A read-only view reduces locking by the database manager and leads to better read performance. • When a database insert, delete, and update activity takes place, a synchronous write to the database manager log is required. It is important to ensure that the database log is on a fast device. • A BLOB written to a database is an immediate write to disk. It is not buffered like other data. If BLOB I/O is frequent, it is beneficial to locate the data portion of the database on a fast device.
