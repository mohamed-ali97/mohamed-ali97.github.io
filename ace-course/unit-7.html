Processing file data

ACE مش بس رسايل MQ. تقدر تقرا ملفات وتكتبها، محليًا أو عبر FTP وSFTP. هنا هتفهم الـ file nodes، إزاي ملف كبير يتقسم لـ records، وإزاي تتعامل مع الأخطاء.

  • وصف الـ file processing nodes
  • وصف خيارات record detection لتقسيم الملفات
  • استخدام ملف كمصدر وكهدف للـ flow
  • استخدام FTP وSFTP مع file input/output nodes

الـ integration node بيقرا ملفات بـ FileInput وFileRead وFTEInput وCDInput، وبيكتب بـ FileOutput وCDOutput وFTEOutput. الـ Unit بيشرح الـ generic nodes بس: FileInput وFileRead وFileOutput.

القسم 7.1: FileInput node

  • بيستقبل رسايل من ملفات في الـ file system بتاع الـ integration node، أو من remote file system بـ FTP أو SFTP
  • بيشغّل الـ flow لما ملف جديد يوصل
  • التركيز على المعالجة مش على تسليم الرسايل
  • لو الـ End Of Data terminal موصول: بيتشغّل بعد معالجة كل رسايل الملف، برسالة BLOB فاضية وLocalEnvironment.File structure

الـ FileInput وFileOutput مدعومين على كل أنظمة التشغيل. على z/OS الملفات بتتحل في HFS أو ZFS وأسماء الملفات case-sensitive زي UNIX. الـ End of Data message بتسمح بمعالجة نهاية الـ flow صراحة في جزء تاني منه.

الخوارزمية الأساسية

  • بيمسح directory معد مسبقًا عن ملفات تطابق مواصفات معينة. مثال: Input directory = /home/sales/files، وFile name pattern = *.txt
  • أقدم الملفات بتتعالج الأول
  • لما يخلص الـ directory الخوارزمية بتتكرر
  • Include local subdirectories: يعالج الملفات تحت الـ Input directory
  • subdirectory اسمه mqsitransitin بيحتفظ بالملفات ويقفلها أثناء المعالجة. افحصه لو فيه ملفات معالجتها ناقصة أو ما اتعالجتش

اسم الـ directory بيتحدد في تبويب Basic وبالصيغة اللي الـ file system متوقعها. افتراضيًا الـ subdirectories مش بتتمسح. اسم الملف ممكن يكون wildcard: * (أحرف متعددة) و? (حرف واحد). قيمة الـ directory لازم تكون مسار كامل أو نسبي لـ $MQSI_WORKPATH/file. لو الملف عليه lock من نظام التشغيل مش هيتقرا لحد ما الـ lock يتشال. لو المسح ما لقاش حاجة، الـ node بيستنى فترة (الافتراضي 5 ثواني) قبل ما يمسح تاني.

لما المعالجة تنجح

  • الملف بيتمسح أو بيتنقل لـ subdirectory اسمه mqsiarchive (بيتنشأ لو مش موجود)
  • الـ LocalEnvironment فيه تفاصيل الملف: LocalEnvironment.File.Directory وName وLastModified وTimeStamp، وLocalEnvironment.Wildcard.WildcardMatch

لو الملف موجود في الـ archive بنفس الاسم وما اخترتش overwrite، الـ node بيعمل exception. لتجنب تكرار الأسماء اختار rename وإضافة time stamp (بدقة milliseconds). محتوى الملف ما بيتغيرش. الـ node بيخزن معلومات الملف في الـ Local Environment للـ nodes اللي بعده. والـ WildcardMatch فيه الحروف اللي طابقت الـ wildcard: لو الـ pattern file*.txt والملف file02.txt، القيمة 02. الـ output node يقدر يستخدمها لاشتقاق اسم ملف الإخراج من الإدخال.

ضبط الـ FileInput node

  1. تبويب Basic: الـ directories والملفات والفعل لو فيه ملفات مكررة
  2. تبويب Input Message Parsing: قيم الـ parsing
  3. تبويب Polling: الـ polling interval
  4. تبويب Retry: إزاي تتم إعادة المحاولة لو الـ flow فشل
  5. تبويب Records and Elements: إزاي كل ملف يتفسر كـ records

الـ node بيقرا raw bytes من الملف قبل الـ parser. في Input Message Parsing فيه حقلين غير عاديين للتعامل مع الحروف: Message coded character set ID وMessage Encoding، فتقدر تحلل معلومات من نظام تشغيل غير اللي الـ node شغال عليه. ملف واحد بيتعالج بـ instance واحد وnode واحد على الأكثر، لكن ملفات تانية في نفس الـ directory ممكن تتعالج بالتوازي. تبويب Instances بيسمح بـ thread pool مخصص للـ node، ومفيد لما يكون فيه input nodes كتير، لأن الـ thread pool المشترك ممكن يجوّع input node. تحويلات FTP ممكن تاخد وقت وتشغل الـ thread، فظبط additional instances لأعلى throughput. لو المسح ما لقاش ملفات، الـ node بينقل ملفات من FTP server المظبوط للـ local directory، والملفات المنقولة بتتمسح من الـ FTP server.

Record detection

  • الـ FileInput بيقسم كل ملف لـ records منفصلة، والـ flow بيتشغل أكتر من مرة
  • بس record واحد في الذاكرة في أي وقت: streaming فعال للملفات الكبيرة (ممكن gigabytes)
  • الـ streaming ممكن مع DFDL وXMLNSC وMRM (CWF وTDS) بس
  • الخيارات في تبويب Records and Elements

ملف واحد بيتعالج بـ thread واحد فقط في الـ integration node، فالـ records بتتعالج بالتتابع مش بالتوازي.

Whole file
كل ملف يطلع رسالة واحدة. بيقرا الملف كله في الذاكرة، فتأكد إن الذاكرة كافية
Fixed length
تحدد طول كل record بالـ bytes (لحد 100 MB). آخر رسالة ممكن تبقى أصغر
Delimited
system line-end أو delimiter مخصص (بـ hexadecimal). النوع: infix أو postfix
Parsed record sequence
الملف فيه واحد أو أكتر من structures يقدر الـ parser المحدد يحللها، وكل structure مطابقة تتبعت كرسالة منفصلة
  • Infix: لو آخر بيانات في الملف بتنتهي بـ delimiter، الـ node بيبعت record فاضي ليدل على وجوده
  • Postfix: ما بيبعتش record فاضي سواء الملف انتهى بـ delimiter أو لأ

أمثلة record detection

الملف: Belgian Bun|10|Jam tart|9|Gingerbread man|8|

Whole file
رسالة واحدة: "Belgian Bun|10|Jam tart|9|Gingerbread man|8|"
Fixed length (10 bytes)
خمس رسايل: "Belgian Bu", "n|10|Jam t", "art|9|Ging", "erbread ma", "n|8|" (آخر واحدة 4 bytes)
Delimited بـ "|" — Infix
سبع رسايل: "Belgian Bun", "10", "Jam tart", "9", "Gingerbread man", "8", ""
Delimited بـ "|" — Postfix
ست رسايل: نفس الأولى من غير الفاضية
Parsed record sequence مع XMLNSC
تلات رسايل، كل واحدة XML document مستقل (cakes/cake بـ name وrating). الملف كله مش XML صالح، لكن كل instance صالحة لوحدها

معالجة الأخطاء في FileInput

  • عند الفشل الـ node بيحاول يعيد المعالجة عدد مرات قابل للضبط
  • لو لسه فشل: Action on failing file = نقل الملف لـ subdirectory اسمه mqsibackout أو مسحه

  • لو الـ node فشل قبل ما الرسالة توصل Out terminal، الرسالة تروح Failure terminal
  • Transaction mode في تبويب Transactions يحدد هل الـ flow يطلّع رسايل تحت transaction منسق. الكتابات المكتملة ما بتتراجعش لو حصل فشل

FileInput مع FTP وSFTP

  • في تبويب FTP اختار Remote Transfer ثم Transfer Protocol (FTP هو الافتراضي، وغيره لـ SFTP)
  • لما يكون شغال بيجيب ملفات من السيرفر البعيد دوريًا للـ local input directory
  • الـ security identity بيتحدد بالأمر mqsisetdbparms
mqsisetdbparms InteNodeName -n ftp::Security_identity -u ftpUser -p ftpPassword
مثال: mqsisetdbparms ACENODE -n ftp::SecurIdent -u user1 -p MyPassword

الـ node بيشتغل شبه معالجة الملفات العادية: بيمسح directory الـ FTP server عن ملفات جديدة وينقلها للـ local directory ويعالجها كملف محلي. لاحظ الصيغة: بعد ftp لازم :: وبعدها الاسم المكتوب في خاصية Security identity في تبويب FTP، ولازم يطابق المعامل في mqsisetdbparms.

أمان
في أي مثال، ما تكتبش password حقيقي في تاريخ shell أو في ملف مشترك. الأمر ده بيخزن الـ credentials لـ ACE.

القسم 7.3: FileRead node

  • بيقرا record واحد أو محتوى الملف كله من نص الـ flow
  • بيوفر keyed access لتحديد record
  • أي parser يقدر يحلل محتوى أي ملف ويبعته كـ message tree
  • افتراضيًا بعد نجاح الإرسال الملف بيتمسح
  • ما فيش file node تاني يقدر يوصل للملف لما FileRead يبدأ يقرا منه

FileRead زي FileInput لكن بيتشغل برسالة داخلة (مش في أول الـ flow). لو ما فيش ملف مطابق، الرسالة الأصلية بتتبعت لـ No match terminal، ولو مش موصول يحصل exception. ممكن تضبط الـ node ما يمسحش الملف، وساعتها أي file read node تاني يقدر يوصل له لو في نفس browse only mode.

ضبط FileRead

  1. Basic: الـ directories والملفات والفعل لو مكررة
  2. Request: مكان البيانات المراد قراءتها بـ XPath أو ESQL
  3. Result: أين تتخزن النتيجة
  4. Input Message Parsing: الـ parsing
  5. Parser Options: غيّر Parse timing لـ Immediate أو Complete لو الرسالة كلها لازم تتحلل فورًا
  6. Records and Elements: إزاي كل ملف يتفسر كـ records

ملخص الـ Unit

  1. FileInput بيشغل الـ flow لما ملف يوصل، FileOutput بيكتب، FileRead بيقرا في النص.
  2. Record detection: Whole file وFixed length وDelimited وParsed record sequence.
  3. الـ streaming بيسمح بملفات كبيرة مع DFDL وXMLNSC وMRM.
  4. أخطاء الملف: retry ثم mqsibackout أو delete.
  5. FTP/SFTP عبر تبويب FTP وmqsisetdbparms.

Figure 7-5 FileInput node

FileInput: بيستقبل رسايل من ملفات في نظام ملفات الـ node أو عبر FTP/SFTP من نظام بعيد، وبيشغّل الـ flow لما ملف جديد يوصل. التركيز على معالجة الرسايل مش توصيل الملفات. على z/OS الملفات بتتحل في HFS أو ZFS (حساسة لحالة الأحرف).
نص الكتاب الأصلي
• It is possible for the integration node to read and write files from and to the local file system. It is also possible to read and write files to and from an FTP server. The focus of the file support in IBM App Connect Enterprise is on message processing, rather than message delivery. • Support for the FileInput and FileOutput nodes is available on all supported operating systems. On z/OS, files are resolved in the HFS or ZFS file system, and file names are treated in the case-sensitive UNIX manner. • There are specific terminals, both on the File Input and File Output nodes, for handling the end of the file. On the File Input node, the End of Data terminal is given control when the integration node detects that it reaches the end of the input file. The End of Data message comprises an empty BLOB message together with a LocalEnvironment.File structure. It allows explicit end-of-flow processing in another part of the flow. • On the FileOutput node, the Finish File terminal is driven to indicate to write the file to the file system.

Figure 7-6 FileInput node: Basic algorithm

الخوارزمية الأساسية: الـ node بيفحص دورياً مجلد محدد (مثلاً /home/sales/files) عن ملفات تطابق نمط (مثلاً *.txt). افتراضياً المجلدات الفرعية مش بتتفحص (ممكن تفعلها). بيقرا الملف المطابق، ويبعت محتواه للـ flow.
نص الكتاب الأصلي
• The FileInput node can read through a preconfigured directory on the file system of the integration node. The directory name is configured on the Basic tab of the node and must be entered in the format that the integration node file system expects. The integration node scans the directory for files. By default subdirectories of the directory are not scanned but you can configure FileInput node to include local subdirectories. • The files to process must be present in the specified directory. The file name can be specified as a wildcard. Acceptable wildcards on the file name pattern are an asterisk (*), which matches multiple characters, and a question mark (?), which matches a single character. The value for the directory must either be a fully qualified directory path, or a directory relative to $MQSI_WORKPATH/file. • After the first file in the directory is processed, the next file in the directory is processed. After all of the files are processed, the directory is rescanned. If there is an operating system lock on a file, it is not read until the lock is removed. If any files that were previously locked are now unlocked, the integration node processes them. • If a directory scan yields no matches, the node waits for a preconfigured amount of time before rescanning. The default value for this interval is 5 seconds.

Figure 7-7 FileInput node: Successful processing

بعد المعالجة الناجحة: الملف يتحذف أو يتنقل لمجلد فرعي mqsiarchive (بيتعمل لو مش موجود). لو في الأرشيف ملف بنفس الاسم لازم تحدد خاصية overwrite وإلا بيحصل exception. وLocalEnvironment.File فيه تفاصيل الملف: Directory وName وLastModified وTimeStamp.
نص الكتاب الأصلي
• After the file is parsed, an option on the node specifies what to do with the file. The options are to delete the input file, or move it to an archive subdirectory of the input directory. If the archive subdirectory (mqsiarchive) does not exist, it is created. • If an archive file exists, a property on the FileInput specifies the actions to take. If you do not set the option to overwrite the file, the node generates an exception if it tries to move a file that is successfully processed with the same name into the archive subdirectory. To prevent duplicate file names, you can select the options to rename the file and include time stamp value in the name. The time stamp includes the time to millisecond granularity, ensuring the uniqueness of file names in the archive directory. When the file is placed into the archive directory, the contents of the file are not altered. • Each time the contents of a file are propagated, the FileInput node stores information about the file inside the Local Environment, which is available in subsequent nodes in the message flow. Also, the FileInput node copies the characters in the file name that the wildcards match, together with any intermediate characters, to the WildcardMatch element. Thus, if the match expression was file *.txt and the file read was file02.txt, then the value of WildcardMatch would be 02. An output node can use this information, where the output name can be derived from the input name.

ضبط FileInput: تبويب Basic: المجلدات والأنماط والتصرف مع الملفات المكررة. تبويب Input Message Parsing: الـ domain والـ message set، وفيه حقلين خاصين: Message coded character set ID وMessage Encoding عشان تقرا ملفات جاية من نظام تشغيل مختلف. الـ node بيقرا bytes خام قبل الـ parser.
نص الكتاب الأصلي
• The FileInput node reads raw bytes from the file that came from the file system before passing it on to the parser. The Input Message Parsing property tab on the FileInput node has two nonstandard fields for handling character data: Message coded character set ID and Message Encoding. These properties make it possible to parse information from an operating system other than the one in which the integration node is running. • At most, one instance and node processes each file. More instances and nodes might concurrently process other files in the same directory. The FileInput node has an Instances tab to enable the use of a dedicated thread pool for the node. This feature is useful in message flows that have multiple input nodes, as the pool of threads of the flow can lead to the starvation of one or more input nodes. In particular, FTP transfers might take a significant amount of time to complete, during which time the thread is busy. For this reason, it is important to tune the additional instances parameter to maximize throughput rates. If no files are found during the directory scan, the node transfers files from the configured FTP server to the local directory that is being used for file input. Transferred files are deleted from the FTP server.

Figure 7-9 Record detection

Record detection: الـ node يقسم الملف لسجلات منفصلة، والـ flow يبدأ مرة لكل سجل. الفايدة: سجل واحد بس في الذاكرة في كل وقت (streaming)، فتقدر تعالج ملفات بحجم جيجابايتات.
نص الكتاب الأصلي
• The FileInput node can split each file into multiple records that are propagated separately. • One particular benefit of record detection is that, depending on the parser that is being used, the FileInput node does not need to store the whole file in memory at any one time. Only the records currently being processed are stored in memory. This streaming allows for large files to be processed. Such files can be several gigabytes in size. The DFDL, MRM, and XMLNSC parsers support streaming. • Record detection allows a file to be split into individual parts by using several techniques. Alternatively, the whole file can be processed as a single entity. Also, a single thread only within the integration node can process a file. Therefore, individual records can be processed only sequentially, not in parallel.

Figure 7-10 Record detection options

الخيارات: Whole file (كل ملف رسالة واحدة، لازم الذاكرة تكفي)، Fixed length (حجم ثابت بالـ bytes لحد 100MB، آخر سجل ممكن يبقى أصغر)، Delimited (نهاية السطر أو فاصل مخصص)، وParsed record sequence (الـ parser نفسه بيحدد نهاية كل سجل، مثلاً DFDL).
نص الكتاب الأصلي
• Whole File reads the entire contents of the file into memory and parses it in its entirety, according to the Inbound Message Parsing options. If this option is used, you must ensure that the available memory in the integration node is sufficient to accommodate the whole file. • Fixed Length breaks the file into a set number of bytes and propagates each chunk as a separate message. The last message in any file can be smaller than the specified length. If you use this option, specify the record size on the FileInput node. • Delimited specifies a delimiter that is used to break the records in a file. In this case, you can specify a standard DOS or UNIX end-of-line delimiter, or a custom delimiter by specifying the hexadecimal characters that indicate the end of line for the particular file. If you specify Delimiter type=Infix and the last data in the file ends with a delimiter, the FileInput node propagates an empty record to indicate the presence of the delimiter. If you specify Delimiter type=Postfix, the FileInput node does not propagate an empty record, whether the last data in the file ends with a delimiter. • Parsed Record Sequence breaks the file into messages, each of which conforms to a single structure as defined on the Inbound Message Parsing options.

Figure 7-11 Record detection examples

مثال الملف: Belgian Bun|10|Jam tart|9|Gingerbread man|8|. Whole file: رسالة واحدة بكل المحتوى. Fixed length 10: خمس رسايل (أول أربعة 10 bytes والأخيرة أقصر). Delimited بفاصل مخصص: رسالة لكل جزء. الاختيار بيحدد كام مرة الـ flow يشتغل.
نص الكتاب الأصلي
By using the Record detection options, an example file, which is shown at the top of the figure, can be processed in different ways: • The file can be processed as a whole file. In this case, the entire file is passed to the message flow as a single piece of data in the message tree. • The file can be split into sections of 10 bytes each. In this case, the FileInput node propagates five messages to the flow: the first four messages have 10 bytes each. The last message has 4 bytes. • The file can use a delimited parser, with a vertical bar as a delimiter. In this case, if the Delimiter Type is infix, seven messages are propagated, where the last record is an empty record. If the Delimiter Type is postfix, six messages are propagated. For the parsed record sequence example, the input file content is not a single valid XML document, but rather 3 distinct XML documents that are propagated separately. On their own, the contents of the file would not pass a validation test of the XML. But, but when it is split into multiple instances of XML, each single instance would be valid. In this case, if the parser is set to XMLNSC, then three messages are propagated to the message flow.

Figure 7-12 FileInput node error handling

معالجة الأخطاء في FileInput: Retry Mechanism: Failure (الافتراضي، يتعامل كفشل)، Short Retry (محاولات عدد معين)، Short and Long Retry (بعد الـ short يكمل محاولات للأبد بفاصل long retry). وخاصية Action on failing file بتنقل الملف الفاشل لمجلد mqsibackout.
نص الكتاب الأصلي
Each FileInput node has a configurable Retry Mechanism: • Failure (default): If the file cannot be read, then it is processed as a failure. • Short Retry: The integration node tries a number of times before processing as a failure. • Short and long retry: After the number of short tries are exhausted, the node continues to try indefinitely, waiting for the Long retry interval period between tries. The Action on failing file option determines failure processing: • Move to Backout Subdirectory writes the file to a backout subdirectory, which is created as a subdirectory of the input directory. If a file of that name exists in the backout directory, the message flow fails, and the failure is reported. • Delete deletes the input file and processes the next file to process. • Add timestamp and Move to Backout Subdirectory renames the failing file so it includes a time stamp. This process helps ensure that duplicate files cannot exist in the mqsi-backout subdirectory.

Figure 7-13 FileInput node that uses FTP

القراءة من FTP/SFTP: على تبويب FTP فعّل Remote Transfer واختار Transfer protocol (FTP افتراضياً أو SFTP). الـ node بيشتغل شبه معالجة الملفات المحلية وبيعمل polling دوري للسيرفر ويجيب الملفات المطابقة.
نص الكتاب الأصلي
• It is possible to use the FileInput to read files from an FTP server. As shown in the figure, FTP, or SFTP support is enabled by selecting Remote Transfer on the FTP tab of the FileInput node. The Transfer protocol property is FTP by default. If you want to use SFTP, change the Transfer protocol property to SFTP. • When using the FTP/SFTP function, the integration node operates in a way that is similar to normal file processing. The FTP server directory is scanned for new files, and any files that are detected are moved into the local file directory that is specified on the FileInput node. The integration node then processes these files as a local file. • The security authorization for the FTP server can be specified by using the Security identity property on the FTP tab. The value that is specified for this option must match the parameter that is specified on the mqsisetdbparms command. When using the mqsisetdbparms command, note the format of the ftp parameter. A double colon (::) must follow ftp, which is then followed by the name that is specified in the Security identity property on the FTP tab of the File node. For example: mqsisetdbparms ACENODE -n ftp::SecurIdent -u user1 -p MyPassword

Figure 7-16 FileOutput node processing

رسالة الـ body بتتكتب للملف المحدد. معلومات المكان ممكن تتحط في الشجرة. اسم الملف ممكن فيه * واحدة بتتبدل بقيمة LocalEnvironment.Wildcard.WildcardMatch (في سيناريو FileInput ← FileOutput بتتملي تلقائياً من اسم الملف الداخل).
نص الكتاب الأصلي
• The FileOutput node is similar to the FileInput node in that, in its simplest form, you can specify both the directory to which files are placed and a file name expression. • The file name expression can include a single asterisk (*) wildcard character, which is replaced with the value of the LocalEnvironment.Wildcard.WildcardMatch element in the tree. For example, in a FileInput to FileOutput scenario, the WildcardMatch element is set during the FileInput node processing. This match element can be used to preserve the name of the input file on the FileOutput node. You can also use standard tree manipulation logic in a transformation node to set the value of the WildcardMatch element to whatever you want, regardless of whether you used a FileInput node. For example, this value can be used to specify the name of the output file. • It is also possible to override the target directory and file name information. By default, this information is obtained from the local environment, although it can be any place in the message tree. These parameters override any hardcoded values that you specified on the Basic tab. • When you are writing to a file with a name that exists in the output directory, various Output File Actions can be selected in the Basic tab: ▪ Replace the existing file overwrites the existing file, with no further warning. ▪ Create the file normally, but fail if the file exists passes control to the Failure output terminal. ▪ Archive any existing file before over-writing it copies the original file to an archive directory. ▪ Archive previous file, with timestamp is similar to the previous option, but you can also change the name of the original file by adding a time stamp to the file name. As with the FileInput node options, this option avoids overwriting an existing file, since the time stamp is unique.
