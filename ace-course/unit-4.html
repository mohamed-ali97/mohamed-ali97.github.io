القسم 4.1: نظرة عامة على IBM MQ

IBM MQ بيعمل إيه؟

IBM MQ بيستخدم رسايل (messages) وطوابير (queues) للتواصل من برنامج لبرنامج. التطبيقات ممكن تبقى على نفس الجهاز أو موزعة على شبكة فيها أنظمة IBM وغير IBM.

Common API
واجهة موحدة (MQI) على كل أنظمة التشغيل المدعومة
Assured delivery
الرسالة مبتضيعش حتى لو النظام وقع، ومفيش تسليم مكرر
Time-independent processing
التطبيقات مش لازم تبقى شغالة في نفس الوقت
Application parallelism
التطبيق يتقسم لوحدات تتكلم بالرسايل، فتشتغل على أجهزة مختلفة وأوقات مختلفة أو بالتوازي
Faster development
المطور مش محتاج يتعامل مع تعقيدات الشبكة

تشبيه

MQ زي صندوق البريد. أنت بتحط الجواب في الصندوق وتمشي، والمستلم ياخده وقت ما يكون فاضي. مش لازم الاتنين يكونوا موجودين في نفس اللحظة.

الـ Messages

  • بتحتوي بيانات التطبيق (payload)
  • بتتحط على queues، فالبرامج تشتغل مستقلة عن بعض: بسرعات وأوقات وأماكن مختلفة وبدون اتصال منطقي بينهم
  • بتحتوي MQMD (Message Descriptor) فيه معلومات تحكم
  • ممكن تحتوي message properties اختيارية بينشئها التطبيق

الرسالة جزئين: message descriptor وapplication data. المرسل بيحدد الاتنين، والمستلم بيرجعله الاتنين. التطبيق اللي بيحط الرسالة بيظبط بعض حقول الـ descriptor، والـ queue manager بيظبط الباقي. الرسالة ممكن تكون طلب خدمة، أو رد، أو تقرير عن رسالة تانية، أو معلومة مفيهاش رد.

الـ Queues

Local queue (QLOCAL)
طابور تملكه الـ queue manager اللي البرنامج متوصل بيها. هو الوحيد اللي بيخزن رسايل فعليًا
Remote queue (QREMOTE)
تعريف لطابور بتملكه queue manager تانية

الـ queue مكان تخزين الرسايل لحد ما تتعالج. وقت الانتظار ممكن يكون قصير أو طويل (لو المستلم لسه ما اشتغلش). في الحالتين، القدرة على تخزين الرسالة بأمان هي الخاصية المهمة.

الـ Queue manager

  • بيوفر خدمات المراسلة للتطبيقات
  • بيتأكد إن الرسايل رايحة للـ queue الصح أو بتتوجه لـ queue manager تانية
  • بيستضيف الـ queues والـ channels اللي بتوصل بين الـ queue managers
  • Listeners بتقبل طلبات الشبكة من queue managers أو clients تانية وبتشغّل الـ channels
  • الـ queue managers على نفس الجهاز لازم تستخدم TCP/IP listener ports مختلفة. كل queue manager في بيئة distributed ليها port فريد (مثال الكتاب: QMGR1 على 1414، وQMGR3A على 1430، وQMGR3B على 1431)

IBM MQ Explorer

  • أداة رسومية لإعداد وإدارة ومراقبة كل كائنات IBM MQ، المحلي والبعيد، من console واحد
  • بتظبط كل الكائنات بما فيها JMS وpublish/subscribe
  • بتدعم فلترة متقدمة وإدارة اتصالات التطبيقات وتجميع queue managers
  • مبنية على Rich Client Platform (RCP) على Eclipse، وبتشتغل على Windows وLinux (x86) بس، لكن تقدر تدير MQ على أنظمة تانية عن بعد

الواجهة: Navigator على اليسار فيه كل الكائنات اللي بتديرها، وعليها أيقونات حالة. الـ Content views بتعرض معلومات الكائن المختار. ومن أيقونة Scheme تغيّر الأعمدة المعروضة وترتيبها.

القسم 4.2: ربط ACE بـ IBM MQ

الـ MQ client

IBM MQ client مكوّن يسمح لتطبيق على جهاز يبعت MQI calls لـ queue manager على جهاز تاني. الاتصال بيتم عبر MQI channel. توليفة client connection وserver connection وقناة الاتصال بينهم (زي SNA LU6.2 أو TCP) هي الـ MQI channel. كل مجموعة MQI calls وخياراتها متاحة للتطبيق الـ client.

اتصال client من ACE

لو MQ مش شغال على نفس سيرفر الـ integration node، لازم تظبط client connection. تعرّفه على الـ MQ nodes بطريقتين:

  • تختار MQ client connection properties وتحدد تفاصيل الـ queue manager صراحة
  • أو تختار Client channel definition table (CCDT) وتحدد مكان ملف الـ CCDT بالأمر mqsichangeproperties وخاصية mqCCDT
mqsichangeproperties ACENODE -o BrokerRegistry -n mqCCDT -v "C:\Program Files\IBM\MQ\Qmgrs\QM1\@ipcc\AMQCLCHL.TAB"

خيارات الاتصال

  • الـ flows بتوصل لشبكات MQ الموجودة عشان تجيب وتحط رسايل
  • MQInput وMQOutput وMQGet وMQReply تقدر تتوصل بـ queue manager محلي أو بعيد
  • MQInput الواحد يقدر يستقبل من queues متعددة على queue managers متعددة
  • لتنسيق transaction عالمي (globally coordinated)، لازم MQInput وMQOutput يستخدموا نفس الـ queue manager المحلي
  • الـ policies والـ configurable services بتعرّف الروابط لـ queue managers

على الأنظمة الـ distributed، في transactions العالمية، الـ queue manager المحلي المحدد على الـ node هو الـ global transaction manager، ومينفعش تستخدم موارد MQ تانية في الـ flow. على z/OS كل الـ queue managers بتتنسق عالميًا.

مميزات المراسلة بـ MQ

  • الـ clients بتخلي التطبيق يتوصل بـ queue manager محليًا أو عن بعد
  • publish/subscribe بيطوّر المراسلة من point-to-point لنمط أقل ارتباطًا
  • MQ clusters بتخلي أكتر من instance لنفس الخدمة تتستضاف على queue managers متعددة (load-balancing وfailover)
  • SSL لتأمين الاتصال بين queue managers أو الـ client
  • دعم واسع لأنظمة التشغيل والعتاد
  • رخصة ACE فيها استحقاق لتسطيب MQ واستخدامه

الـ MQInput node

  • بيستقبل رسايل من queue محدد عبر اتصال local أو client
  • بيعمل polling على الـ queue للرسايل اللي تطابق معايير البحث
  • فيه قيم افتراضية لاختيار الـ parser ولـ topics الـ publish/subscribe
  • بيحدد transaction mode للـ flow كله
  • بيبدأ thread منفصل
  • أكتر من MQInput في flow = مصادر دخول بديلة
  • رسالة واحدة لكل thread
  • تلات output terminals: Failure وOut وCatch

وقت التشغيل الـ node بيعمل «MQGet with wait» على الـ queue. أول ما رسالة توصل، بياخدها ويحوّلها (parse) من bit stream لـ logical tree ويبعتها للـ node اللي بعده. كمان بيضبط الخصائص الـ transactional للـ flow وبيشارك في معالجة الأخطاء. الرسالة الناجحة بتطلع من Out.

z/OS
على z/OS الاتصالات المحلية بـ queue managers هي المدعومة بس.

الـ MQOutput node

  • بيحط رسالة على queue محلي أو بعيد، تحت transaction الـ flow أو commit صريح
  • مش لازم يبقى نهاية الـ flow: Out terminal بيوجّه الرسالة لو اتحطت بنجاح (مفيد لفرض تسلسل في كتابة الرسايل)
Queue name (الافتراضي)
يرسل للـ queue المكتوب في خاصية Queue name. لازم تحدد queue manager وقيمة Queue name
Reply-to queue
يرسل للـ queue اللي في حقل ReplyToQ في MQMD (زي MQReply)
Destination List
توجيه ديناميكي: أسماء الـ queues بتتحدد بـ ESQL في nodes تانية وتتحط في local environment

الـ MQReply node

  • بيبعت رد لصاحب رسالة الدخول، للـ queue اللي حقل MQMD ReplyToQ بيحدده
  • على الأنظمة الـ distributed يقدر يكتب على queue في queue manager محلي أو بعيد (بتحدد الـ queue manager من MQ Connection properties على MQOutput أو من MQEndpoint policy في تبويب Policy)
  • خاصية Transaction Mode تحدد هل الرسالة تتكتب تحت sync point
طريقتين لحماية الرسالة من الضياع في MQ
Message persistence: لو الرسالة persistent، MQ بينسخها على القرص فمتضيعش لو حصل عطل. Sync point control: التطبيق يطلب معالجة الرسالة في synchronized unit-of-work (UOW).

الـ MQGet node

  • بيجيب رسالة MQ في نص الـ flow (مش بس في الأول زي MQInput)
  • بيمنع flows زيادة، وبيوفر parsing وsync points وأنماط فشل زيادة
  • IBM MQ مش database: متحسّن لكتابة مرة وقراءة بتمسح (destructive read)، وأنسب لـ request/reply وSOAP over MQ
  • كل خيارات MQGET متاحة عبر إعدادات الـ node (ثابتة أو معرّفة بالرسالة الداخلة)

في نمط request/reply المتزامن: الطلب بيتبعت بـ MQOutput والرد بيستلمه نفس الـ flow بـ MQGet. لكن لو المعالجة طويلة، النمط المتزامن مش مناسب لأن الرسايل التانية مبتبدأش لحد ما الحالي يخلص. ساعتها صمّم flows منفصلة للطلب والرد (asynchronous)، واحفظ سياق الربط (correlation context) في وسيط تخزين في flow الطلب واسترجعه في flow الرد، مثلًا في queue تستخدم MQGet في flow الرد لاسترجاعه. كده طلب تحديث طويل مش هيعطّل استعلامات سريعة.

كيف الـ MQGet بيبني شجرة الإخراج؟

الـ output tree = الـ input tree مدموجة مع الـ result tree من استدعاء MQGET. مثال الكتاب: خصائص الـ node: outputDataLocation = OutputRoot.XML.A و resultDataLocation = ResultRoot.XML.C. النتيجة: العنصر C من ResultRoot بيحل مكان العنصر A وإخوته من InputRoot.

InputRoot.XML        : Child1 { A, B }, Child2
ResultRoot.XML       : Child1 { C, D }, Child2
outputDataLocation   = OutputRoot.XML.A
resultDataLocation   = ResultRoot.XML.C
OutputRoot.XML       : Child1 { A(C) }, Child2

طبولوجيا MQ المرنة

  • node واحد يتوصل بـ queue manager واحد
  • أكتر من node يتوصلوا بـ queue manager واحد
  • الـ queue manager ممكن يبقى محلي أو بعيد عن الـ node
  • لو MQ متسطّب، ACE بيكتشفه ويظبطه حسب الحاجة
  • MQ policies بتحدد الموارد وقت التشغيل

ميزات ACE اللي محتاجة MQ

بعض الميزات محتاجة MQ server على نفس جهاز الـ node وتحديد queue manager على الـ node، لأنها بتستخدم system queues لتخزين معلومات الحالة:

Flow control
TimeoutControl وTimeoutNotification
Aggregation
AggregateControl وAggregateReply وAggregateRequest
Advanced data processing
Collector وResequence وSequence
Managed file support
CDInput وCDOutput وFTEInput وFTEOutput
Accounting and statistics
لو بتستخدمهم من الـ web UI وبتستخدم IBM MQ بدل MQTT
Publish and subscribe
Publication node

القسم 4.3: إنشاء queue manager محلي بـ MQ Explorer

ممكن تعمل queue manager من أمر أو من MQ Explorer. الـ Explorer بيعرض كل الـ queue managers المحلية بغض النظر عن طريقة إنشائها. الخطوات الست:

  1. كليك يمين على Queue Managers في Navigator > New > Queue Manager
  2. اكتب اسم الـ queue manager والقيم الأساسية (default transmission queue وdead-letter queue وtrigger interval)
  3. حدد نوع وقيم الـ log. بيانات الـ log في ملفات، وحجم الملف بوحدات صفحات 4 KB
  4. اختار خيارات الإعداد والبدء: Start queue manager after it has been created (يبدأ فورًا)، وAutomatic (يبدأ تلقائيًا بعد إعادة تشغيل النظام)، وCreate server-connection channel (يسمح لمسؤول على جهاز تاني بإدارتها = remote administration)
  5. عرّف listener لـ TCP/IP وحدد الـ port. كل listener على نفس الجهاز لازم port فريد، ولو مستخدم هيظهر خطأ أعلى الصفحة
  6. ظبط الـ automatic refresh (الـ remote managers بتتحدث أقل تكرارًا لتقليل ترافيك الشبكة)

صفحة الـ queue manager فيها تلات QuickViews: Connection (حالة الاتصال والنوع والاسم)، Status (حالة command server وchannel initiator واسم التسطيب)، Properties (النظام وcommand level وdefault transmission queue).

queue manager افتراضي للـ integration node

بعض إمكانيات ACE بتحتاج system queues على الـ queue manager المربوط بالـ node لتخزين معلومات الرسايل اللي في الطريق (in-flight).

  • المتطلبات: تسطيب IBM MQ server، والمستخدم عضو في مجموعتي mqm وmqbrkrs، وعلى Linux/UNIX شغّل mqsiprofile
  • 1) أنشئ وشغّل الـ queue manager في MQ
  • 2) على Linux/UNIX شغّل setmqenv لتجهيز بيئة MQ
  • 3) حدد الـ queue manager للـ integration node

تحديد الـ default queue manager بيحدد الـ queue manager المستخدم لـ: الـ MQ nodes لو مفيش queue manager على الـ node نفسه، ولـ nodes اللي بتحتاج queue manager على الـ integration node، وإدارة الـ transactions العالمية، ورسايل publish/subscribe من الـ node.

mqsicreatebroker IntNodeName -q QmgrName      (ينشئ node بـ default queue manager، لكن لا يعرّف ولا يشغّل الـ queue manager)
mqsichangebroker IntNodeName -q QmgrName      (يضيف أو يغيّر الـ default queue manager)
تنبيه
لازم توقف الـ integration node قبل mqsichangebroker وتشغله بعده عشان التغيير يسري.

القسم 4.4: إنشاء local queue بـ MQ Explorer

  1. كليك يمين على Queues تحت الـ queue manager > New > Local Queue
  2. اكتب اسم الـ queue (الافتراضي بيستخدم SYSTEM queue كـ model، وممكن تختار غيره، وفيه خيار لتشغيل wizard لعمل JMS queue مطابق)
  3. عدّل خصائص الـ queue لو لازم واضغط Finish

خصائص الـ queue مقسّمة: General وExtended وCluster وTriggering وEvents وStorage وStatistics.

الـ system queues بتاعة ACE

ميزات ACE اللي بتحتاج queue manager وsystem queues افتراضية عليه:

  • Flow control: TimeoutControl وTimeoutNotification
  • Record and replay
  • Aggregation: AggregateControl وAggregateRequest وAggregateReply
  • Advanced data processing: Collector وSequence وResequence
  • HTTP proxy servlet مع الـ integration node
  • استخدام integration node listener بدل الـ embedded listeners
  • Accounting and statistics من الـ web UI مع IBM MQ
  1. تأكد من وجود MQ server وqueue manager للـ node
  2. تأكد إنك عضو في mqm وmqbrkrs
  3. من command environment (Linux/UNIX) أو ACE Console (Windows) روح لـ: ace_install_dir/server/sample/wmq
  4. شغّل: iib_createqueues.cmd QmgrName على Windows، أو ./iib_createqueues.sh QmgrName على Linux/UNIX
الأمان
الأمر iib_createqueues بيعطّل channel authentication للـ queue manager افتراضيًا. لو عايز تفعّله عدّل سكربت MQSC النموذجي iib_queues_create.mqsc.

القسم 4.5: MQEndpoint policy

  • بتتحكم في قيم اتصال MQ nodes وقت التشغيل
  • بتلغي الخصائص المكافئة اللي في MQ Connection properties في تعريف الـ flow
  • بتتفحص وقت التشغيل (validated at run time)
  • تقدر توصل بـ queue manager محلي أو بعيد مؤمّن بتحديد username وpassword في الـ policy
  • تختار هل تستخدم SSL لما يكون الاتصال client لـ queue manager بعيد

لتحديد policy افتراضية لكل الـ flows على integration server، ظبط خاصية mqConnector في server.conf.yaml باسم الـ MQEndpoint policy. لو الـ policy في policy project غير الافتراضي، اكتب الاسم كامل: {policyProject}:PolicyName.

ربط الـ policy بالـ node

تقدر تربط MQEndpoint policy بـ MQInput وMQOutput وMQReply وMQGet. بتحط اسمها في خاصية Policy على الـ node بالصيغة {policyProjectName}:policyName. لازم تنشر الـ policy قبل ما الـ flow يبدأ.

ملاحظة
ACE بتوحّد مفهومي configurable services وpolicies، فمفيش أوامر mqsicreatepolicy وغيرها (زي ما شفنا في Unit 2).

القسم 4.6: اختبار الـ flows

بـ MQ Explorer

تقدر تختبر flows فيها MQInput أو MQGet بوضع رسايل اختبار على الـ input queues، وتتأكد إن رسايل وصلت للـ output queues. كليك يمين على queue:

  • Clear Messages: يفضّي الـ queue
  • Put Test Message: يحط رسالة
  • Browse Messages: يعرض الـ header والمحتوى

بـ RfhUtil

  • بيحط ويجيب ويتصفح رسايل
  • بيعرض الرسالة بصيغ: character وhexadecimal وXML وCOBOL
  • بيعرض ويضبط كل الـ headers
  • بيعرض ويفضّي ويحمّل ويحفظ queue
  • بيصدر أوامر publish/subscribe

RfhUtil كانت SupportPac لـ WebSphere Message Broker (حاليًا withdrawn) وبقت على GitHub: github.com/ibm-messaging/mq-rfhutil. بيقرا ويكتب بيانات من ملفات أو queues. بيعرض بيانات المستخدم بصيغ مختلفة لكن مينفعش يغيّرها، وبيضيف RFH headers.

فين الرسالة بتروح لو حصل خطأ؟ (أهم جزء في الـ Unit)

لو الـ flow خلص بنجاح الرسالة غالبًا بتوصل للـ output زي ما صممت. لو فيه مشكلة، المصير بيتحدد بعوامل:

  • هل Failure وCatch terminals موصولين
  • خاصية Transaction mode على الـ MQInput
  • إعدادات MQ: BOQNAME وBOTHRESH على الـ input queue، وـ DLQ على الـ queue manager

Transaction mode على الـ MQInput

Automatic
الرسالة بتتستقبل تحت sync point لو التطبيق علّمها persistent، وإلا لا. لو حصل فشل والرسالة non-persistent بتتجاهل
Yes (الافتراضي)
كل الرسايل تحت sync point وبتتعامل كـ persistent. لو فشل ممكن يحصل rollback بغض النظر عن الـ persistence
No
مفيش sync point. لو فشل الرسالة بتتجاهل بغض النظر عن الـ persistence

ترتيب فحص الخطأ (زي الفلاتر)

  1. لو الـ Failure terminal للـ node اللي حصل فيه الخطأ موصول: الرسالة تتبعت منه
  2. لو مش موصول: افحص الـ Catch terminal على الـ MQInput. لو موصول: الرسالة تتبعت منه
  3. لو مش موصول: افحص Transaction mode. لو الرسالة مش تحت sync point (مش transactional): تتجاهل (discard). لو تحت sync point: rollback لـ input queue والـ flow يبدأ تاني (retry)
  4. المحاولة التانية ممكن تفشل برضه وتعمل backout تاني. الـ BOTHRESH على الـ input queue بيحدد عدد مرات المحاولة

لما BOTHRESH يتخطى

لو الفشل حصل بعد Failure terminal الـ input node، المحاولات بتستمر لحد ما MQMD.BackoutCount يوصل ضعف BOTHRESH (2 × BOTHRESH). ساعتها الـ node بيحاول يحط الرسالة على الـ backout queue (BOQ)، ولو مفيش أو فشل فعلى الـ dead-letter queue (DLQ). الترتيب: 1) Failure path للـ input node لو موصول، 2) Backout queue، 3) Dead-letter queue.

الخطر
لو مفيش BOQ ولا DLQ، أو لو أي منهم فشل، الرسالة بتفضل في loop على الـ input queue وتمنع أي رسايل جديدة من المعالجة. لازم تتصلح يدويًا.
تذكير بالمفاهيم
DLQ بتحفظ الرسايل اللي ما تتسلمش لأي مستقبل أو معالجتها فشلت. BOQ هو الـ backout queue اللي بيستقبل الرسايل بعد تخطي عتبة الرجوع.

IBM MQ uses messages and queues to provide program-to-program communication. The communicating applications can be on the same system, or distributed across a network of IBM and non-IBM systems. The major benefits of IBM MQ are: • There is a common application programming interface, the Message Queue Interface (MQI) that is consistent across all the supported operating systems. • IBM MQ can transfer data with assured delivery; messages do not get lost, even when a system failure occurs. There is no duplicate delivery. • Communicating applications do not have to be active at the same time. • An application is divided into discrete functional modules that communicate with each other with messages. In this way, the modules can run on different systems, be scheduled at different times, or they can act in parallel. • Application development is faster because the developer is shielded from the complexities of the network.

A message can also carry information for which no reply is expected. • A message consists of two parts: ▪ Message descriptor ▪ Application data • The message descriptor contains information about the message. The sending application supplies both the message descriptor and the application data when it puts a message on a queue. Both the message descriptor and the application data are returned to the application that gets the message from the queue. The application that puts the messages on the queue sets some of the fields in the message descriptor; the queue manager sets others on behalf of the application.

In these cases, the message flow would be better designed asynchronously, with separate request and reply flows. Any required correlation context must be saved to a storage medium in the request flow and restored during the reply flow. A possible solution is to use a queue to store the required correlation context and use an MQGet node in the reply flow to retrieve it. This solution would prevent, for example, a longer running update request from blocking fast-running inquiry requests.

Figure 4-46 Message flow result dependencies

مصير الرسالة مع الأخطاء بيعتمد على: الـ terminals الموصلة (Failure وCatch)، وخاصية Transaction mode في input node: Automatic (تتستقبل تحت sync point لو الرسالة persistent بس)، Yes (دايماً تحت sync point)، No (مش تحت sync point). لو تحت sync point والخطأ حصل، الرسالة بترجع للـ queue وتتعاد المحاولة.
نص الكتاب الأصلي
If a message flow completes successfully, messages almost always end up on the output as designed. However, depending on the terminals that are connected and if there is a problem, the message can go to another destination. Other factors can affect the message path if a runtime error occurs. For example, the MQInput node Transaction mode property that controls whether the incoming message is received under sync point. • If Transaction mode is set to Automatic, the incoming message is received under sync point if it is marked as a persistent message by the application; otherwise it is not received under sync point. If a failure occurs, the message is discarded if it is marked as non-persistent. • If Transaction mode is set to Yes, the incoming message is received under sync point. If there is a failure, a rollback can occur regardless of message persistence. • If Transaction mode is set to Yes No, the incoming message is not received under sync point. If a failure occurs, the message is discarded regardless of message persistence. IBM MQ also has two other queues where messages might appear: the queue manager dead-letter (DLQ) queue and a backout queue (BOQ). The purpose of the dead-letter queue is to hold messages that cannot be delivered to any receiver, or messages that could not be processed.

Figure 4-47 Message flow error behavior with IBM MQ

مخطط الخطأ (فلاتر بالترتيب): لو حصل exception في node، (1) لو Failure terminal للـ node موصل، الرسالة تتبعت منه. (2) وإلا ينتقل للـ Catch terminal لـ MQInput: لو موصل تتبعت له. (3) وإلا بيفحص الـ transaction mode: لو الرسالة تحت sync point بترجع للـ queue وتتعاد، ولو لا، بتروح للـ Failure terminal لـ input node أو تضيع (حسب التوصيل).
نص الكتاب الأصلي
This slide shows the events that occur when an error occurs in a processing node and the flow starts with an MQInput node. • The levels of error handling are like filters. If the Failure terminal of the node where the exception occurred is connected, the message is propagated out the Failure terminal. If the Failure terminal is not connected, the next step is to check the Catch terminal on the MQInput node. • If a node is wired to the Catch terminal of the MQInput node, the message is propagated to that node. If the Catch terminal of the MQInput node is not connected, then the next step is to check the Transaction mode setting on the MQInput node. • If the message is not under sync point (not transactional), it is discarded. If the message is under sync point the message is rolled back to the input queue, and the message flow restarts. The second attempt might not work and ends with another backout. • The backout threshold (BOTHRESH) property on the input queue limits the number of times the message flow tries to process the message. The next page shows the behavior that occurs when the input queue backout threshold is exceeded.

Figure 4-48 Message flow error behavior: BOTHRESH exceeded

لما BOTHRESH (backout threshold) يتعدى: يتحقق بالترتيب: (1) مسار Failure لـ input node لو موصول، (2) Backout queue (BOQ) لو معرّفة للـ input queue، (3) Dead-letter queue (DLQ) للـ queue manager. لو الفشل بعد Failure terminal للـ input node تستمر المحاولات لحد ما MQMD.BackoutCount يبقى ضعف الـ threshold وبعدها تروح للـ BOQ أو DLQ.
نص الكتاب الأصلي
• If the backout threshold is reached, the message destination depends on whether the Failure terminal input node is wired. The message destination also depends on the existence of a backout queue (BOQ) for the input queue, and existence of a queue manager dead-letter queue (DLQ). The queues are checked in the order that is shown in the flow chart. • If a failure occurs beyond the FAILURE terminal of the input node, further retry attempts occur until the backout count in the MQ message descriptor (MQMD) is twice the backout threshold that is set for the input queue. When this limit is reached, the node attempts to put the message to either the backout queue or dead-letter queue. If the backout queue or the dead-letter queue do not exist, or if any of the queues fail, the message ends looping on the input queue and prevents any new messages from being processed. In these cases, the error condition must be corrected manually.
