القسم 10.1: ضبط الاتصال بقواعد البيانات

استخدام databases في الـ flows

  • الاتصال بقواعد بيانات التطبيقات على DB2 وMS SQL Server وOracle وSybase وInformix وSolidDB
  • ACE ODBC بيدير الـ transactions تلقائيًا مع: ESQL وmaps وJavaCompute (MbSQLStatement). وكمان integration node managed JDBC type 4 مع JavaCompute وDatabaseRoute وDatabaseRetrieve
  • لازم تدير الـ transactions يدويًا في الكود مع: standard JDBC API (type 2 و4) في JavaCompute، وSQLJ في JavaCompute
  • استخدم mapping أو compute nodes لعمل SELECT وINSERT وUPDATE وDELETE
  • database definitions ممكن تتستورد أو تتكتشف: بـ New Database Definition File wizard في الـ Toolkit، وبتتستخدم للـ maps وESQL content assist

الـ flow ممكن يعدل محتوى الـ database بإضافة معلومات جديدة أو حذف أو استبدال القديمة. الـ integration node بيدير connection pooling تلقائيًا وبيتعامل مع الـ flow كـ transaction واحدة. لما الـ flow يبقى idle حوالي دقيقة أو يخلص، الـ node بيقفل الـ connection. للوصول لـ user database في map محتاج database definitions في الـ workspace. الـ Toolkit ممكن يتصل بالـ database ويكتشف الـ definition ويخزنه في الـ workspace. لو مفيش صلاحيات، خلي مدير الـ database يصدّر ملفات الـ definitions. ومع ESQL Editor، الـ Content Assist بيساعد في بناء مراجع الـ schema والأعمدة.

التحقق من اتصالات ODBC

  • الأمر mqsicvp لاختبار integration node أو اتصالات ODBC
  • على Linux وUNIX بس: تتأكد من ضبط بيئة ODBC صح: mqsicvp IntNodeName
  • لعرض معلومات عن user data source: mqsicvp -n Datasource -u DatasourceUserId -p DatasourcePassword
  • لمقارنة data sourcesين: mqsicvp -n Datasource -u primaryDatasourceUserId -p primaryDatasourcePassword -c secondaryDatasource -i secondaryDatasourceUserId -a secondaryDatasourcePassword

معاملات user ID وpassword مطلوبة لو ما ربطتش الـ data source name بالـ integration node قبل كده. لما تستخدمه كأداة اختبار ODBC، الأمر بيطلع رسالة معلومات عند نجاح الاتصال فيها اسم الـ data source ونوع الـ database والإصدار. لو في secondary data source بيطلع رسالة تانية ويقول إنه هيقارن. لما يشتغل على data source واحد، بيعمل عدة فحوصات على واجهة ODBC: أنواع البيانات والدوال المدعومة بأسمائها وأحجامها، وأي حاجة مش مدعومة بتتلخص في رسالة معلومات أخيرة.

تفعيل اتصالات JDBC

  • استخدم JDBC من برامج Java المرتبطة بـ JavaCompute أو user-defined node مكتوب بـ Java
  • لازم تظبط JDBC لو الـ flows فيها graphical data maps بـ database transforms من Mapping node، أو DatabaseRetrieve أو DatabaseRoute nodes
  • على Windows: ظبط database موجودة كـ System ODBC data source
  • على Linux وUNIX: عدّل ملف odbc.ini
  • Integration node managed JDBC Type 4: أنشئ JDBCProvider configurable service لكل database (موجودة) متصلة بتطبيقات Java

ACE بيوفر أنواع اتصال مختلفة حسب الـ nodes. استخدم ODBC وintegration node managed JDBC type 4 كل ما أمكن لتقليل البرمجة اليدوية. قد تحتاج تغيير خصائص خاصة بالـ database والبيئة، مثلًا jarsURL بيحدد مكان ملفات JAR اللي بيوفرها مزود الـ database.

خطوات تفعيل JDBC

  1. أنشئ وانشر jdbc policy project فيه معلومات ضبط الـ database
  2. شغّل mqsisetdbparms لربط الـ security identity بمورد أو أكتر
  3. اعمل restart للـ integration server (mqsistop ثم mqsistart)
mqsisetdbparms ACENODE1 -n jdbc::mydbuser -u Administrator -p passw0rd
mqsistop ACENODE1
mqsistart ACENODE1
أمان
القيم دي أمثلة الكتاب. ما تكتبش password حقيقي في سكربتات أو تاريخ shell مشترك.

تقدر تشغل mqsisetdbparms أثناء تشغيل الـ server أو الـ node، لكن لازم توقف وتشغل كل integration server بيستخدم ResourceName معين قبل ما يقرا المعلومات الجديدة.

Database service discovery

قواعد البيانات هي systems of record لكيانات الأعمال المهمة (customers وaccounts وpartners وproducts). أدوات ACE بتكتشف وبتمثل البيانات دي، وintegration services بتمدد الوصول لتطبيقات المستخدمين. تقدر تعرّف database service لإتاحة عمليات الـ database داخل الـ flow ولتطبيقات خارجية بتنادي الـ flow. الـ database service فيه:

  • تعريفات واجهة موجهة للعمليات عن التفاعل مع الـ database (مثلًا التغييرات على جدول معين) في ملف WSDL
  • database connection binding بيلتقط دلالات العمليات، في WSDL
  • ملفات XSD بتوصف مدخلات ومخرجات العمليات
  • ملف .service فيه metadata لعملية الـ discovery. الـ Toolkit بيستخدمه لحفظ حالة Database Service editor ولـ discovery متكرر للعناصر المكتشفة سابقًا

استخدامات: الـ WSDL فيه معلومات منطقية وفيزيائية، وبتسحبه لإنشاء SQL access methods تلقائيًا، وتنشئ integration service لوصول مخصص.

القسم 10.2: Policies

الـ policies اتشرحت في unit سابق، وهنا تفاصيل أكتر عن إنشائها ونشرها.

نظرة عامة

  • بتتحكم في خصائص nodes معينة (زي بيانات الاتصال) وجوانب من سلوك الـ flow (زي معدل التدفق flow rate)
  • تعريف مشترك ومُدار وقابل لإعادة الاستخدام
  • بتحتوي خصائص تشغيلية معرّفة
المطورين
يستخدموها للتحكم في سلوك وقت التشغيل وإعادة استخدام معلومات الضبط في أماكن كتير، فيقل التكرار. وتفاصيل الاتصال تتحدث من غير تعديل الـ flows
الإداريين
يحددوا بيانات ضبط كل بيئة ويلغوا خصائص حددها مطور الـ flow
المشغّلين
يراقبوا ويعدلوا بيانات الضبط ديناميكيًا

الـ policies هي XML documents معرّفة بـ XML Schema (Policy.xsd) في مجلد التسطيب الافتراضي. على Windows: C:\Program Files\IBM\ACE\version\common\schemas\Policy. الـ policies بتحل محل configurable services في ACE. تقدر ترحّل configurable services الموجودة لـ policies بالأمر mqsiextractcomponents.

فرق سلوك
في الإصدارات القديمة، خاصية فاضية في configurable service كانت تلغي خاصية الـ node بقيمة فاضية. مع الـ policy، الخاصية الفاضية ما بتلغيش خاصية الـ node، وبتتستخدم قيمة الـ node.

الأمر mqsicreateconfigurableservice بقى deprecated في ACE وما بيعملش configurable services، لكن لو استخدمته في سكربتات بينشئ policies مكافئة (لو مدعومة). الـ policies دي بتتنشأ في default policy project (DefaultPolicies) وبترتبط بـ integration node وبتتورث لكل الـ integration servers عليه. تقدر تلغي policy موروثة بنشر نسخة محدثة على الـ integration server، أو بوضع نسخة محدثة في overrides sub-directory في work directory للـ server.

Policy projects

لما تشغل mqsicreateworkdir بيتنشأ server.conf.yaml فيه إعدادات افتراضية للـ integration server، وفيه تعريف default policy project اللي بيخزن الـ policies غير المؤهلة (unqualified). لما تنشئ policy في الـ Toolkit لازم تنشئها داخل policy project. تقدر تضيف policies كتير في policy project، وتنظمها مثلًا: كل policies integration server معين، أو كل policies من نوع معين (JDBC Providers مثلًا)، أو كل policies لـ application معين.

  • لما تشير لـ policy من flow أو node: استخدم اسم الـ policy لو في default policy project
  • لو في policy project تاني: ضيف اسم الـ project قبل الاسم بالصيغة {policyProject}:PolicyName
  • الـ default policy project اسمه DefaultPolicies ومعرّف في server.conf.yaml

أنواع policies ممكن تعدلها وتعيد نشرها

تقدر تغير وتعيد نشر الأنواع دي بإعادة نشر الـ policy project: Activity Log، Aggregation، CDServer، CICSConnection، Collector، CORBA، EmailServer، FtpServer، IMSConnect، MQEndpoint، MQTTPublish، MQTTSubscribe، Resequence، SAPConnection، SMTP، Timer، WorkloadManagement.

تنبيه
لما تعيد نشر policy project، كل الـ flows اللي بتستخدم الـ policy بتتوقف وتتشغل تاني. الأنواع التانية اللي ما ينفعش إعادة نشرها لازم تمسح كل الموارد المنشورة من الـ integration server وتنشر نسخة جديدة. لو بتستخدم mqsicreateconfigurableservice في سكربتات، استخدم النسخة المختصرة من اسم الـ policy.

نشر الـ policies

  • بتنشر policies في policy projects داخل BAR file مستقل، أو BAR file مع الـ flow المرتبط
  • لو اسم policy محدد على flow أو node، لازم تنشر الـ policy قبل ما الـ flow يبدأ
  • تقدر تلغي policy منشورة بوضع policy project محدث في overrides sub-directory في work directory الـ server وعمل restart
  • لو الـ flow فيه local environment override، أي قيمة بيحددها بتلغي القيمة من policy أو BAR file override أو الـ node

الـ policies المنشورة بتظهر في run sub-directory تحت work directory للـ server داخل sub-directory باسم الـ policy project. تقدر تشوف خصائصها في Integration Explorer في الـ Toolkit أو تبويب Policies في الـ web UI. وتشوف الخصائص المستخدمة وقت التشغيل من REST API أو web UI. لحذف الموارد: استخدم الـ Toolkit أو معامل -m في mqsideploy.

إعداد JDBC provider

  • استخدم JDBC Providers policy لضبط JDBC provider service
  • الـ policy بتدعم اتصالات بـ database واحدة بس، لازم policy لكل database
  • الـ policy محتاجة معلومات حسب ضبط الـ database

هتنشئ وتنشر jdbc policy داخل policy project في التمرين. بعدها شغّل mqsisetdbparms لربط الـ security identity ثم restart للـ integration server.

القسم 10.3: ESQL ودعم الـ transactions

ESQL SELECT مقابل SQL SELECT

ESQL SELECT شبه SQL SELECT بقيود. الفروق:

  • ESQL ينتج tree-structured result data
  • ESQL بيقبل arrays في SELECT clauses
  • ESQL فيه دالة THE ومعاملات ITEM وINSERT
  • ESQL مفيهوش SELECT ALL ولا ORDER BY ولا SELECT DISTINCT ولا GROUP BY ولا HAVING
  • مفيهوش AVG column function في الإصدار ده (حسب الكتاب)

تقدر تستخدم PASSTHRU لإرسال SELECTs معقدة لـ database لو ACE ما بيدعمهاش. PASSTHRU بيتجاوز parser ACE: للـ SELECTs الخاصة وصياغة database خاصة واستدعاء stored procedures وتنفيذ statement جاهز.

THE (SELECT ...)

  • SELECT بيرجع list
  • THE (SELECT ...) بيرجع أول عنصر في الـ list
SET OutputRoot.XML.Msg.Name[] = (SELECT E.LASTNAME from Database.EMPLOYEE as E);
-- list: Name/LASTNAME لكل صف (Haas, Thompson ...)

SET OutputRoot.XML.Msg.Name = THE(SELECT E.LASTNAME from Database.EMPLOYEE as E);
-- non-list: أول عنصر بس (Haas)

THE ضرورية لأن ESQL بيقبل list على الجانبين أو non-list على الجانبين في المساواة.

SELECT (ITEM ...)

  • بيجيب القيمة بس
  • من غير ITEM: اسم عمود الجدول أو XML tag بيتستخدم كـ message tag، وممكن تغيّره بكلمة AS
  • مع ITEM: النتيجة بتبقى بدون اسم، list من قيم النوع اللي بيرجعه التعبير بدل صف
SET OutputRoot.XML.Msg.Name[] = (SELECT ITEM E.LASTNAME from Database.EMPLOYEE as E);

استخدامات SELECT(ITEM): مع تعبير scalar ودالة THE لعمل query بيرجع قيمة scalar واحدة (سعر صنف من جدول مثلًا). ومع CASE وROW constructors لإنشاء أو معالجة رسايل بعض الصفوف فيها بنية مختلفة. ومع ROW constructor لـ query بيطوي مستويات التكرار في رسالة الإدخال.

مثال PASSTHRU

SET OutputRoot.XMLNSC.Msg.Results[] = PASSTHRU(
  'SELECT WORKDEPT, MAX(SALARY) AS MaxSalary
   FROM schema1.EMPLOYEE
   GROUP BY WORKDEPT
   HAVING MAX(SALARY) > ?'
  TO Database.SAMPLE
  VALUES(InputBody.Msg.Salary));
  • PASSTHRU بيصدر كمان أوامر إدارية لـ database
  • استخدم parameter markers (علامة ؟) للأداء

لو لازم تستخدم SQL SELECT الكامل، استخدم SQL SELECT GROUP BY كـ text string داخل PASSTHRU، والـ database لازم تتعرف كـ data source زي العادة. علامة ؟ بتتعامل كـ substitution variable في prepared SQL statement. الـ statements الديناميكية مكلفة في التحضير، فاسعى لإعادة استخدامها بأقصى قدر: استخدم ؟ مش قيم literal. القيم بتتبدل قبل الاستدعاء مباشرة. PASSTHRU ما فيهوش مكسب أداء مقارنة بنفس SQL من ESQL، فاستخدمه بس لو الـ SQL مش صالح في ESQL (مثلًا لمعاملات خاصة بالـ database).

دعم الـ transactions

  • افتراضيًا الـ flow هو logical unit of work: commit أو rollback للموارد
  • خاصية Transaction على input node، والافتراضي YES
  • بعض processing nodes ممكن تتستبعد صراحة من الـ unit of work: لو TransactionMode للـ node = Commit يبقى transaction منسقة جزئيًا (partially coordinated)
  • لو في أكتر من resource manager في الـ flow (IBM MQ وDBMS)، اختار transaction coordinator للـ flow المنشور في BAR
IBM MQ كـ coordinator
بيسمح بتحديثات atomic مع resource manager خارجي، عبر XA connection بين MQ والـ resource manager

مثال: مع XA التطبيق بيصدر MQCMIT واحد لـ commit تحديثات MQ وDB2 معًا. من غير XA لازم MQCMIT لـ MQ وEXEC SQL SYNCPOINT لتحديثات DB2. بين الـ commits ممكن يحصل فشل يضر بسلامة البيانات. للأداء الأعلى حط logs الـ queue manager والـ resource manager على disks قليلة الـ latency. الـ XA-coordinated transaction بيتفعل في BAR file.

خيارات الـ transaction coordinator

Uncoordinated (الافتراضي)
الـ integration node يدير الـ transaction: database commit ثم MQCMIT. المشكلة لو MQCMIT فشل بعد نجاح database commit
XA-coordinated
الـ queue manager بتاع الـ integration node بيعمل كـ XA transaction manager. two-phase commit بيشمل موارد database وIBM MQ (MQBEGIN). محتاج إعداد خاص
  1. أعدّ XA للـ queue manager بتاع الـ integration node
  2. في BAR file اعرض خصائص الـ flow واختار Coordinated transaction
  3. غيّر الـ transaction لـ Automatic على database nodes
  4. فعّل XA في application database لو لازم

الـ flows uncoordinated هي اللي خاصية Coordinated مش مظبوطة لها في BAR، ومديري موارد منفصلين بيديروا التحديثات. بعض مديري الموارد (زي MQ) بيسمحوا بتحديثات non-transactional أو داخل transaction خاصة بالمورد، وغيرهم (database managers) دايمًا بيستخدموا transaction خاصة بالمورد (نطاقها موارد مدير واحد). لتقليل نافذة الشك (window of doubt) توفر XA على distributed systems بواسطة IBM MQ، وعلى z/OS بواسطة RRS. على z/OS الـ flows دايمًا globally coordinated بغض النظر عن خاصية Coordinated.

القسم 10.4: Database nodes

DatabaseInput node

  • بيكتشف أحداث مسجلة في database ويسترجع البيانات المتأثرة بيها
  • تبويب Database Event Design بيولّد ESQL module فيه الـ query

بتبني flows بترد على أحداث في database. لما تسحب DatabaseInput node على الـ canvas، الـ Toolkit بينشئ ESQL module فيه نص قالب تعدله حسب احتياجك. لما تدبل كليك لتعديل الـ ESQL، الـ editor بيعرض تبويب Database Event Design للـ module. املا الحقول الإلزامية واضغط Generate query.

الـ Database node

  • بيسمح بـ transaction على شكل ESQL expression
  • رسالة الإدخال بتتبعت من غير تغيير لـ output terminal
  • UPDATE وINSERT وDELETE وSELECT
  • الـ SELECT ما يقدرش يعدل الرسالة مباشرة
INSERT INTO Database.DSN2.Schema2.PRICEDATA
  (PRODUCT_NAME, ITEM_PRICE, STATUS)
VALUES (Body.Message.ProductID,
        Body.Message.UnitPrice, 'OPEN');

Compute node ممكن يستخدم لاستخراج وتحديث الـ databases وإنشاء output message. في Database node تعمل كل عمليات الـ database من غير بناء output message جديدة.

خصائص الـ nodes للوصول للـ database

  • حدد الـ Data source كـ default DSN (ODBC)
  • Transaction = Automatic: تحديثات الـ database تتعمل commit أو rollback مع الـ flow كله
  • Transaction = Commit: تحديثات default DSN بتحصل فورًا حتى لو الـ flow فشل بعد كده، وكل التحديثات غير المعمولة commit في الـ flow على default DSN بتتعمل
  • لمعالجة أخطاء SQL في ESQL بدوال SQLNATIVEERROR: امسح علامة Throw exception on database error

كل node بيوصل لـ database لازم يحدد الـ default DSN في خصائصه. لو في database mapping في الـ flow، كل ESQL nodes في الـ flow لازم تحدد data source (أي واحد). الـ integration node ممكن ينسق الـ transaction ويعمل commit بعد انتهاء الـ flow (Automatic)، أو يعمل commit لكل التحديثات على الـ database فورًا حتى من nodes سابقة (Commit). في أي database node تقدر تضبط: Treat warnings as errors (الافتراضي NO) وThrow exception on database error (الافتراضي YES).

DatabaseRoute node

  • بيوجه الرسايل اللي تطابق معايير معينة لأجزاء مختلفة من الـ flow
  • بيطابق على محتوى database (اتصال JDBC)
  • بيستخدم XPath أو ESQL expressions لتحديد معايير المطابقة
  • تعرّف custom output terminals لتحديد expressions متعددة
  • Default terminal لو مفيش تطابق
  • KeyNotFound terminal لو الـ query فشلت أو توجيه الرسالة فشل

مثال الكتاب: رسالة customer record فيها اسم العميل لازم تتوجه حسب STATUS العميل (Bronze أو Silver أو Gold أو Platinum) المخزن في database، والـ node بيقرا الـ database. لو السجل ما اتلاقاش أو الرسالة ما اتحدثتش صح: التحكم لـ keyNotFound. لو خطأ عام: Failure زي العادة.

ضبط DatabaseRoute

  1. الـ workspace لازم فيه database definition وmessage model
  2. ضيف custom output terminals
  3. ضيف query elements
  4. ضيف filter expressions
  5. حدد Distribution mode: يوزع للـ terminal الأول المطابق (FIRST) أو لكل المطابقين (ALL)
  6. وصّل الـ terminals
  7. ظبط JDBC للـ integration node
  8. انشر

عدد الـ output terminals حسب profile الـ flow. تضيف terminals: كليك يمين > Add Output Terminal.

Query elements

Table name
اسم الجدول. في المثال MQSIUSER هو الـ schema وCUSTOMER اسم الجدول
Column
اسم عمود الجدول. في المثال LAST
Operator
بيحدد طريقة جلب الصف. في المثال "=" (مطابقة مباشرة)
Value
تعبير XPath بيحدد البيانات في الرسالة الداخلة المستخدمة لقراءة صف الـ database. ممكن تكتبه يدويًا أو بأيقونة على يمين الحقل

الـ SQL المتولد بيظهر أسفل الخصائص. لضمان إن الـ query بترجع صف واحد صحيح على الأقل لازم يكون في query element بـ value type = null (None)، وإلا الـ SQL غلط.

Filter expressions

  • الترتيب مهم: بتتطبق بالترتيب في الـ filter table
  • لو النتيجة true، نسخة من الرسالة تتوجه لـ output terminal المرتبط

Figure 10-17 ESQL SELECT compared with SQL SELECT

ESQL SELECT مشابه لـ SQL SELECT مع اختلافات: ESQL ينتج بيانات tree-structured، ويقبل arrays في SELECT، وفيه THE وITEM، وناقص بعض الميزات (SELECT DISTINCT وALL وGROUP BY وHAVING، ودالة AVG كـ column function). لو محتاج SQL كامل استخدم PASSTHRU للمرور من غير معالجة ESQL.
نص الكتاب الأصلي
The ESQL SELECT statement is similar to the SQL SELECT statement, with limitations. ESQL SELECT differs from database SQL SELECT in the following ways: • ESQL can produce tree-structured result data • ESQL can accept arrays in SELECT clauses • ESQL has the THE function and the ITEM and INSERT parameters • ESQL has no SELECT ALL function • ESQL has no ORDER BY function • ESQL has no SELECT DISTINCT function • ESQL has no GROUP BY or HAVING parameters • ESQL has no AVG column function in this release You can use the PASSTHRU function to send complex SELECTs, not currently supported by IBM App Connect Enterprise, to databases.

Figure 10-18 THE (SELECT …)

SELECT بيرجع list، وTHE (SELECT ...) بيرجع قيمة واحدة (non-list). ضروري لأن ESQL بيقبل list على الجانبين أو non-list على الجانبين. المثال: SET OutputRoot.XML.Msg.Name[] = (SELECT ...) مقابل بدون [] مع THE.
نص الكتاب الأصلي
• This slide shows the difference between a SELECT statement and a THE(SELECT) statement. • SELECT returns a list. THE (SELECT) returns a non-list. This function is necessary because ESQL accepts only both lists or both non-lists on either side of the equation.

Figure 10-19 SELECT (ITEM …)

SELECT ITEM بيرجع القيمة بس (من غير اسم عمود أو tag). من غير ITEM بيستخدم اسم العمود أو الـ XML tag كاسم عنصر. بيفيد مع THE لجلب قيمة scalar واحدة، ولعمل قائمة قيم.
نص الكتاب الأصلي
• The SELECT clause can consist of the keyword ITEM and a single expression. The effect of SELECT(ITEM) is to make the results nameless. That is, the result is a list of values of the type that the expression returns, rather than a row. • The SELECT(ITEM) option has several uses: ▪ With a scalar expression and the THE function, it can be used to create a SELECT query that returns a single scalar value (for example, the price of a particular item from a table). ▪ With a CASE expression and ROW constructors, it can be used to create a SELECT query that creates or handles messages in which the structure of some rows is different from others. This use can handle messages that have a repeating structure but in which the repeats do not all have the same structure. ▪ With a ROW constructor, it can be used to create a SELECT query that collapses levels of repetition in the input message.

Figure 10-20 PASSTHRU example

PASSTHRU: لتنفيذ SELECT معقد بـ SQL كامل (GROUP BY مثلاً) كنص: PASSTHRU('SELECT WORKDEPT, MAX(SALARY) AS MaxSalary FROM ... GROUP BY WORKDEPT'). لازم القاعدة تتعرف كـ input/output data source. علامة ? متغير بديل (substitution) في prepared statement.
نص الكتاب الأصلي
• If you must use the full SQL SELECT function, use a SQL SELECT GROUP BY as a text string in an ESQL PASSTHRU statement. The database must be defined as an input or output data source in the typical way. • The question mark character (?) is processed as a substitution variable in a prepared SQL statement by the DBMS. The ESQL PASSTHRU statement allows a message flow to run a dynamic SQL statement. Because these statements are expensive to prepare, aim to achieve maximum reuse; use substitution variables (?), not literal values, in the PASSTHRU statement. The values in the variables are substituted just before the call is made. • In the example in the slide, this method allows the statement to be reused for multiple MAX(SALARY) values. • PASSTHRU has no performance gains when compared to using the same SQL statement from ESQL. So, use PASSTHRU only if the SQL statement is not valid in ESQL; for example, to provide database-specific parameters.

Transaction support: افتراضياً الـ flow وحدة عمل منطقية: commit أو rollback للموارد حسب خاصية transaction في الـ input node. IBM MQ ممكن يبقى transaction coordinator عبر XA بحيث MQCMIT واحد يعمل commit لـ MQ وDB2 معاً. من غير XA التطبيق بيعمل commit منفصل لكل واحد.
نص الكتاب الأصلي
• IBM MQ can act as a transaction coordinator. ▪ It allows updates with external resource manager to be atomic. ▪ It is provided through an XA connection between IBM MQ and the resource manager • For example, with XA the application issues one MQCMIT call to commit both IBM MQ and DB2 updates. Without XA, the application must send an MQCMIT call to commit IBM MQ processing and an EXEC SQL SYNCPOINT to commit DB2 updates. • There is a potential for failure between commits, which can compromise data integrity. • For maximum performance, ensure that both the queue manager and the resource manager logs are on low latency disks. • An XA-coordinated transaction is enabled in the BAR file.

Figure 10-22 Transaction coordinator options

خيارات التنسيق: Uncoordinated (الافتراضي: الـ node يتولى؛ commit للقاعدة وبعدين MQCMIT، فخطر عدم تطابق عند فشل بين الاتنين)، أو Coordinated (XA: كل الموارد تتعمل لها commit أو rollback معاً، لازم تفعّل Coordinated في الـ BAR).
نص الكتاب الأصلي
• Uncoordinated flows are flows for which the Coordinated property is not set in the BAR file. Separate resource managers manage updates to resources used by an uncoordinated flow. • Some resource managers, such as IBM MQ, allow updates to be made non-transactionally, or as part of a resource-specific transaction. Other resource managers, such as database managers, always use a resource-specific transaction. A resource-specific transaction is a transaction whose scope is limited to the resources owned by a single resource manager, such as a database or queue manager. • To reduce the window of doubt when multiple separate resource managers are synchronized, transaction coordination by using the XA protocol is provided on distributed systems by IBM MQ and on z/OS systems by RRS. Message flows are always globally coordinated on z/OS, regardless of whether the Coordinated property of the message flow is specified as coordinated or not.

Figure 10-31 DatabaseRetrieve node

DatabaseRetrieve: بيملّي حقول الرسالة من سجل في القاعدة (مشابه Compute مع SELECT). القيم بتتحول لنوع Java ثم لنوع داخلي. terminals: Out (نجاح) وNo match وFailure.
نص الكتاب الأصلي
• The DatabaseRetrieve node looks up values from a database and stores them as elements in the outgoing message assembly trees. The lookup process returns column values, which are acquired and passed back in the result set from SQL queries. The values are converted first into a matching Java type and then into an internal message element value type when it is stored in an outgoing message assembly tree. If a message element exists in the outgoing message tree, the new value overwrites the old value. If the target element does not exist, it is created, and the value is stored. • The node needs query information that is used to form an SQL select query, which can access multiple tables in a database by using multiple test conditions. Sometimes, not all the information that you want to retrieve in a result set is in a single database table. To get the column values that you want, it might be necessary to retrieve them from two or more tables. This node supports the use of SELECT statements that facilitate getting columns from one or more tables in a single result set. • The application of the expression must return a single element, double element, Boolean, or string. If the query returns multiple rows, the first row is chosen and the rest are ignored, unless the Multiple rows option is selected. In this case, all rows are processed, and values in those rows are used to update the outgoing message assembly trees.
