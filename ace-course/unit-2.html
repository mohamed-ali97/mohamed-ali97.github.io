القسم 2.1: معالجة الرسايل (Message processing)

المكونات الأساسية

Figure 2-5 و 2-6
  • Integration node: بيوجّه الرسايل ويحوّلها ويثريها حسب الـ message flows والـ message models
  • Integration server: مجموعة مسماة من الـ message flows
  • Message flow: تسلسل عمليات
  • Message flow nodes: هي اللي بتحدد العمليات
  • Message models: بتحدد هيكل وخصائص البيانات

الـ node بيركّز دوال الـ routing والتحويل اللي الـ flows بتعرّفها. الـ flow بيحدد تسلسل العمليات على الرسالة عن طريق سلسلة nodes، والقرارات بتتبني على شكل الرسالة ومحتواها ونتيجة كل خطوة.

اتجاه الـ flow دايمًا من التطبيق المصدر للتطبيق الوجهة. الافتراض إن الوجهة عايزة ومستنية كل الرسايل اللي بتتبعتلها.

الـ flow ممكن كمان يحوّل الرسالة من صيغة لصيغة: يعدّل أو يدمج أو يضيف أو يشيل حقول. ويقدر يربط بين الرسايل وقواعد البيانات. ولو التحويل معقد، تكتب كود في ESQL أو Java جوه nodes قابلة للبرمجة (configurable).

تفاعل المكونات

Figure 2-6
  • الـ Toolkit بيئة تطوير متكاملة، والأصول (artifacts) ممكن تتخزن وتتدار في repository خارجي
  • الـ integration node هو محرك التشغيل للـ flows اللي اتعملت في الـ Toolkit
  • كل node فيه process واحدة أو أكتر اسمها integration servers، وكل server فيه flow واحد أو أكتر
  • بعض الـ flows محتاجة message models أو schemas. الـ node بيستخدمها لعمل parse وvalidate (اختياري) لمحتوى الرسالة وبناء رسايل جاهزة

الـ Integration node بالتفصيل

Figure 2-7
  • بيوجّه ويحوّل ويثري الرسايل أثناء مرورها حسب الـ flows والـ models
  • ممكن يبقى فيه أكتر من node، كل واحد على نظام مختلف، للحماية من الأعطال وفصل الشغل
  • بيحتاج IBM MQ queue manager لبعض الوظائف، وأحيانًا مجموعة SYSTEM queues خاصة
  • لازم يبقى معاك صلاحيات administrator لإنشائه

الـ integration node هو service على Windows، وdaemon على UNIX، وstarted task على z/OS.

الـ Integration server بالتفصيل

Figure 2-8
  • مجموعة مسماة من الـ flows متعيّنة لـ node
  • بتشتغل في address spaces أو processes منفصلة، فبتوفر عزل وقابلية للتوسع
  • جواها thread pools قابلة للضبط للـ flows المنشورة
  • لازم كل server جوه الـ node يبقى اسمه فريد
  • من V11: الـ servers ممكن تشتغل مستقلة عن الـ nodes، on-premise أو على IBM Cloud
قاعدة الـ 30 حرف
بعض التطبيقات بتقطع اسم الـ integration server عند 30 حرف. لو أول 30 حرف من اسمين متطابقين، هيتعاملوا إنهم نفس السيرفر. فخلّي الاسم 30 حرف أو أقل.

بيئة التشغيل: threads وinstances

Figure 2-9
  • الـ flows بتشتغل كـ threads (على z/OS اسمها TCBs) جوه الـ integration server
  • لما تنشر flow، الـ node بيشغّل instance واحد تلقائيًا
  • تقدر تحدد عدد threads إضافية (additional instances) يستخدمها الـ server لخدمة رسايل الـ flow. بتتعمل بس لو فيه رسايل داخلة كفاية. الحد الأقصى 256 thread لكل flow
  • نفس الـ flow ممكن يتحط على أكتر من server. ده بيزوّد الـ throughput، لكن مفيش طريقة تتحكم في ترتيب معالجة الرسايل
  • كل instance بيستنى رسالة من الـ input node ويشتغل بالتوازي مع الباقي
نقطة مهمة بتتسأل
الـ flow = thread جوه server، مش process منفصلة. الـ server هو اللي process. (ده بيجاوب سؤال 1 في الاختبار آخر الـ Unit).

القسم 2.2: الـ Message flows

شكل الـ message flow

Figure 2-12
  • تسلسل عمليات مكوّن من nodes موصولة ببعض
  • لازم يبدأ بـ input node واحد على الأقل (مصدر الرسايل)
  • غالبًا فيه output node أو أكتر لتسليم البيانات للوجهات (ممكن flow يخلص من غير output node)
Input node
نقطة دخول الرسالة، بتمثل المصدر. ممكن يبقى فيه أكتر من input node كل واحد على مصدر مختلف
Processing node
nodes وسيطة بتحوّل وتثري الرسالة
Output node
بيحط الرسالة على transport أو وجهة
Terminal
نقطة دخول (input terminal) أو خروج (output terminal) على الـ node
Connection / wire
السلك اللي بيوصل terminal بـ terminal، وبيوفّر مسار للرسالة

الـ terminal الواحد ممكن يتوصّل بأكتر من سلك. ساعتها الرسالة بتتنسخ، أو بتطلع رسايل مختلفة. ترتيب اتباع المسارات عشوائي، لكن المسارات بتتنفذ واحد ورا التاني (sequentially): كل مسار بيتمشي لحد ما يخلص وبعدين يتاخد اللي بعده.

انتبه
وصل أكتر من سلك على نفس الـ input terminal مش معناه aggregation (تجميع رسايل).

Stateless وTransactional

الـ flow العادي stateless: كل تشغيل (instantiation) بيتعامل كـ transaction مستقلة ملهاش علاقة بأي طلب قبلها. هنشوف بعدين إزاي تربط transactions ببعض. ولو ظبطت الخصائص صح تخلي الـ flow transactional فلو حصل runtime error يتم التراجع (back out) عن المعالجة الوسيطة. وتقدر تخلي أجزاء من الـ flow تشتغل على أكتر من thread، وتكتب منطق معالجة أخطاء خاص بيك بعيدًا عن الافتراضي.

الـ Logical message tree (مهم جدًا)

Figure 2-13

ACE مبيشتغلش على الرسالة وهي bits خام. بيحوّلها الأول لشجرة منطقية (logical tree) وبعدين يشتغل عليها. ده بيفصل الشكل الفيزيائي للبيانات عن هيكلها المنطقي، وده اللي بيسهّل التحويل والـ routing.

  • الـ input node بيحوّل الـ bit stream لشجرة عن طريق عملية اسمها parsing
  • الـ output node بيرجّع الشجرة لـ bit stream بعملية اسمها serialization
  • الشجرة بتحتوي بيانات الرسالة الأصلية + معلومات عن بيئة التشغيل وخصائص الـ transport ومعلومات «تحكم» تانية
  • نوع الـ transport هو اللي بيحدد الـ headers اللي تتحط في الشجرة

هيكل الشجرة

Root
 ├─ Properties
 ├─ MQMD  (header خاص بـ MQ)
 ├─ Other headers
 └─ Body  (محتوى الرسالة نفسه)
(+ ExceptionList لو حصل خطأ)

الشجرة بتبدأ بـ node اسمه Root، وتحته الـ subtrees. لو حصل runtime error، بيتبني tree خاص اسمه Exception List فيه معلومات الخطأ ويتحط مع الـ Root. ولأن الشجرة ليها هيكل واضح، تقدر تستخدم XPath للتنقل فيها وتعديلها في nodes كتير.

تنبيه دقة
أي جزء من الشجرة تقدر توصله من الـ nodes. لكن التعديل بيتم عن طريق nodes معينة (زي Compute وMapping) مش أي node. وكمان الـ parsing ممكن يتأجل (on demand) ومش لازم يحصل كله أول ما الرسالة توصل. الكتاب هنا بيبسّط.

مثال للـ parse والـ serialize

Figure 2-14

الكتاب بيدّي مثال: رسالة COBOL فيها عمر وطول واسم بتوصل كـ bit stream: «032 1725 Joe Bloggs». الـ parser بيحوّلها لـ input logical tree. بعدين Compute node بيطبّق منطق ويبني output logical tree. بعدين الـ serializer بيحوّله لـ XML.

Input bit stream:  032 1725 Joe Bloggs
        |  Parser (بيستخدم Model)
        v
Input logical tree
        |  Transformation (مستقل عن الصيغة الفيزيائية)
        v
Output logical tree
        |  Serializer (بيستخدم Model)
        v
Output bit stream:
<Person Age="32" Height="172.5"><Name>Joe Bloggs</Name></Person>
Parser = المكوّن اللي بيحوّل bit stream لشجرة. والعملية العكسية اسمها serialization.

القسم 2.5: المشاريع والتطبيقات والمكتبات

أنواع الحاويات

Figure 2-30 و 2-31
Integration project
حاوية متخصصة بتعمل فيها وتدير كل موارد flow أو أكتر. بتظهر في Independent Resources folder. ممكن تحتوي: message flows وsubflows وmessage maps وملفات ESQL وdatabase definitions وBAR files
Application
حاوية لكل الموارد المطلوبة لحل كامل: message flows وmessage definitions (ملفات DFDL وXSD) وJAR files وXSL stylesheets وملفات WebSphere Adapters. وتقدر تنشر أكتر من application على server، والمورد مرئي جوه الـ application بتاعه بس
Library
تجميع منطقي لموارد قابلة لإعادة الاستخدام (message models وmaps وsubflows). نوعين: static وshared
BAR file
وحدة النشر على الـ node، وفيها integration projects وapplications وlibraries
قاعدة ذهبية
الحاويات دي ملفات على نظام التشغيل، والـ Toolkit هو اللي بيدير العلاقات المنطقية بينها. لو عدّلت الملفات برا الـ Toolkit ممكن تكسر المشروع. استخدم الـ Toolkit للتعبئة والنقل، ومتنقلش الملفات بإيدك.

Static library مقابل Shared library

Figure 2-32 و 2-33
Static library
كل application بياخد نسخته الخاصة من المكتبة. لو حدّثتها لازم تعيد packaging وdeploy لكل application بيستخدمها. وقت الـ packaging الهرمية بتتجاهل والمكتبات بتتسطّح في قايمة. التغييرات في الـ Toolkit بتبقى متاحة لكل application بيشاور عليها.
Shared library
بتتنشر مرة على الـ integration server مباشرة، والـ applications بتستخدم اللي منشور. التحديثات بتتعرف تلقائيًا. الـ deployment بيفشل لو المكتبة المطلوبة مش منشورة. مينفعش تشيلها من الـ server طول ما فيه applications بتشاور عليها. لازم الـ application يشاور عليها صراحة. الهرمية بتتحفظ وقت التشغيل. ممنوع تحط message flows جواها. مالهاش حالة تشغيل (مينفعش start أو stop ومفيش threads).

مثال عملي: لو عندك message model مشترك بين 10 applications. استخدم shared library لو عايز نسخة واحدة تتحدث وتتطبق على الكل. استخدم static لو عايز كل application مستقل بنسخته.

  • بيتنتقل للـ node مع الـ deployment

كل كائن في ACE اسمه الكامل = namespace + name (fully qualified name). ده بيسهّل تحديد الكائنات وإصلاح المراجع المكسورة. لو كائن اتغير اسمه، كل المراجع بتتكسر. لو استبدلته بكائن بنفس الاسم تتصلح تلقائيًا. المفهوم ده اسمه name linking، وهو مهم في الشغل الجماعي. ولما تنشئ message flow project بيتعمل broker schema افتراضي اسمه default ومش بيظهر إلا لو عرّفت schemas تانية.

ملخص الـ Unit

  1. Node يشغّل servers، والـ server يشغّل flows كـ threads.

  3. ACE بيحوّل الرسالة لشجرة (parsing)، يشتغل عليها، وبعدين يرجّعها bits (serialization).
  4. الـ Toolkit مبني على Eclipse: perspectives وviews وeditors وworkspace.
  5. المشاريع: integration project وapplication وlibrary (static أو shared) وBAR للنشر.
  6. الـ nodes بتتظبط بخصائص: mandatory وoptional وconfigurable وpromoted.
  7. الـ patterns بتوفر قوالب جاهزة، والـ Flow exerciser بيختبر الـ flow ويوريك المسار.

نص الكتاب الأصلي
This figure shows the components of a message flow. • A message flow starts with at least one input node, which acts as the source of messages for the message flow to process. Often there is only one input node, but there can be multiple input nodes, each pointing to a different source. • Message flow processing and transport nodes are the intermediate nodes where messages are transformed and enriched. • Output nodes place messages on a transport or another destination, although it is possible to end a flow without an output node. • Input and output terminals are the connectors between nodes in a flow. The terminals of the nodes are “wired” together. Wires provide a path for messages to flow from one node to another. A terminal can have multiple connections, which result in a duplication of the message, or multiple different messages. The order in which any of the output paths are taken is random, but the paths are run sequentially. Each path is followed until it ends, and then the next path is taken. • A typical message flow is said to be “stateless,” which means each instantiation of a message flow is treated as an independent transaction, unrelated to any previous request. Later in the course, you see how multiple transactions can be “related” to one another. • By setting the appropriate properties, you can make message flows transactional so that a runtime error backs out any intermediate processing. You can also cause the integration node to process particular parts of a message flow on multiple threads, for parallel processing. You also can define explicit error handling logic, so that runtime errors are handled according to your specific needs, beyond the default error handling that IBM App Connect Enterprise provides. Note: multiple connections to the same input terminal are not message aggregation

ACE بيفصل الشكل الفعلي للبيانات (bits) عن البنية المنطقية. الـ input node بيحوّل الـ bit stream لشجرة (logical message tree أو message assembly) جذرها Root. تحت الجذر الفروع الأساسية: Properties وheaders (زي MQMD وHTTPInputHeader) وBody، وبعدهم LocalEnvironment وEnvironment لمعلومات وقت التشغيل. كل الـ nodes بتشتغل على الشجرة دي، وده سر إنك تحوّل من أي صيغة لأي صيغة.
نص الكتاب الأصلي
• To simplify message transformation and routing, IBM App Connect Enterprise separates the physical format of the data from the logical structure of the data. The logical message tree (or “message assembly”) is the method that IBM App Connect Enterprise uses to describe the structure of the message properties, header, and body. • The tree structure begins with a node called Root. Under Root, other nodes and subtrees are created. These nodes and trees contain the original message body itself, along with information about the message transport that was used to bring in the message. Information about the runtime environment is also part of the tree. If a runtime error occurs, a special tree that is called an Exception List that contains information about the error, is constructed and attached to the Root tree node. • Any part of the logical message tree is accessible by message processing nodes. This capability allows your message flows to make processing decisions that are based on the context of the runtime environment and other factors. • Because the logical message follows a tree structure, it is convenient to use XPath expressions to traverse and modify the message. You can specify XPath expressions in several message processing nodes.

Some nodes require that you write code; these nodes are examined in detail later in this course. Multiple types of properties are associated with a message flow node. You configure some properties at design time. Other properties are configured when you deploy the message flow. You can also configure some properties at run time, after deployment, for greater flexibility. Run time properties are used to modify how the message flow operates without having to re-edit the message flow and then redeploy it. Node properties are accessed in the Properties view. This view has multiple subordinate tabs, each of which has one or more sets of properties. • Mandatory properties are those properties that you must set before you can deploy the message flow to the integration node, or the message flow node cannot operate. In the example that is shown on the figure, the MQ Input node Queue name property is mandatory because the queue from which the node retrieves a message must be specified. Unset mandatory properties prevent a message flow from being deployed. • Optional properties are those properties that you can configure at design time, but if you do not, default values are used. • Configurable properties and Promoted properties are used to alter the properties of message flow nodes at the level of the BAR file or at the integration server or integration node level. For example, a message flow might access a particular database while in development, but a different one when the message flow is running in production. With configurable and promoted properties, you can modify the database information for all message flow nodes that access the database. By making one change, you override all references to the database used in development to the database that the message flow uses in production, without re-editing all those nodes. Configurable properties and promoted properties are covered later in the course.
