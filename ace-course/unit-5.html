التحكم في مسار الرسائل

Controlling the flow of messages

هنا تفهم إزاي ACE بيمثّل أي رسالة كشجرة منطقية (logical message tree)، وتتعلم nodes التوجيه (Filter وRoute وLabel وRouteToLabel وFlowOrder)، ومبادئ ESQL وXPath، وبعدين الـ subflows اللي بتخليك تعيد استخدام جزء من الـ flow.

أهداف الـ Unit

القسم 5.1: Message parsing and assembly

نظرة عامة على الـ parsing

الـ flow عادةً بيستقبل رسالة بصيغة معينة ويحوّلها لصيغة تانية. مثال الكتاب: رسالة COBOL فيها age وheight وname بتوصل كـ input bit stream، فتتحول لـ input logical message tree، وبعد التحويل في Compute node بتطلع output logical message tree، وبتتحول لـ output bit stream على شكل XML.

  • الـ Parser: مكوّن الـ integration node اللي بيحوّل bit stream لـ logical message tree
  • الـ Serializer: بيحوّل الشجرة تاني لـ bit stream
  • الـ logical tree مستقلة عن الصيغة الفيزيائية ومنطق التحويل
  • الاتنين بيعتمدوا على model

الـ Logical message model

  • طريقة موحدة ومريحة لتمثيل محتوى الرسالة جوه ACE
  • بتشيل التفاصيل الفيزيائية وتعزلها
  • منظمة كـ message assembly فيها أربع أشجار
Message tree (Root)
الخصائص والمحتوى
Environment
تخزين معلومات أثناء مرور الرسالة في الـ flow
Local environment
بينشئه الـ input node لتخزين متغيرات تقدر nodes لاحقة تقراها وتعدلها
Exception list
معلومات الاستثناءات في الـ flow
  • قيم العناصر بتتخزن بـ Unicode لتسهيل تحويل الترميز
  • العناصر بتتعنون بـ XPath أو dotted name، مثال: TRANSACTION.CUSTOMER.FIRST_NAME

الـ message assembly

لما input node يستقبل رسالة بيتكوّن message assembly من أربع أشجار. الرسالة المحلّلة بتتكتب في الـ Root، والتلاتة التانية فاضية في الأول. بتتملّي: بواسطة nodes معينة (LocalEnvironment)، وبواسطة الـ integration node لما يحصل استثناء (ExceptionList)، وبواسطة ESQL أو Java في JavaCompute وCompute وFilter وDatabase (كل الأشجار). الـ Root وأجزاء من LocalEnvironment ممكن تتعدل بـ Mapping node كمان.

الـ Root فيه: Properties وMQMD (اختياري) وheaders تانية والـ Body.

نفس البيانات بصيغ مختلفة

الكتاب بيوضح إن Address ممكن تكون XML أو Java class أو COBOL structure أو C struct، وكلهم نفس الكيان المنطقي. شجرة بسيطة (من فوق لتحت ومن الشمال لليمين) تقدر تمثل أي منهم. أي بيانات محتاجة تتعالج في flow ممكن تتمثل كشجرة.

مثال logical model

COBOL copybook يمثل رسالة fixed-format (TRANSACTION فيها CUSTOMER وADDRESS وTRANS-DATE وCOST وCC-NO). من الـ copybook والرسالة الفعلية بتتبني الشجرة. كل leaf فيها label وvalue، مثلًا Surname = Herbison. الأنواع المدعومة في الـ leaf بسيطة: string وinteger وfloat.

نقطة مهمة
مش بتهتم إن الـ integer fullword أو doubleword أو Big-endian أو Little-endian. دي تفاصيل فيزيائية مالهاش علاقة بمحتوى الأعمال. والقيم بتتخزن بـ Unicode مش EBCDIC ولا ASCII، فالمطور بيركز على البيانات.

الـ ResetContentDescriptor node

  • بيطلب parser مختلف لتحليل الرسالة
  • بيربط معلومات الـ parser الجديد بالـ bit stream الداخل
  • مش بيغير المحتوى ولا بيحوّل من صيغة لصيغة
  • موجود في drawer اسمه Construction في الـ palette

مثال: لو صيغة الرسالة مجهولة عند الدخول فبتختار BLOB parser على الـ input node. لاحقًا لو احتجت تقرا محتوى، تستخدم ResetContentDescriptor لتحديد الـ domain (DFDL أو XMLNSC) فالـ nodes اللي بعده تقدر تشير للمحتوى.

القسم 5.2: Routing nodes وESQL

يوجه الرسالة حسب المحتوى بتقييم ESQL filter expression داخل ESQL module
Route
يوجه الرسالة عبر مسارات بتقييم XPath expressions
Label
هدف (target) لقرار التوجيه
RouteToLabel
يفحص الرسالة ليعرف معرّف الـ Label المطلوب التوجيه إليه

يفرض ترتيب معالجة محدد للرسالة اللي بيمررها
ترتيب غير مضمون
لو وصلت أكتر من node أو تسلسل nodes بـ output terminal واحد، مش هتقدر تتوقع أي تسلسل يتعالج الأول. لو الترتيب مهم استخدم FlowOrder.

الـ Filter node

  • بيقيّم ESQL expressions في ESQL module (زي WHERE clause في SQL)
  • بيوجه الرسالة عبر terminal مناسب
  • الرسالة الداخلة مش بتتعدل
  • الرسالة بتضيع لو الـ terminal مش موصول (True وFalse وUnknown)
  • ممكن يوصل لـ relational database
True
التعبير رجّع true
False
التعبير رجّع false
Unknown
قيمة غير صالحة كـ Boolean، أو RETURN; من غير تعبير، أو null. وكمان لو حصل خطأ أثناء الوصول لقاعدة بيانات
Failure
حصل runtime error أثناء المعالجة. لو موصول بتتبعت منه، وإلا error handling الافتراضي

الـ node له input terminal واحد وأربع output terminals. حتى لو كتبت ESQL بتغير الرسالة، التغييرات بتتجاهل عند الإرسال. مهم: الرسالة دايمًا بتتبعت من terminal، فلو الـ terminal مش موصول ممكن تضيع (الكلام ده ما بينطبقش على Failure اللي بيتعامل زي أي node). لتفرع أعقد استخدم Route أو RouteToLabel وLabel.

ESQL

Extended Structured Query Language: لغة من IBM بتمدّد SQL لتعريف سلوك الـ nodes: تختبر وتحسب وتعدّل حقول الرسالة، وتشير لـ header fields، وتغير خصائص الحقول. مبنية على SQL 3.

RETURN Body.Msg.Name = 'IBM';
SET OutputRoot.XMLNSC.Msg.Name = 'IBM';
SET OutputRoot.XMLNSC.Msg.Name = InputBody."First.Name";
  • السطر الأول لـ Filter node: بيختبر Msg.Name على الثابت IBM، ومحتوى الرسالة هنا ما بيتغيرش
  • السطرين التاني والتالت لـ Compute node: هنا بتقدر تغير الرسالة، فبنفرق بين InputRoot وOutputRoot
  • في "First.Name" النقطة جزء من الاسم مش تسلسل هرمي، فلازم تحط الاسم بين double quotes. الكتاب بيقول إنه مش ممارسة برمجة جيدة، لكن ممكن يحصل لما تستورد structure قديم

Correlation names للوصول للشجرة

أسماء زي Root وInputRoot وOutputRoot وBody وInputBody وLocalEnvironment وEnvironment وExceptionList وDatabase هي مؤشرات (pointers) داخل الشجرة (والقاعدة في حالة Database). بتتستخدم في كود ESQL وفي patterns الـ Trace node وفي data location parameters في MQGet وغيرها. مثال: Root.XMLNSC.Complaint.Text.

Body
اختصار لـ Root.*[<] يعني آخر ابن للـ Root، وفيه الرسالة الأصلية
InputBody
اختصار لـ InputRoot.*[<]

الـ ESQL module

  • لازم يبدأ بـ CREATE node_type MODULE وينتهي بـ END MODULE
  • اسم الملف لازم يطابق الاسم في خاصية الـ node (Filter expression)
  • امتداد الملف .esql
  • جوه الملف، قيمة الخاصية المناظرة في الـ node بتحدد اسم الـ module
  • المحتويات: constants وPATH statements، وSHARED وEXTERNAL variables، وfunctions وprocedures

كل module معرّف في ملف ESQL ضمن نفس integration node schema اللي فيه الـ node. لكل node لازم يكون فيه module من النوع الصح (Filter node يستخدم FILTER module). لإعادة استخدام constants أو functions أو procedures، عرّفها على مستوى الـ schema واستدعيها بالاسم الكامل أو بـ PATH statement (في نفس الملف وبره أي module).

PATH MySchema2;
CALL MySchema2.ProcX(p);

مثال ESQL لـ Filter

CREATE FILTER MODULE FilterByDepartment
  CREATE FUNCTION Main() RETURNS BOOLEAN
  BEGIN
    DECLARE Department REFERENCE TO Root.XMLNSC.Department;
    IF Department = 'B01' THEN
      RETURN TRUE;
    ELSE
      IF Department = 'C01' THEN
        RETURN FALSE;
      ELSE
        RETURN UNKNOWN;
      END IF;
    END IF;
  END;
END MODULE;

اسم الـ Filter expression هو FilterByDepartment، وبيطابق اسم ملف الـ ESQL واسم الـ module. الكود بيفلتر حسب حقل Department: B01 يطلع من True، وC01 من False، وغير كده من Unknown. الـ DECLARE بتعرّف متغير محلي بيشير لقيمة في الشجرة، وXMLNSC في المسار Root.XMLNSC.Department هو الـ parser.

الـ ESQL editor

  • فحص صياغة (syntax): علامات ترقيم ناقصة، وfunctions وkeywords مستخدمة غلط
  • فحص دلالي (semantic): identifiers غير محلولة، وعدم تطابق message أو database reference، وkeywords deprecated
  • تقدر تنشر المشروع مع warnings لكن مش مع errors
  • تقدر تظبط تفضيلات الفحص
  • Content assist: Ctrl+Space، وكليك يمين لخيارات إضافية

يضيف تلقائيًا للـ PATH الـ schemas اللي فيها procedures أو functions بيستدعيها الكود

لإنشاء module لـ node بتتسمى flowName_nodeName، أو تربط node بـ module موجود. علامة الخطأ (decorator) على الهامش: مثلث أصفر = warning، وعلامة تعجب حمراء = error، والتفاصيل في تبويب Problems.

الـ Route node

  • XPath expressions بتوجه الرسايل للـ output terminals
  • Match: لو الـ filter اتحقق
  • Default: لو ولا expression اتحقق
  • Failure: لو runtime error (لو موصول)
  • ممكن تضيف terminals زيادة
  • بيبعت للـ terminals بالترتيب اللي في الـ Filter table
  • Distribution mode (First أو All) يحدد السلوك لو الرسالة طابقت أكتر من pattern

الـ node له input واحد وثلاث outputs افتراضيًا. وقت التصميم بتملّي جدول فيه XPath expressions وأسماء terminals. وقت التشغيل الجدول بيتفحص، وأول ما expression يتحقق الرسالة تتوجه للـ terminal المسمى. لو Distribution mode = First بيقف عند أول تطابق. لو All بيكمل فحص الباقي. الـ expressions لازم تبدأ بـ $Root أو $Body أو $Properties أو $LocalEnvironment أو $DestinationList أو $ExceptionList أو $Environment. للأداء حط الأكتر تحققًا في أول الجدول. غالبًا بتحدد terminal فريد لكل expression. زي Filter، Route ما بيغيرش الرسالة.

XPath

  • اختيار عناصر من شجرة XML بتعبير تصريحي من غير تنقل صريح: /document/chapter/title
  • بيرجع nodeset
  • ممكن يختار عناصر متعددة. مثال: /library/books/book
  • 13 axis للتنقل: self وparent وchild وancestor وdescendant وattribute وnamespace وغيرها، والصيغ المختصرة: ... // @ *
  • predicates للبحث. مثال: book[author='Steven Bawking']
  • functions. مثال: count(/sum/library/books/book)

XPath متصمم لـ XML لكن بيشتغل على أي شجرة، وفي ACE بيختار عناصر من الـ logical model بغض النظر عن صيغة الـ bit stream. فيه متغيرات XPath جاهزة زي $Body و$Environment. دبل كليك على عنصر في الشجرة بيبني التعبير لحد العنصر. مرجع كامل: www.w3.org/TR/xpath

XPath Expression Builder

بتفتحه من معظم الحقول اللي بتتوقع XPath. بيساعد في بناء تعبيرات XPath أو ESQL. فيه تلات views: Data Types Viewer (types وelements وattributes)، وXPath Functions (String وBoolean وNumeric وNodeset)، وOperators. اللي بيظهر بيعتمد على نوع الـ property editor.

إضافة terminals للـ Route

كليك يمين على الـ Route node > Add Output Terminal، واكتب اسم الـ terminal.

RouteToLabel وLabel

  • بيحولوا التحكم داخل الـ flow حسب محتوى LocalEnvironment
  • RouteToLabel بيفحص LocalEnvironment.DestinationData ليعرف معرّف الـ Label الهدف
  • تقدر تضبط DestinationData بـ Compute أو JavaCompute أو Mapping
  • Label مش بيغير الرسالة وبيستقبلها كنقطة دخول لفرع في الـ flow (غالبًا subflow)
  • Label ممكن يشتغل مع SOAPExtract أو كهدف لـ PROPAGATE في ESQL
خطأ شائع
لو قيمة حقل الوجهة ما اتضبطتش لما الرسالة توصل RouteToLabel، بيحصل runtime error.

القيمة اللي بيجيبها RouteToLabel لازم تطابق خاصية Label على Label node معين. تقدر تستخدم Label من غير RouteToLabel بإرسال الـ flow ليه عبر PROPAGATE في Compute node.

الـ FlowOrder node

  • عنده output terminalين: First وSecond
  • الرسالة اللي بتطلع من الاتنين متطابقة (هي نفس الرسالة الداخلة)
  1. الرسالة تتبعت للـ node الموصول بـ First
  2. كل المعالجة في كل الـ nodes اللي بعده في التسلسل ده تخلص قبل ما التحكم يرجع للـ FlowOrder
  3. الرسالة تتبعت للـ node الموصول بـ Second

مثال الكتاب: Compute بيعمل error topic. الـ FlowOrder بيبعت الرسالة الأول لـ Publication node (على First)، ولما يخلص بيبعتها لـ Throw1 (على Second). الـ FlowOrder ما بيعملش أي معالجة تانية، بيفرض الترتيب بس.

القسم 5.3: Subflows

إيه هو الـ subflow؟

Subflow هو message flow ممكن يتنادى من flow تاني، زي الـ macro في البرمجة: تكتبه مرة وتدمجه في flows تانية. بتبنيه زي أي flow (nodes وwiring)، لكن لازم يبدأ بـ In node وينتهي بـ Out node اللي بيمرروا التحكم من وللـ main flow.

  • flows بـ Input أو Output nodes أو الاتنين
  • يتعرّف في ملف .subflow أو في ملف .msgflow
  • سلسلة أفعال مشتركة بين flows أو applications أو integration services
  • بيتعامل كأي node (compound node): بتسحبه (embed) وتوصل الـ terminals
  • إعادة استخدام كود، ودعم nesting متعدد المستويات
  • ممكن تعمل promote لخصائص الـ node وتضبطها من مستوى أعلى

Nodes المستخدمة مع الـ subflows

  • كل subflow لازم يبدأ بـ input node واحد على الأقل وينتهي بـ output node واحد على الأقل
  • لما تستخدمه في main flow بيظهر كـ node واحد
  • كل Input node في الـ subflow = In terminal على الـ subflow node، وكل Output = Out terminal
  • لو استخدمته كأول node في الـ flow: محتاج Input node زي MQInput وOutput node عام
  • لو في النص: Input node عام، وOutput node عام لو هتوصل nodes بعده
  • لو في الآخر: Input node عام وOutput node زي MQOutput

اسم الـ terminal (بتشوفه لما تحط الماوس عليه) بيطابق اسم نسخة الـ Input node، فسمّي الـ Input nodes أسماء واضحة.

Subflow في ملف .subflow

الكتاب بيقول: لما تطور حلول جديدة، اعمل subflows كملفات .subflow. بتتنشر بطرق:

  • على نفس integration server لكن منفصلة عن الـ flows اللي بتستخدمها (لازم تكون على نفس الـ integration server)
  • مباشرة على الـ integration server أو كجزء من library. لو عدّلت وأعدت النشر، كل الـ flows اللي بتستخدمه (خارج application أو integration service) بتتحدث تلقائيًا من غير إعادة نشرها. ولو في shared library، كل flows الـ application أو الـ integration service بتتحدث تلقائيًا
  • كجزء من application أو integration service
قيود
مينفعش تستخدم في النوع ده: nodes بتمثل subflows معرّفة في ملفات .msgflow، ولا user-defined nodes اتعملت من subflows في .msgflow. ولو عملت BAR file فيه ESQL وsubflow من .subflow، مينفعش تحط الـ ESQL مباشرة في compiled message flow files.

Subflow في ملف .msgflow

  • بيتدمج جوه الـ parent flow لما يتحط في BAR file
  • لازم ينتشر على integration server مع الـ flow اللي بيستخدمه
  • لو عدّلته لازم تعيد نشر كل الـ flows اللي بتستخدمه
  • ممكن يتجمع كـ user-defined node
توصية الكتاب
لو ممكن، حوّل الـ subflows القديمة في ملفات .msgflow لـ .subflow.

Subflows في shared libraries

  • ممكن تحتوي input وoutput nodes القياسية، وممكن أي input node
  • الـ subflow بيتعمل له instance لما يتستخدم جوه flow بس
  • ما بياخدش thread pool خاص بيه ومينفعش يشتغل خارج application
  • لازم يتحط في broker schema، وممكن في schemas متعددة
  • تقدر تسحبه في flow أو subflow داخل application من الـ Toolkit
  • مينفعش يكون في الـ default broker schema
  • الـ subflows لـ schema معين مينفعش تكون في أكتر من shared library يشير لها application واحد أو library

خصائص الـ subflow في BAR

  • تقدر تظبط overrides للـ subflows
  • قيم مشتركة أو قيم مختلفة لكل instance
  • قابلة للضبط وقت النشر: مع الـ main flows والـ applications أو لما تنشر الـ subflow لوحده
  • متوافقة مع BAR file editor وأمر mqsiapplybaroverride وAPI applications

مثال: Generic error handler subflow

  1. الرسالة الأصلية بتتنشر (published)
  2. الدعم الفني أو تطبيقات المراقبة بيشتركوا في topics الأخطاء
  3. في أحيان بيحتاج تدخل يدوي

الـ flow بيكتشف أي exception، وفي subflow بيضيف محتوى ExceptionList للرسالة وينشرها على topic خاص. الرسالة المسببة للمشكلة بتتشال من الـ input queue وتتجاهل. الدعم يقدر يشترك، ويفحص ExceptionList، ويتصرف، ويمسحها ويعيد معالجة الرسالة. الحل ده عام لكل الـ message domains ويتعامل مع أخطاء الـ parsing كمان. السر: تعامل مع محتوى الرسالة كـ BLOB، فتعيد التحليل (reparse) كـ BLOB بـ ResetContentDescriptor قبل باقي معالجة الـ error handler.

ملخص الـ Unit

  1. الرسالة بتتحول لشجرة منطقية مستقلة عن الصيغة، والـ message assembly فيها Root وEnvironment وLocalEnvironment وExceptionList.
  2. Filter يستخدم ESQL ويطلع True/False/Unknown/Failure. Route يستخدم XPath ويطلع Match/Default/Failure وterminals مخصصة.
  3. RouteToLabel + Label = توجيه ديناميكي حسب LocalEnvironment.DestinationData.
  4. FlowOrder يفرض ترتيب معالجة بين First وSecond.
  5. Subflows بتعيد استخدام الكود، والأفضل ملفات .subflow.

اختبر نفسك

1. صح أم غلط: الـ Subflow لازم يتعمل في نفس الـ project اللي فيه الـ main flow اللي بينادي عليه.
غلط. ممكن يتعمل في ملف .subflow منفصل وينتشر لوحده عن الـ flows اللي بتناديه.
2. صح أم غلط: الـ Route node بتستخدم جدول ESQL statements لتحديد الـ terminals.
غلط. جدول الـ Route مكوّن من XPath statements.
3. الرسالة وصلت لـ Filter node ومفيش حاجة موصولة على Unknown terminal والـ ESQL رجّع UNKNOWN. إيه اللي هيحصل؟

Filter node: terminal دخل واحد وأربع terminals خرج (True, False, Unknown, Failure). بيقيّم ESQL expression (زي شرط WHERE) لازم ترجع Boolean: True تروح لـ True، False لـ False، Unknown (لو القيمة NULL) لـ Unknown. الرسالة الأصلية بتتبعت زي ما هي من غير تعديل.

The original incoming message is routed to one of the four output terminals. • The Filter node works by running ESQL that you write. The ESQL must return a Boolean value of “True”, “False”, or “Unknown”. The message is routed as follows: ▪ If the return value evaluates to “True”, the message is propagated out the True terminal. ▪ If the return value evaluates to “False”, the message is propagated out the False terminal. ▪ If the return value evaluates to an unknown value (a value that is not a valid Boolean), the message is propagated out the Unknown terminal. The values that are retrieved from the database can be part of the ESQL code, which can be used to set the Boolean return value. Database access is covered in a subsequent unit. When you are accessing a database and an error occurs, the message is propagated through the Unknown terminal. • For more sophisticated branching and routing capabilities, use the Route node (or RouteToLabel and Label nodes).

• A subflow is a message flow that can be started from another flow. You can also use a subflow to simplify the main flow, by breaking out a portion of the processing logic into its own subflow, and then calling that subflow from the main flow. • You construct a subflow the same way that you do a main flow, by adding, configuring, and wiring message flow nodes. A subflow differs from a main flow in that it must begin with an In node, and end with an Out node. These nodes are used to pass control from and return control to the main flow. • You can develop subflows in two ways: ▪ You create a subflow in its own .subflow file. ▪ You can create a subflow that is part of a .msgflow (or main flow) file. • Both of these methods for subflow development are described later in this unit.

Figure 5-29 Message flow nodes that are used with subflows

الـ subflow لازم يبدأ بـ Input node واحد على الأقل وينتهي بـ Output node واحد على الأقل. لما تستخدمه في flow بيظهر كـ node واحد؛ كل Input node فيه بيظهر كـ terminal دخل (In)، وكل Output node بيظهر كـ terminal خرج (Out).
نص الكتاب الأصلي
• When you create a subflow, it is represented as a single node that you add to the canvas at whatever point you want to start it. • Every Input node that is defined in the subflow represents an In terminal on the Subflow node. Every Output node that is defined in the subflow represents an Out terminal on the Subflow node. You can use these terminals to connect the subflow node to other nodes in the parent flow. • The slide indicates that you must have at least one Input node and one Output node per subflow. Depending on your processing requirements, you can have more than one of each. Multiple input nodes correspond to multiple entry points into, and multiple return points from the subflow. ▪ If you want to use a subflow as the first node in your message flow, you need to add at least one Input node, such as the MQInput node, and one generic Output node. ▪ If you want to use a subflow in the middle of a message flow, you need to add at least one generic Input node. You need to add a generic Output node if you want to connect more nodes in the message flow after you add the subflow. ▪ If you want to use a subflow as the last node in a message flow, you need to add at least one generic Input node, and at least one Output node, such as the MQOutput node. • When you include the subflow in a “main” message flow, this subflow icon shows a terminal for each Input node that you include in the subflow. The name of the terminal (which you see when you hover the mouse cursor over it) matches the name of that instance of the Input node. Give your Input nodes meaningful names that you can recognize easily when you use their corresponding terminal on the subflow node in your message flow.

Figure 5-30 Subflow that is defined in a .subflow file

Subflow في ملف .subflow: ينفع يتنشر منفصل (على نفس الـ integration server مع الـ flows اللي بتستخدمه)، أو كجزء من library. لو عدلته وأعدت نشره، كل الـ flows اللي بتستخدمه (اللي مش جوه application) بتتحدث تلقائياً من غير redeploy لها.
نص الكتاب الأصلي
A subflow that is defined in a .subflow file can be deployed in any of the following ways: • The subflow is deployed separately from any of the message flows that use this subflow. The subflow and the message flows that include this subflow must be deployed in the same integration server. • The subflow can be deployed directly to an integration server or as part of a library. If you update this type of subflow and redeploy it, all message flows that use this subflow, and are not part of an application or the integration service, are automatically updated. You do not need to redeploy these message flows. If you update a subflow in a shared library and redeploy it, all message flows in an application or integration service that use the subflow are updated automatically. • The subflow is deployed as part of an application or integration service. You cannot use the following nodes in this type of subflow: • Nodes that represent subflows that are defined in .msgflow files • User-defined nodes that are created from subflows that are defined in .msgflow files If you create a BAR file that contains both ESQL code and a subflow that is defined in a .subflow file, you cannot include the ESQL code directly in compiled message flow files.

Figure 5-31 Subflow that is defined in a .msgflow file

Subflow في ملف .msgflow: بيتضمّن جوه الـ parent flow لما تعمل BAR، فينتشر مع الـ flow بس. لو عدلته لازم تعمل redeploy لكل flows اللي بتستخدمه. وممكن يتغلّف كـ user-defined node.
نص الكتاب الأصلي
• A subflow that is defined in a .msgflow file is embedded inside any parent message flows that use it when the message flow is placed in a BAR file. • This type of subflow can be deployed only to an integration server with the message flow in which it is used. If you update this type of subflow, you must redeploy all message flows that use the subflow for the changes to be used. • This type of subflow can be packaged as a user-defined node.

الـ subflows في shared libraries ممكن تحتوي input/output nodes عادية أو أي input node. بتتعمل instance لما تتستخدم في flow بس. شروط: مينفعش تبقى في الـ default broker schema، ومينفعش نفس الـ schema تتكرر في libraries متعددة بيشير لها application واحد.

في الـ BAR تقدر تعمل overrides لخصائص الـ subflow: قيم مشتركة أو قيم لكل instance، وقت الـ deploy بأدوات الـ BAR editor أو أمر mqsiapplybaroverride.

Figure 5-34 Example: Generic error handler subflow

مثال Generic error handler: (1) الرسالة الأصلية بتتنشر، (2) فريق الدعم أو تطبيقات المراقبة بتشترك في topics الأخطاء، (3) أحياناً بيحصل حل يدوي. الـ subflow بيلقط أي exception، بيضيف محتوى ExceptionList للرسالة وينشرها على topic خاص، والرسالة بتتشال من الـ input queue. الدعم يفحص الـ ExceptionList ويعيد معالجتها بعد الإصلاح.
نص الكتاب الأصلي

The offending message is removed from input queue and discarded. • Support personnel or monitoring applications can subscribe to the error topic, receive error messages, inspect its ExceptionList, take appropriate actions to resume the error, delete the ExceptionList, and reprocess the message. • This solution is a generic error handler; it works for all message domains. It also handles parsing errors. The only way to achieve this result is to treat the message body as BLOB. To do that, first you reparse the message as BLOB in a ResetContentDescriptor node before doing the other manipulations in the error handler subflow.
