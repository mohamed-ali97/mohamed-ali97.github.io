الـ Compute node

  • البيانات بتتنسخ من الـ input لـ output area: الرسالة كلها أو الـ headers بس، أو أجزاء تانية من الـ message assembly
  • تبني رسالة أو رسايل بكتابة ESQL في ملف ESQL الخاص بالـ flow
  • بيدعم التلاعب بهيكل الـ output: جلب بيانات من database خارجية وإعادة ترتيب الحقول
  • عبارة PROPAGATE تولد رسايل output متعددة أو توجه الرسالة لـ terminals مختلفة: Out وOut1 وOut2 وOut3 وOut4
  • خاصية Compute Mode بتحدد أنهي message trees تتبعت

في الـ Compute node لازم تكتب Input أو Output قبل Root عشان تفرّق بين الرسالة الداخلة والخارجة (InputRoot وOutputRoot). OutputBody مش correlation name صالح (زي InputBody) في بعض statements لأن الـ node ما يعرفش أنهي parser يبني الـ body، فلازم تحدد الـ parser صراحة بـ OutputRoot، مثلًا:

SET OutputRoot.XMLNSC.a.Field = ...;
SET OutputRoot.DFDL.b.Field = ...;

بيتبني output message واحدة في المرة، وتقدر تبني سلسلة رسايل بـ PROPAGATE. خاصية Compute Mode بتتحكم أنهي مكونات (Message وLocalEnvironment وException List) تتستخدم افتراضيًا في الـ output، وتتطبق لما الرسالة تروح لـ Out terminal أو لما PROPAGATE ما يحددش التركيبة.

ملف ESQL والـ module

  • ملف ESQL فيه ESQL لكل node في الـ flow محتاجه، اسمه الافتراضي MessageFlowName_ComputeNodeName.esql
  • كل Compute node مرتبط بـ module واحد، واسم الـ module لازم يطابق خاصية ESQL Module
  • كل module فيه function اسمها Main() هي نقطة الدخول
  • RETURN في Main() بيتحكم في الـ propagation
RETURN TRUE;
الرسالة تتبعت لـ Out terminal
RETURN FALSE;
الرسالة ما تتبعتش
RETURN UNKNOWN;
الرسالة ما تتبعتش

كل ESQL module لازم فيه function Main() من غير arguments وبترجع Boolean. الـ RETURN في Filter أو Database node له وظيفة مختلفة (بيحدد الـ terminal)، وفي Filter مفيد لأنه بيسمح باتخاذ القرار بقوة ESQL كاملة مش مجرد expression.

الـ module والـ integration node schema

اسم كل ESQL module في ملف لازم يكون في نفس الـ integration node schema بتاع الـ node اللي بيشير له. لو عايز تعيد استخدام constants أو functions أو procedures، اعلنها على مستوى الـ schema وارجع لها من أي resource في نفس الـ schema (حتى من project تاني). لازم تكتب الاسم كامل أو تستخدم PATH statement تحدد الـ qualifier، والـ PATH يتكتب في نفس ملف ESQL خارج أي module.

PATH MySchema2;
CALL MySchema2.ProcX(p);

هيكل الـ Compute module

CREATE COMPUTE MODULE MessageFlowName_ComputeNodeName
  CREATE FUNCTION Main() RETURNS BOOLEAN
  BEGIN
    -- CALL CopyMessageHeaders();
    -- CALL CopyEntireMessage();
    RETURN TRUE;
  END;

  CREATE PROCEDURE CopyMessageHeaders() BEGIN
    DECLARE I INTEGER 1;
    DECLARE J INTEGER CARDINALITY(InputRoot.*[]);
    WHILE I < J DO
      SET OutputRoot.*[I] = InputRoot.*[I];
      SET I = I + 1;
    END WHILE;
  END;

  CREATE PROCEDURE CopyEntireMessage() BEGIN
    SET OutputRoot = InputRoot;
  END;
END MODULE;

أنت بتشيل الـ comment من CALL CopyMessageHeaders() لو عايز تنسخ الـ headers بس، أو CALL CopyEntireMessage() لنسخ الرسالة كلها. المتغيرات والـ functions اللي تعلنها جوه الـ module محلية للـ module ده بس.

الكتاب بيستخدم رسالة طلب اسمها OrderMsg فيها OrderData (Nr وDate) وCustomer (Nr وFirstName وLastName) وعدة OrderItem (Nr وPrice وInStock وQuantity وأحيانًا Discount). بتتحول في الأمثلة الجاية.

  <OrderItem Nr="222" Price="8765.12"><Quantity>2</Quantity></OrderItem>

SET OutputRoot.XMLNSC.OrderMsg.OrderItem[] =

   FROM InputBody.OrderMsg.OrderItem[] as I,

الـ debugger

الـ Debugger في الـ Toolkit بيدخل جوه كود ESQL statement بـ statement: حط breakpoints في ESQL وبعدين اعرض الـ message assembly. الـ debugger اتشرح في Unit 8.

قواعد syntax أساسية

  • ESQL keywords مش case-sensitive: SET وset وSeT نفس الشيء
  • الـ correlation names وfield references case-sensitive: OutputRoot وInputBody.Msg.field
  • الـ character constants وliterals بين apostrophes (علامات تنصيص مفردة)
  • الـ field references بين quotation marks (علامات مزدوجة) لو الاسم فيه حرف خاص زي مسافة، أو لو الاسم reserved word
  • فاصل الـ statement هو ; (semicolon)
  • Comments: سطر واحد بـ -- ، وبلوك بـ /* ... */

الكتاب بيقترح كتابة الـ statements والـ functions بحروف كبيرة لسهولة التمييز. قائمة الـ reserved words في IBM Knowledge Center.

إضافة وتعديل وحذف الحقول

  • SET بيعدل حقل أو structure لو موجود
  • SET بيضيف حقل أو structure (والمسار كله) لو مش موجود
  • SET ... = NULL بيحذف حقل أو structure
  • ترتيب statements بيحدد ترتيب الحقول
CALL CopyMessageHeaders();
SET OutputRoot.XMLNSC.Msg.A.B.C = 1;
SET OutputRoot.XMLNSC.Msg.E = 2;
SET OutputRoot.XMLNSC.Msg.D = 3;
SET OutputRoot.XMLNSC.Msg.E.B.C = 4;
SET OutputRoot.XMLNSC.Msg.A.B.C = 5;
SET OutputRoot.XMLNSC.Msg.E.B = NULL;

النتيجة حسب الكتاب: Msg فيها A/B/C بقيمة 5، ثم E بقيمة 2، ثم D بقيمة 3. لما SET يشتغل على حقل مش موجود، الحقل وكل الآباء والإخوة اللازمين بيتعملوا كـ next sibling لأدنى ancestor موجود، عشان كده الترتيب مهم.

أنواع بيانات خاصة بالـ trees: ROW وREFERENCE

  • ROW: شجرة مسماة بنوع ديناميكي للـ leaf nodes. بتتعمل من نسخ أو subsets من ROWs تانية (زي Root)، أو نتيجة SELECT، أو بدالة ROW()
  • REFERENCE: مؤشر (tree cursor) ديناميكي
DECLARE rowCust ROW InputRoot.XMLNSC.OrderMsg.Customer;
SET rowCust.Address = ROW('Hursley' AS Town, 'UK' AS Country);

DECLARE refCust REFERENCE TO InputBody.OrderMsg.Customer;
IF LASTMOVE(refCust) THEN ... END IF;
IF FIELDNAME(refCust) <> 'Customer' THEN ...
تحذير
لو عملت REFERENCE لحقل مش موجود، المؤشر بيشاور على Root. اتأكد بـ FIELDNAME أو LASTMOVE أو IF InputBody.Order.NonExistentField IS NOT NULL. وSET على refCust نفسه غير مسموح. الـ REFERENCE ممكن يشاور على حقل في رسالة أو متغير scalar، لكن مش على constant أو database table أو column أو reference تاني.

تحريك الـ REFERENCE

  • PARENT
  • PREVIOUSSIBLING وNEXTSIBLING
  • FIRSTCHILD وLASTCHILD
DECLARE myRef REFERENCE TO InputBody.OrderMsg;
MOVE myRef FIRSTCHILD;
MOVE myRef NEXTSIBLING NAME 'OrderItem';
MOVE myRef LASTCHILD TYPE XMLNSC.Attribute;
MOVE myRef PREVIOUSSIBLING REPEAT TYPE;
WHILE LASTMOVE(myRef) DO ... END WHILE;

لو الـ MOVE فشل، المؤشر بيفضل ثابت. اتأكد من النجاح بدالة LASTMOVE، وبتتستخدم عادةً في WHILE loops.

الحذف وإعادة الترتيب

DELETE FIELD OutputRoot.XMLNSC.OrderMsg.Customer;
DECLARE myRef REFERENCE TO OutputRoot.XMLNSC.OrderMsg.OrderItem[1];
DELETE NEXTSIBLING OF myRef;
SET OutputRoot.XMLNSC.OrderMsg.OrderItem[2] = NULL;
DETACH myRef;
ATTACH myRef TO OutputRoot.XMLNSC.OrderMsg AS FIRSTCHILD;
  • DELETE بيحذف ويحرر الذاكرة (مفيد للرسايل الكبيرة)
  • SET = NULL بيحذف
  • DETACH (قص) ثم ATTACH (لصق) لإعادة الترتيب

في مثال الكتاب، بعد الكود، OrderItem بتتحرك لأول الرسالة قبل OrderData وCustomer. لو ترتيب الحقول في الـ output مختلف عن الـ input، ممكن يبقى أسهل تبني الـ output خطوة خطوة.

عبارة CREATE

SET OutputRoot = InputRoot;
CREATE FIELD OutputRoot.XMLNSC.OrderMsg.Customer.AnAttr
  TYPE XMLNSC.Attribute VALUE 'C';

DECLARE myRef REFERENCE TO OutputRoot.XMLNSC.OrderMsg;

CREATE بتتيح تتحكم في التنقل بالكامل. ممكن تحدد TYPE وNAME وVALUE صراحة (حقل scalar واحد)، أو تكرر حقل بـ FROM. أمثلة تانية: CREATE NEXTSIBLING OF myRef TYPE Name NAME anEmptyTag، وCREATE PREVIOUSSIBLING OF myRef ... VALUE NULL.

القيمة NULL

  • NULL حالة مستقلة: مش 0 ومش مسافة، بتقابل SQL_NULL_DATA
  • بتنطبق على كل أنواع ESQL ما عدا REFERENCE
  • معناها: unknown أو undefined أو uninitialized
  • القاعدة: لو أي operand بـ NULL، النتيجة NULL
  • استخدم NULL لحذف حقل أو structure
SET OutputRoot.XMLNSC.Msg.Field = NULL;
SET OutputRoot.XMLNSC.Msg.F2 = InputBody.Msg.Unknown;
مشكلة شائعة
السطر الأخير بيحذف F2 لو Unknown مش موجود في InputBody، وده ممكن ميكونش المتوقع. تكتشف ده في debug-level User Trace. وضبط حقل لـ NULL بيحذفه بس لو NULL مش مسموح كقيمة (الافتراضي).

Procedures

subroutines بـ IN وOUT وINOUT parameters وRETURNS اختياري. ممكن تتنادى recursively، واللغة ESQL أو Java أو database (stored procedure).

CREATE PROCEDURE navigate (IN root REFERENCE, INOUT answer CHARACTER)
LANGUAGE ESQL
BEGIN
  SET answer = answer||'Reached Field...Name:'||FIELDNAME(root);
  DECLARE cursor REFERENCE TO root;
  MOVE cursor FIRSTCHILD;
  IF LASTMOVE(cursor) THEN
    SET answer = answer || 'Field has children... drilling down ';
  ELSE
    SET answer = answer || 'Listing siblings... ';
  END IF;
  WHILE LASTMOVE(cursor) DO
    CALL navigate(cursor, answer);
    MOVE cursor NEXTSIBLING;
  END WHILE;
  SET answer = answer || 'Finished siblings... Popping up ';
END;
  • CALL بينادي procedure معرّف بـ CREATE PROCEDURE ويمرر الـ parameters بالترتيب
  • IN وINOUT بيتقيموا قبل النداء، والـ OUT دايمًا بيدخل NULL من النوع الصح
  • بعد الانتهاء الـ OUT وINOUT بيتحدثوا، والـ IN ما بيتغيرش أبدًا
  • عدد ونوع الـ parameters لازم يطابق التعريف
  • الـ output message trees ما ينفعش تتوصل لها مباشرة داخل الـ body، لازم تتمرر كـ REFERENCE
  • الـ procedures والـ functions تقدر تنادي بعض (recursion مدعوم)

Scope وlifetime وsharing

  • Scope: أين يُستخدم المتغير (node، flow، integration server، integration node)
  • Lifetime: مدة الحياة (code block، module، thread)
  • Sharing: رؤية الـ threads. SHARED variable بتنتهي لما الـ flow أو الـ integration server يقف
  • BEGIN ATOMIC بتسلسل الوصول لـ SHARED variables
DECLARE s_counter SHARED INT 1;
BEGIN ATOMIC
  SET s_counter = s_counter + 1;
END;

لو محتاج بيانات تعيش أكتر من رسالة واحدة: database (دايمة وفيها transaction لكن بطيئة في الكتابة)، أو متغيرات long-lived (SHARED) أسرع لكن أقل persistence وبدون transaction. بس thread واحد من flow instances ينفذ BEGIN ATOMIC معين في نفس الوقت. مش لازم ATOMIC لو الـ flow ما بينشرش بأكتر من instance، ولا لقراءة وكتابة SHARED عادية، لأن الـ integration node بيكتب ويقرأ بأمان دايمًا. ATOMIC مطلوب بس لو التطبيق حساس لرؤية نتائج وسيطة.

استخدام Compute node للوصول لـ database

خاصية DSN بتتحدد في خصائص الـ node (وممكن في deployment descriptor بتاع BAR)، والـ ESQL بيشير لها بالاسم Database، فالكود مش مربوط بـ database معينة.

SET OutputRoot.XML.Message.Price =
  THE (SELECT ITEM A.PRICE
       FROM Database.PRICEDATA AS A
       WHERE A.PRODUCT = 'Widget');

الـ Compute node كمان بيعمل UPDATE وINSERT وDELETE على database.

إعادة استخدام ESQL

ملف ESQL ممكن فيه modules متعددة، وnodes كتير في flows مختلفة ممكن تشير لكل module. ملفات ESQL ممكن تكون في application أو library، وتقدر تعمل مكتبات كود مشتركة بشرط إن الـ application فيه references للـ libraries المناسبة. مثال الكتاب: My_Application فيه My_Flow وA_Module وB_Module، ومكتبة My_EsqlLibrary فيها Common.esql وC_Module وD_Module.

القسم 11.2: الـ JavaCompute node
