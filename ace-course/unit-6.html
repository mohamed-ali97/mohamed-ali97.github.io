القسم 6.1: Message modeling

ليه محتاجين model؟

  • معظم الرسايل محتاجة model وقت التشغيل لتحليل الـ bit stream (parse) وإنشاء الـ bit stream تاني (serialize)
  • الـ modeling بيسرّع تطوير الـ transformations وقت التصميم في الـ Toolkit: بيوفر source وtarget للـ graphical mappings وبيساعد في تحرير برامج التحويل
  • الـ validation للتأكد من صحة الرسالة وقت الـ parsing
  • version control لما تخزن الـ artifacts في repository مركزي
  • توثيق فوري للمبرمجين والمحللين وأخصائيي الـ integration

معظم الرسايل مش self-defining. برنامج C أو COBOL بيطلع stream من binary data معناه ضايع من غير model. الـ XML عكس كده: verbose وبيوصف نفسه، فأي XML parser يقرا أي XML من غير model. لكن للتأكد إن المحتوى صحيح محتاج model. والـ graphical mapping من رسالة لرسالة مستحيل من غير model حتى لو XML.

تشبيه
زي الـ COBOL copybook: المبرمج بيعمل نسخة جديدة منه كل ما الرسالة تتغير. نفس الفكرة مع الـ message models.

خصائص الـ message model object

Logical model
وصف مستقل عن الصيغة (شبيه بالقيم الافتراضية). بيقول الـ object فيه إيه من غير ما يقول بيتكتب إزاي
Physical model
بيتحكم في parsing وwriting الـ object. فيه مجموعة خصائص فيزيائية لكل صيغة. في MRM message set: مجموعة لكل صيغة (XML وText وBinary)
Documentation
ما بيأثرش على المعالجة

الـ message modeling في ACE

الـ models في ACE كلها مبنية على W3C XML schema 1.0، حتى للصيغ غير الـ XML. الـ message set هي الحاوية الأصلية للـ message models. الأفضل حاليًا لمعظم الصيغ: ملفات الـ schema داخل applications وlibraries. وقت التشغيل ACE بيستخدم الـ model والـ parser لإنشاء الـ logical model من الـ bit stream، وفي آخر الـ flow بيعمل serialize لإنشاء الـ bit stream اللي التطبيق الهدف محتاجه. الـ Importers (COBOL وC وWSDL وAdapters) بتنتج الـ models. الـ domains: DFDL وXMLNSC.

أنواع الـ parsers

Programmatic parsers
معرفة الصيغة مكتوبة في برنامج. كل صيغة جديدة تحتاج parser جديد. لو الصيغة اتغيرت لازم تعدّل وتعيد compile وlink وdeploy
Descriptive parsers
المعرفة مكتوبة في model، وparser عام واحد بيستخدم الـ model. ممكن يستخدم كما هو أو يتولد منه كود
  • XMLNSC وJSON وBLOB: programmatic parsers
  • DFDL وMRM وXMLNSC مع XML schema: model-driven parsers
MRM
الكتاب بيقول إن MRM (Message Repository Manager) مدعوم في WebSphere Message Broker بس، وبيركز على DFDL.

ملفات تعريف الـ model

  • بتوصف البنية المنطقية للرسالة
  • وبتوصف الصيغ الفيزيائية للـ bit stream أثناء النقل
  • ممكن تستوردها من WSDL أو XML schema أو DTD أو COBOL أو C (أو تعدلها يدويًا)
  • فيها messages وelements وtypes وغيرها
  • ممكن تربط DFDL schema files
  • مبنية على معايير XML schema

عادةً تستورد صيغ تطبيقاتك الموجودة لإنشاء الـ models، وبعدين تعدّل البنية المنطقية. في MRM message definition editor تقدر تنشئ وتعدل صيغ binary وXML وtag-delimited string. ممكن كمان تبدأ من ملف فاضي. تركيز الـ Unit ده على DFDL والـ DFDL schema editor.

Message definition importers

  • بتستورد: COBOL وC وXML DTD وXML schema وWSDL
  • منطقيًا: بتنشئ types وelements وattributes، وإنشاء الـ messages اختياري
  • فيزيائيًا: بتملّي الـ wire formats المختارة، وتنشئ wire formats زيادة (مثل XML) لو لازم
  • لـ C أو COBOL لازم تحدد الـ target environment والـ compiler
  • باقي الـ wire formats بتتملّي بقيم افتراضية وممكن تظهر warnings للـ custom wire format والـ tagged-delimited
  • الأداة: Message Definition wizard أو الأمر mqsicreatemsgdefs (بيطلع ملفات *.mxsd حسب option file)

لو اسم الـ message model file موجود، محتواه بيتمسح ويتعاد إنشاؤه. الـ model الناتج فيه معلومات منطقية وفيزيائية، وبيتعدل بعد كده في الـ Toolkit.

المواصفات والـ model والـ logical tree

مثال الكتاب: AddressesMsg بتحتوي HomeAddress وWorkAddress، كل واحد فيه Line (مرتين) وCountry وPostalCode. الـ complex type بيتمثل كمستوى في الشجرة، فمثلًا WorkAddress نوع معقد فيه Line وCountry وPostalCode. في الـ Root.Properties فيه MessageSet = My_Set.xsd وMessageType = AddressesMsg.

Custom wire format (Binary أو CWF)

  • صيغة legacy نموذجية، مثل تعريفات COBOL أو C
  • تمثيلات فيزيائية متنوعة: 4-byte integer أو packed
  • غالبًا fixed-length، أو length-encoded، أو null-delimited
  • حقول variable length ومتكررة: بطول أو عدد محدد مسبقًا، أو ديناميكي بعداد من حقل INTEGER سابق
  • ترتيب الحقول ثابت

في البيانات binary أو CWF مستحيل تفرّق عنصر عن اللي بعده من غير معرفة بنية الرسالة. الـ parser محتاج: ترتيب العناصر (logical properties)، وطول كل عنصر (bytes أو characters)، والـ cardinality، ونوع البيانات، وخصائص العنصر حسب النوع المنطقي. صيغ تانية زي XML بتدعم عناصر بتوصف نفسها، لكن CWF لأ.

مثال CWF

  • الخطوة 1: عرّف كل element وtype
  • الخطوة 2: حدد عدد التكرار: MinOccurs=1 إلزامي، 0 اختياري، MaxOccurs>1 متكرر
  • CWF بيتطلب كل الحقول إلزامية وبترتيب ثابت عند الإدخال، لأن مستحيل الـ parsing من غير tags
  • الخطوة 3: عرّف خصائص CWF الفيزيائية للعنصر داخل complex type. الـ global element ممكن يكون له CWF properties مختلفة (bit stream مختلف) لما يتستخدم في complex type تاني

مثال الكتاب: Line من نوع Fixed Len Str بـ length 20 وpadding character *، وCountry بـ length 2 وpadding NUL، وPostalCode بـ length 10 وpadding SPACE، والـ default للكل #.

Tagged and delimited string (Text أو TDS)

  • صيغ معيارية صناعية: SWIFT وEDI وACORD وAL3 وTLOG
  • غالبًا نص لكن ممكن يدعم binary
  • طول وتكرار وترتيب حقول متغير
  • منظمة
Fixed length
زي CWF
Delimited
كل العناصر أو العناصر المتغيرة الطول بس. مثال: CSV
Tagged
قبل كل قيمة tag. مثال: TAG1:aaa/TAG2:xx/
Encoded length
TAG103aaaTAG202xx: الطول مكتوب بعد الـ tag
Data patterns
regular expressions زي [A-Z] أو {1,3}

TDS متصمم لنمذجة رسايل نصية وبيدي مرونة عالية، مش مقيد بمعايير صناعية، فتقدر تستخدمه لرسايلك أنت. الحقل ممكن يسبقه tag بيعرّفه بشكل فريد. في الرسالة ممكن يبقى فيه delimiter يفصل كل قيمة عن التانية. مثال الكتاب: {LINE:Mail Point 135;LINE:Hursley Park;COUNTRY:UK;ZIP:SO21 2JN} فيه Group indicator "{" وGroup terminator "}" وTag data separator ":" وDelimiter ";".

القسم 6.2: DFDL

إيه هو DFDL؟

  • معيار مفتوح من Open Grid Forum (OGF)
  • بيستخدم تقنيات XML: subset من W3C XML Schema ونظام الـ types لوصف الشكل المنطقي
  • الـ annotations جوه الـ XSD بتوصف التمثيل الفيزيائي
  • XPath لمراجع الحقول
  • بيوصف أي صيغة: نصية وbinary وسجلات تجارية وعلمية وحديثة وقديمة ومعايير صناعية
  • بيدعم round-tripping: القراءة والكتابة من نفس الوصف

DFDL لغة مبنية على XML لتعريف بنية البيانات المنسقة بشكل مستقل عن الصيغة نفسها. الوصف بيسمح بقراءة البيانات من صيغتها الفيزيائية وتمثيلها كـ Infoset أو XML، وبالعكس. بتكتب XML schema للنموذج المنطقي وتضيف عليه DFDL annotations للتمثيل الفيزيائي. DFDL بيستخدم XSDL 1.0.

ACE بيدعم DFDL domain للصيغ غير الـ XML أساسًا. وقت القراءة الـ DFDL parser بيفسر الـ bit stream بقواعد من DFDL schema ويبني DFDL domain logical message tree. وقت الكتابة الـ DFDL serializer بيولّد الـ bit stream من الشجرة.

حدود DFDL
DFDL مش لغة تحويل عامة، ومش مقصود منه ربط البيانات بأي XML model عشوائي.

أنواع البيانات المدعومة

  • نصية: strings وnumbers وzoned decimals وcalendars وBooleans
  • binary: integers وfloats وBCD وpacked decimal وcalendars وBooleans
  • bidirectional text
  • bit data بأي طول
  • pattern languages للنص والأرقام والتواريخ
  • محتوى ordered وunordered وfloating
  • قيم افتراضية عند parsing وserializing
  • Nil values للبيانات خارج النطاق
  • XPath 2.0 expression language مع متغيرات لنمذجة بيانات ديناميكية
  • Speculative parsing لحل الـ choices والمحتوى الاختياري
  • arrays ثابتة ومتغيرة
  • إخفاء عناصر من البيانات
  • حساب قيم العناصر
  • validation بقواعد XML schema 1.0
  • scoping mechanism لتطبيق قيم خصائص مشتركة في أماكن متعددة
  • متغيرات user-defined في تعبيرات DFDL
  • TLOG packed numeric fields
  • Delimited binary data
  • أطوال حقول من regular expressions

DFDL ممكن يمثل superset من الصيغ المتاحة في مكونات الـ modeling التقليدية، لكن المكونات التقليدية (زي MRM message set) لسه موجودة.

مثال: بيانات delimited

البيانات: int=5;float=-7.1E8. دي ASCII text. فيها initiator ("int=" و"float=") وseparator (;). الـ Separators وinitiators (tags) وterminators كلها أمثلة على DFDL delimiters. بتعرفهم في الـ DFDL schema عشان الـ parser يعرف يفسر البيانات.

<xs:complexType name="myNumbers">
 <xs:sequence>
  <xs:annotation>
   <xs:appinfo source="http://www.ogf.org/dfdl/v1.0">
    <dfdl:sequence separator=";" encoding="ascii"/>
   </xs:appinfo>
  </xs:annotation>
  <xs:element name="myInt" type="xs:int">
   <xs:annotation><xs:appinfo source="http://www.ogf.org/dfdl/v1.0">
    <dfdl:element representation="text" textNumberRep="standard" encoding="ascii"
       lengthKind="delimited" initiator="int=" />
   </xs:appinfo></xs:annotation>
  </xs:element>
  <xs:element name="myFloat" type="xs:float"> ... initiator="float=" ... </xs:element>
 </xs:sequence>
</xs:complexType>

الشكل المختصر (short form) بيحط الخصائص مباشرة كـ attributes:

<xs:complexType name="myNumbers">
 <xs:sequence dfdl:separator=";" dfdl:encoding="ascii">
  <xs:element name="myInt" type="xs:int" dfdl:representation="text"
     dfdl:textNumberRep="standard" dfdl:encoding="ascii"
     dfdl:lengthKind="delimited" dfdl:initiator="int=" />
  <xs:element name="myFloat" type="xs:float" dfdl:representation="text"
     dfdl:textNumberRep="standard" dfdl:encoding="ascii"
     dfdl:lengthKind="delimited" dfdl:initiator="float=" />
 </xs:sequence>
</xs:complexType>

دعم DFDL في ACE

  • الـ DFDL models (schema files) بتتخزن في ACE projects
  • الـ DFDL domain والـ model-driven parser متاحين في كل الـ nodes
  • الـ Toolkit فيه أدوات لإنشاء DFDL models، وDFDL model debugger لاختبار parsing وserialization
  • بتتنشر على الـ integration server، وممكن تتخزن مع applications في libraries

تقدر تختبر الـ DFDL model من غير نشر. وعند النشر: في library أو في الـ BAR file مع باقي المكونات.

إمتى تستخدم DFDL وإمتى لأ؟

استخدم DFDL لـ
بيانات binary من COBOL وC وPL/I وASM، وtext بـ delimiters زي CSV، ومعايير نصية صناعية زي SWIFT وHL7 وEDIFACT وX12، ومعايير binary زي ISO8583 وTlog
لا تستخدم DFDL لـ
XML فيه XML parsers وschema أو DTD، وJSON فيه JSON parsers، وصيغ serialization اللي المستهلك مبيشوفش فيها الـ wire format أصلًا ويستخدم APIs
تنبيه
لا تستخدم DFDL expressions لتنفيذ قواعد validation معقدة.

استخدم DFDL لما تحتاج تنمذج وتحلل بيانات نصية أو binary ومعاك مواصفات الصيغة أو أمثلة للبيانات.

الـ DFDL schema editor

  • بتنشئ وتعدل وتختبر DFDL schema files
  • بيفتح لما تفتح ملف DFDL schema موجود أو تنشئ واحد بـ New Message Model wizard
  • تقدر: تعدل الملفات، وتملّي ملف فاضي بـ DFDL schema objects، وتعمل parse لعينة بيانات، وتعمل serialize لـ logical instance document

إنشاء DFDL schema بـ New Message Model wizard

الـ wizard بيولّد DFDL schema من نمذجة ملف بيانات موجود: CSV، أو record-oriented، أو custom text أو binary، أو COBOL data structures.

  1. File > New > Message Model (أو اسحب DFDL schema موجود جوه ACE application)
  2. اختار نوع البيانات: CSV text أو Record-oriented text أو COBOL أو C أو Other text or binary

تلات طرق لبناء الـ schema:

  • الـ wizard بيرشدك (guided authoring): بتحدد خصائص البيانات (delimiters وrecord terminators وfield settings وcode page وglobal settings) والـ wizard بيولّد الـ schema
  • تنشئ DFDL schema فاضي وتنمذج البيانات بالـ editor
  • تستورد أو تستبدل قيم IBM الافتراضية لخصائص CSV

إنشاء model بالـ editor

الـ editor بيستخدم Eclipse views: Logical structure view وPhysical Properties view وDetailed view وDFDL properties view. فيه كمان خيارات للـ parse والـ serialize لبيانات الاختبار. الـ Problems view بيبين المشاكل، وعلامات حمرا في الـ editor عند الأخطاء.

نقاط عدم اليقين (points of uncertainty)

الـ DFDL parser هو recursive-descent parser بيستخدم look-ahead لما يقابل points of uncertainty: choice أو optional element أو variable array. بيحاول يحلل لحد ما الـ object يبقى «معروف إنه موجود» أو «معروف إنه مش موجود».

  • لما يحصل parsing error هو بيكتم الخطأ ويرجع (backtrack) ويجرب بديل
  • استخدم discriminator annotation لتأكيد إن object «معروف إنه موجود» ومنع backtracking غير لازم
  • الـ initiator بيأكد الوجود كمان. لو كل البدائل ليها initiator اضبط Initiated Content = Yes على الـ sequence أو choice بدل discriminator

ربط الـ DFDL parser بالرسالة

ACE بيستخدم Root.Properties لتحديد الـ parser والـ dictionary للـ parsing (In) والـ serialization (Out). المعلومتين المطلوبتين: message domain وmessage. في مثال الكتاب: الـ domain = DFDL في تبويب Input Message Parsing في File Input node، ولازم تحدد الـ DFDL schema في خاصية Message. ممكن تحدد الـ parser ديناميكيًا وقت التشغيل.

شجرة DFDL في الـ trace

Parse timing على الـ input nodes

  • الـ parsing عملية مكلفة، من أغلى العمليات وقت التشغيل
  • On demand (الافتراضي): الرسالة بتتحلل لما حقل يتشار له أول مرة في ESQL، ولحد هذا الحقل بس. الـ debugger أو Trace node بـ ${Body} بيجبر parsing للـ body كله

Complete وImmediate بيعملوا parse كامل بغض النظر عن الحقول المشار لها؛ الفرق لما validation مفعّل وعنصر ما يتحلش وقت الـ parse. الـ parse الكامل بسبب الـ debugger أو Trace ممكن يكشف أخطاء كانت مخفية. ممارسة جيدة: حلّل البيانات المطلوبة بس.

القيم الافتراضية والثابتة (default / fixed)

  • خاصية منطقية للعنصر (logical property)
  • ACE بيطبق القيم الافتراضية أو الثابتة بس لما يكون لازم لإنشاء bit stream قابل للـ parse
  • يحصل في رسايل CWF وTDS الـ fixed-length الخارجة
  • في صيغ تانية ممكن تحصل أخطاء validation غير متوقعة لعناصر ناقصة رغم وجود default أو fixed
  • ESQL ممكن يوفر القيم الافتراضية
  • أو استخدم ResetContentDescriptor لعمل serialize بالخصائص ثم reparse بالـ domain الموجود في خصائص الـ node

يعني لو عرّفت default في message set لكن الحقل ما اتحللش أثناء المعالجة، القيمة الافتراضية ما بتتطبقش. ResetContentDescriptor مفيد لو عايز تعيد التحليل ديناميكيًا، مثلًا بعض error handlers بتعيد تحليل الرسالة كـ BLOB لحفظها في ملف أو database أو queue بغض النظر عن أنواع البيانات.

تنظيم الـ message models

  • ACE بيوفر عزل وقت التشغيل: رؤية الـ resource محصورة في الـ application اللي هو فيه
  • استخدم applications لضمان إن تحديث مجموعة موارد منشورة ما يأثرش على مجموعة تانية
  • فكّر في shared libraries لمشاركة الـ models بين فرق ومشاريع وintegration nodes متعددة

تقدر تنشئ الـ models في applications أو libraries. لو الـ models بتتستخدم من applications كتير: اعملها في libraries وأشر لها وقت التشغيل. ولو عايز تحديث الـ model معزول: خزّنه في الـ application نفسه.

  1. الـ model مهم للـ parse والـ serialize والـ mapping والـ validation والـ versioning.

In IBM App Connect Enterprise, you can model data with DFDL. DFDL is an XML-based language that is used to define the structure of formatted data in a way that is independent from the data format itself. • DFDL is a language for describing data formats. A DFDL description allows data to be read from its physical format and to be presented as an instance of an information set (Infoset) or converted to the corresponding XML document. DFDL also allows data to be taken from an instance of an Infoset and written out to its physical format. • An XML schema is written for the logical model of the data. The schema is augmented with special DFDL annotations. These annotations are used to describe the physical representation of the data. This established approach is being used today in commercial systems. • DFDL uses W3C XML Schema Definition Language (XSDL) 1.0. • IBM App Connect Enterprise supports a DFDL domain. The DFDL domain can be used to parse and write a wide variety of message formats, and is primarily intended for non-XML message formats. • When reading a message, the DFDL parser interprets a bit stream by using grammar that is defined in a DFDL schema file, and generates a corresponding DFDL domain logical message tree in the integration node. When writing a message, the DFDL serializer generates a DFDL formatted bit stream from a DFDL domain logical message tree. • DFDL maps data from a non-XML representation to an instance of an information set. Think of this representation as a data transformation. However, DFDL is not intended to be a general transformation language and in particular, DFDL does not intend to provide a mechanism to map data to arbitrary XML models.

Do not parse an element opaquely in any of the following cases: • The message flow must access one of its child elements. • The message flow changes the namespace prefix in a way that affects the opaque element or one of its child elements and the element is copied to the output bit stream. • The element, or any child element, contains a reference to an internal entity that is defined in an inline DTD and the element is copied to the output bit stream. • The element contains child attributes that have default values that are defined in an inline DTD and the element is copied to the output bit stream.

Parse timing: الـ parsing مكلف. On demand (الافتراضي): يتحلل لحد أول حقل بتشير له في ESQL بس؛ ولو مفيش إشارة للمحتوى مبيتحللش أصلاً. Complete وImmediate بيحللوا الرسالة كلها (الفرق في توقيت اكتشاف الأخطاء). الـ debugger أو Trace node (${Body}) بيجبر الـ parse.

• An input message can be of any length. To improve the performance of message flows, a message is parsed only when necessary to resolve the reference to a particular part of its content. It is a good practice to parse only the data that is required to process a message. Parsers that use on-demand or partial parsing can help to reduce the amount of processor and memory that is needed at run time.

الـ validation بيتطبق على الرسايل المنمذجة والمنشورة بس، وبيشتغل مع on-demand أو complete parsing حسب إعدادات الـ node.
نص الكتاب الأصلي
