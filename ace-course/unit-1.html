ثانيًا: المشكلة اللي ACE بيحلها

Figure 1-7 و 1-10

أي شركة كبيرة عندها عشرات الأنظمة: نظام محاسبة، CRM، قاعدة بيانات، موقع، تطبيق موبايل، أجهزة، ملفات بتتبعت كل يوم. كل نظام بيتكلم «لغته»: ده بيبعت XML، ده بيستنى ملف نصي بعرض أعمدة ثابت، ده بيكلمك على طابور MQ، وده عن طريق HTTP.

لو وصّلت كل نظام بالتاني مباشرة (point to point) هتبقى عندك شبكة مسلوقة: كل ما تغيّر نظام واحد لازم تعدّل كل اللي بيكلمه. ده اللي الكتاب بيسميه «expensive coupling» يعني ارتباط غالي بين الأنظمة.

تشبيه بسيط

تخيل مطار كبير. لو كل شركة طيران عملت خط مباشر لكل مدينة بنفسها، هتبقى فوضى. الحل إن يبقى فيه مطار مركزي (hub) والكل بيتصل بيه (spokes). ده النمط اسمه hub-and-spoke، وACE هو الـ hub: كل نظام بيتصل بيه مرة واحدة بس، وهو اللي بيعرف يوصّل لأي حد.

ACE = برنامج وسيط (integration software). بياخد رسالة من نظام، يغيّرها لو لازم، ويوديها للنظام اللي محتاجها، «من أي حاجة لأي حاجة».

الكتاب بيوضح إن ACE (واللي قبله IIB) استُخدم تقليديًا كـ ESB: ناقل خدمات مركزي في الشركة. وفيه سطر مهم: «Point to point» معناه كود تكامل مكرر في كل تطبيق، أما «Hub and spoke» معناه connector قابل لإعادة الاستخدام وـ hub واحد للتكامل (Figure 1-7).

تحديث المعمارية: من ESB مركزي لتطبيقات مستقلة

Figure 1-8

في الإصدار V11، ACE اتغيّر عشان يشتغل كويس داخل الـ containers (زي Docker على Kubernetes). بدل ESB واحد ضخم، تقدر تقسّم التكاملات لتطبيقات صغيرة مستقلة (fine-grained integration)، وكل فريق يملك تكامله (decentralized ownership). الفايدة: تغيّر تكامل واحد بثقة من غير ما تعمل عدم استقرار في باقي التكاملات، وبتكبّر (scale) وترجع بسرعة.

  • Centralized ESB: كل حاجة في مكان واحد
  • Fine-grained integration: تكاملات صغيرة
  • Decentralized ownership: كل فريق مسؤول عن تكامله
  • Containerization: تشغيل داخل containers
  • Application autonomy: التطبيق مستقل
مصطلح
agile integration architecture: أسلوب بناء التكاملات كوحدات صغيرة مستقلة بدل الكتلة المركزية. الكتاب بيحيل لكتاب إلكتروني بنفس الاسم من IBM لو عايز تتوسع.

ثالثًا: ACE بيعمل إيه بالظبط؟

Figure 1-10 إلى 1-12

الكتاب بيوصف ACE بإنه بيوفر connectivity (توصيل) عبر الأنظمة والتطبيقات والبيانات. النقاط الأربعة الأساسية:

  • بيمنع إعادة كتابة الكود كل ما ييجي طلب تكامل جديد (avoid rewrites)
  • بيسهّل الصيانة لإنه بيقلل الارتباط الغالي بين الأنظمة (reduce coupling)
  • بيضيف مرونة لأن المرسل مش لازم يعرف مين المستقبل (anonymity بين producers وconsumers)
  • بيدّيك رؤية (insight) عن التطبيقات وقيمتها للشغل

إيه اللي ممكن يتوصّل بـ ACE؟

الكتاب بيعدد نقط النهاية (endpoints): تطبيقات جاهزة، web applications، أجهزة، برامج مخصصة. ومداخلها ومخارجها:

  • مراسلة (messaging): IBM MQ وJMS
  • بروتوكولات: TCP/IP وHTTP وFTP وSMTP
  • قواعد بيانات: DB2 وSQL Server
  • صيغ (formats): ملفات flat files، COBOL، XML، معايير الصناعة (SWIFT وEDI وHL7)، وصيغ يحددها المستخدم

الأفعال الأساسية اللي ACE بيعملها في الرسالة

الكتاب بيقول إنه فيه عمليات شاملة: route وfilter وtransform وenrich وmonitor وdistribute وdecompose وsequence وcorrelate وdetect. أهم تلاتة تفهمهم دلوقتي:

Route
يوجّه الرسالة لمكان معين حسب محتواها (مثلًا: لو المبلغ كبير يروح لفريق المراجعة)
Transform
يغيّر شكل البيانات (مثلًا من XML لـ JSON)
Enrich
يضيف معلومات للرسالة من مصدر تاني (مثلًا يجيب اسم العميل من قاعدة بيانات حسب رقمه)
Filter
يتجاهل رسايل معينة
Monitor
يراقب الرسايل ويعدّها ويسجّلها

كمان: تحويل بروتوكول النقل بين الطالب والخدمة (مثلًا الطالب بيبعت HTTP والخدمة بتستنى MQ)، والتعامل مع business events من مصادر مختلفة. التحويل بيتعمل بأربع طرق: graphical mapping، وJava، وESQL، وXSL.

وفيه publish/subscribe مع IBM MQ أو MQTT: نمط فيه ناس «بتنشر» رسايل على topic وناس تانية «مشتركة» بتستلمها من غير ما تعرف بعض.

تنبيه مهم عن الكلام ده
الكتاب كاتب إن ACE بيعمل «detect» و«correlate»، بس السؤال 3 في آخر الـ Unit بيوضح حدود: ACE مش أداة لعمل workflow طويل أو بإيدك (D مش من اللي يعمله). هنرجع للسؤال ده في الأسئلة.

مكونات وقت التشغيل (runtime components)

Figure 1-14
Integration node
المحرك اللي بيمرّر الرسائل ويحوّلها ويثريها. اسمه القديم integration broker. ممكن يبقى فيه أكتر من node على أجهزة مختلفة للحماية من الأعطال أو لفصل شغل الأقسام. على Windows هو service، على UNIX daemon، على z/OS started task.
Integration server
مجموعة مسماة من الـ message flows اتحطت على integration node. كل integration server هو process منفصل في نظام التشغيل، يعني بيئة تشغيل معزولة. لو واحد وقع، التاني مش بيتأثر.
Message flow application
بيوصف المسار اللي البيانات بتمشيه وإيه المعالجة اللي بتتعمل عليها بواسطة nodes. بيشاور على message models اللي بتوصف شكل البيانات.

تشبيه للتلاتة

فكّر في الـ integration node كأنه مصنع، والـ integration servers هي عنابر المصنع (كل عنبر معزول بحيطانه)، والـ message flows هي خطوط الإنتاج جوه العنبر. الرسالة هي المنتج اللي بيمشي على الخط.

الـ message flow بيتجه من التطبيق المصدر لتطبيق الوجهة. يعني الافتراض إن الوجهة عايزة ومستنية وبتتعامل مع كل الرسايل اللي بتتبعتلها.

خامسًا: أدوات المطور (Developer tools)

Figure 1-17 إلى 1-22

1) ACE Toolkit

Figure 1-18
  • بيئة تطوير متكاملة (IDE) مبنية على Eclipse
  • بتشتغل في perspective واحد لـ compiling وtesting وdeploying وfixing للـ message flows
  • بتتوصل بـ integration node أو أكتر
  • بتتوصل بمكتبات patterns عشان تبدأ بسرعة
  • بتشتغل على Windows وLinux على x86، وبتخزن في الـ file system المحلي

من الـ Toolkit تعمل: تعريف applications وmessage flows، تعريف واستيراد message definitions، deploy للـ node أو الـ server (on-premise أو لـ IBM App Connect على IBM Cloud)، تتحكم في log entries أثناء الـ deployment، وتبدأ وتوقف وتعمل trace للـ flows.

2) Web user interface

Figure 1-19

لوحة تحكم في المتصفح من غير برنامج إدارة إضافي:

  • تشوف وتدير الـ integration server resources: deploy لـ BAR files، stop وstart وdelete للـ applications
  • تشوف statistics وaccounting data للـ flows
  • تشوف موارد الـ servers
  • تشوف وتعيد تشغيل (replay) رسايل متسجلة
  • تبدأ وتوقف user trace وservice trace
  • تصدّر تعريف REST APIs المنشورة لـ IBM API Connect

ومعاها أدوات مراقبة أداء بتعرض throughput بشكل مرئي، وتبين elapsed time وCPU time، فتلاقي الاختناقات بسهولة.

3) Command utilities

Figure 1-20

أوامر بتتكتب من الـ command line. بعضها بيشتغل على نفس الجهاز اللي عليه الـ node بس، وبعضها عن بعد (remotely). ولو انت مش عندك صلاحيات قراءة وكتابة وتنفيذ على الـ node أو الـ server، هتبقى محدود. بعض الأوامر محتاجة إعدادات أمان إضافية. هنفصّلها في Unit 2.

4) Integration API

Figure 1-21

واجهة برمجة بلغة Java لإدارة ACE عن بعد. برنامجك يقدر يـ: يعمل deploy لـ BAR، يغيّر خصائص الـ node، ينشئ ويعدّل ويحذف integration servers، يسأل عن حالة الـ node والـ servers والـ flows والملفات المنشورة، ويتبلّغ لما الحالة تتغير، وكمان ينشئ ويعدّل message flow applications. حتى الـ Toolkit نفسه بيستخدمها.

5) ACE في الـ Cloud

Figure 1-22

خدمة مُدارة بالكامل على IBM Cloud. بتستخدم نفس الأدوات، والأصول اللي تتعمل ممكن تتنشر في أي بيئة (cloud أو on-premise) ضمن حدود الـ cloud.

أنماط التشغيل (operation modes)

Figure 1-24

النمط بيتحدد حسب الرخصة اللي اشتريتها. الجدول في الكتاب:

Developer
كل الميزات شغالة بس للتجربة والتطوير والاختبار. integration server واحد. معدل الرسايل محدود برسالة (transaction) واحدة في الثانية على مستوى الـ flow.
Non-production
كل الميزات شغالة بدون حدود وظيفية، بس للتقييم والتطوير والاختبار فقط. عدد servers غير محدود.
Standard
كل الميزات شغالة. لو بتستخدم integration node تربط معاه integration server واحد بس، وعدد الـ flows اللي تنشرها غير محدود.
Advanced
كل الميزات شغالة بدون أي قيود. ده الافتراضي إلا لو معاك Developer Edition.
لازم تعرف
لو اشتريت الباقة الكاملة أو Standard Edition، الـ integration servers بتتعمل تلقائيًا بنمط advanced إلا لو حددت النمط الصح لرخصتك. انت مسؤول إن السيرفرات تشتغل بالنمط اللي اشتريت رخصته.

Figure 1-14 IBM App Connect Enterprise runtime components

ده أهم شكل في الـ Unit. Integration node (اسمه القديم broker) هو المحرك اللي بيوجّه ويحوّل ويثري الرسايل اللي بتمر. بيتعمل على Windows كـ service وعلى UNIX كـ daemon. ممكن يبقى عندك أكتر من node على أجهزة مختلفة للحماية من الأعطال أو لفصل الشغل. جوه الـ node فيه Integration servers: كل server عبارة عن process مستقل في نظام التشغيل، فيه مجموعة message flows متنشرة. لو server وقع، التانيين مش بيتأثروا (isolation). والـ Message flow هو اللي بيحدد تسلسل العمليات على الرسالة، من التطبيق المصدر للوجهة.
نص الكتاب الأصلي
• The runtime engine of IBM App Connect Enterprise is the integration node, also known as the integration broker. The integration node routes, transforms, and enriches in-flight messages based on the message flows and message models. • You can create integration nodes on every operating system that IBM App Connect Enterprise supports. An integration node is a system service on Windows, a daemon process on UNIX, or a started task on z/OS. It controls processes that run message flows. • There can be many integration nodes, and each can be running on a different system. This architecture provides protection against failure, and can separate work across different divisions in a business. • An integration server is a named grouping of message flows that are assigned to an integration node. Each integration server is started as a separate operating system process, providing an isolated runtime environment for a set of deployed message flows. • In IBM App Connect Enterprise, the message flow defines the sequence of operations on a message. The actions are defined in terms of the message format, its content, and the results of individual actions along the message flow as determined by the message flow processing nodes and connections. A message flow can route messages from a sender to a recipient based on the content of the message. The direction of the flow is from the source application to the destination application. In other words, it is assumed that the destination wants, expects, and handles all messages sent to it.

Figure 1-37 IBM App Connect Enterprise runtime security

الأمان وقت التشغيل: لما الرسالة توصل لـ input node، الـ security profile بيحدد إيه اللي بيتعمل من authentication وauthorization وmapping للهوية. فتقدر تتحكم مين مسموح له يبعت رسالة للـ flow، وتكمل المعالجة باسم هوية الرسالة.
نص الكتاب الأصلي
• Security is an important consideration for both developers of IBM App Connect Enterprise applications, and for system administrators that are configuring IBM App Connect Enterprise authorities. • When you are designing an IBM App Connect Enterprise application, it is important to consider the security measures that are needed to protect the information in the system. When a message arrives at an input node, a security profile is used to indicate whether runtime security is configured. • The security manager of the integration node is called to read the security profile. The security profile specifies the combination of authentication, authorization, and mapping that is done with the identity of the message, and by what external security provider. • At subsequent processing nodes in the message flow, it might be necessary for an identity to be used to access a resource such as a database. The identity that is used to access such a resource continues to be a proxy identity, either the identity of the integration nodes, or an identity that is configured by using a command. The resource is accessed by using the appropriate proxy identity. • Two external security providers are supported so that the integration node can participate in a centralized security framework: LDAP for authentication and authorization and Tivoli Federated Identity Manager for authentication, mapping, and authorization.
