الـ Flow exerciser

  1. تنشئ وتبعت رسالة لـ input node الـ flow
  2. يظلل مسار الرسالة في الـ flow وأي subflows مرتبطة
  3. يعرض محتوى الـ logical message tree للرسالة اللي عدّت من connection
  4. يحفظ محتوى الشجرة كـ recorded message ممكن تبعتها للـ flow بعدين

تقدر تبعت رسايل للـ flow بالـ Flow Exerciser أو بعميل خارجي زي RfhUtil، وبعدين تستخدم الـ Flow Exerciser لعرض مسار كل رسالة.

التعامل مع الأخطاء في الـ flows

الـ integration node بيوفر error handling أساسي لكل الـ flows. لو مش كفاية وعايز تتصرف في حالات معينة، تستخدم terminals الـ nodes لعمل معالجتك. أمثلة: flow بيتوقع أخطاء معينة وعايز يعالجها بطريقة معينة، أو flow بيحدّث database ولازم يعمل rollback لو باقي المعالجة ما اكتملتش. ما فيش إجراءات ثابتة: لازم تقرر التوليفة المناسبة لكل حالة.

Basic error handling

  1. لو الـ Failure terminal للـ node اللي حصل فيه الخطأ موصول: الرسالة بتتبعت مع الـ Exception List
  2. لو مش موصول: بيتم throw exception ويرجع التحكم لـ Input node
  3. لو الـ Catch terminal على الـ Input node موصول: الرسالة بتتبعت مع Exception List
  4. لو مش موصول: معالجة افتراضية حسب نوع الـ input node (مثلًا لو بيدعم Transaction mode: لو الرسالة مش transactional بتتجاهل، وإلا rollback للـ input queue والـ flow يبدأ تاني، والمحاولة التانية ممكن تفشل برضه)

طريقتين لمعالجة الأخطاء

1. Failure checking
وصّل Failure terminal للـ node عشان تفحص صراحة أي أخطاء جواه. لو حصل خطأ، exception list بتتبعت لـ Failure terminal، والرسالة اللي في الطريق (in-flight) بتفضل زي ما كانت قبل ما الـ node يتنادى. تقدر تعمل فحص أخص في الـ nodes اللي بتتخصص بـ ESQL (مثلًا exit handlers)
2. Catching exceptions
لو ما وصلتش Failure، الفشل بيتحول لـ exception بتتطلع من الـ node. تقدر تمنع rollback للـ transaction وتتحكم في مدى التراجع عن تغييرات الرسالة بإضافة TryCatch node

معظم الـ nodes فيها Catch terminal، وغالبًا هي اللي في بداية transaction (حيث exception غير ممسوكة بتسبب rollback). في الـ nodes دي الـ Catch terminal بيتصرف كأن TryCatch node موصول بـ Out مباشرة. استخدم Catch terminal لمعالجة الاستثناءات اللي بتحصل بعد الـ node، ووصّل Failure لمعالجة الأخطاء داخل الـ node نفسه.

عوامل نتيجة الـ flow

  • Failure وCatch terminals الموصولة
  • نوع الـ input node
  • خاصية Transaction mode على بعض الـ input nodes: تحدد هل باقي الـ nodes تشتغل تحت sync point
Automatic
تحت sync point لو الرسالة persistent، وإلا لأ. لو فشل: بتتجاهل بس لو non-persistent
Yes
تحت sync point. لو فشل ممكن rollback بغض النظر عن الـ persistence
No
مش تحت sync point. لو فشل الرسالة تتجاهل بغض النظر عن الـ persistence

الـ ExceptionList

  • بيحتوي معلومات عن الاستثناءات اللي حصلت لما الرسالة اتمسكت في local Failure path أو Catch path
  • ممكن تقراه وتعدله وتعمله trace
  • جزء من الـ logical message tree
  • بيتكون من صفر أو أكتر من exception descriptions
  • أعمق ابن (innermost child) هو السبب الأصلي للخطأ

مثال الكتاب: ثلاث RecoverableException متداخلة، وأعمق واحدة فيها: Label = mf1.Compute1، Text = Divide by zero calculating ... ، Catalog = App Connect Enterprise، Severity = 2، Number = 2450، وInsert Type = 5 وText = 100 /0. في معظم الحالات المعلومة المهمة في آخر (أعمق) structure.

خيارات الإمساك بالاستثناءات

  • وصّل Failure terminal بتسلسل nodes يعالج الاستثناء الداخلي للـ node
  • وصّل Catch terminal بتسلسل يعالج الاستثناءات اللي بتتولد بعده
  • حط TryCatch nodes في نقط محددة
  • استخدم Throw node لتوليد exception
  • تأكد إن كل الرسايل اللي بتدخل MQInput: كلها transactional أو كلها لأ، وكلها persistent أو كلها لأ

مثال: وصّل Failure terminal بـ subflow يعالج رسالة الخطأ في ExceptionList ويبعت email لمسؤول.

القسم 8.2: TryCatch node

  • افتراضيًا أي runtime exception بيرجع التحكم لـ input node
  • TryCatch بيتحكم في الأخطاء محليًا
  • له input واحد وoutputين: Try وCatch
  • الرسالة بتتبعت لفرع Try وتكمل للآخر إلا لو حصل exception
  • بيعمل كنقطة قرار ولا يعدل الرسالة

لو حصل exception في فرع Try:

  • الـ integration node بيحدّث ExceptionList
  • معلومات ExceptionList الموجودة بتتكتب في local error log
  • Root وLocalEnvironment بيرجعوا لحالتهم عند بداية TryCatch
  • أي تغييرات في database أو MQPUTs في فرع Try ما بتتلغيش (not undone)
  • بيدخل فرع Catch، ولو مش موصول يرجع التحكم لـ Input node

معلومات نوع الاستثناء في ExceptionList، فتقدر تستخدمها في الـ nodes اللي بعده: تفلتر على نوع الاستثناء، أو تحدّث حقل بمعلومات الخطأ، أو تكتب ExceptionList في database.

استخدم TryCatch بحذر
لو تحديث database جزء من الـ transaction وحطيت TryCatch، تحديث الـ database في Try path بيفضل يحصل. لازم تعمل backout يدويًا بعد كده أو تحط Throw node في Catch path لفرض rollback مضبوط.

سلوك الخطأ مع TryCatch

  1. لو Failure terminal للـ node اللي حصل فيه الخطأ موصول: الرسالة تتبعت منه، والتشخيص في ExceptionList
  2. لو مش موصول: exception بتتولد وتترمى ناحية الـ input node
  3. لو في الطريق قابلت TryCatch: التحكم يروح Catch terminal، وRoot وLocalEnvironment يرجعوا لقيمهم قبل TryCatch. تقدر تشير لـ ExceptionList بـ ESQL
  4. لو ما فيش TryCatch، الـ exception توصل الـ input node. لو Catch terminal موصول: الرسالة تتبعت له، وExceptionList متاحة، وRoot وLocalEnvironment يرجعوا للقيم الابتدائية
  5. لو مش موصول: بتتفحص حالة الـ transaction. لو مش transactional الرسالة بتتجاهل (ده مش موثق صراحة، وفي system log معلومات عن الخطأ الأصلي بس). وبعد كده المعالجة بتعتمد على نوع الـ input node

إلقاء وتسجيل الاستثناءات بشكل متحكم فيه

  • Throw node عادةً بيتوصل في آخر Catch path
  • دالة ESQL THROW: توقف المعالجة في Compute node وتعالج أخطاء database صراحة
  • أكواد الـ database ممكن تتجاب بدوال ESQL لو الخاصية المتقدمة Throw exception on database error مش مختارة
THROW USER EXCEPTION
  CATALOG 'BIPv610' MESSAGE 2950 VALUES(
    'SQL State:', SQLSTATE,
    SQLCODE, SQLNATIVEERROR, SQLERRORTEXT);

الـ Throw node له input واحد ومفيش output. حطه آخر node في Catch path لرمي user-defined exception. تقدر تظبطه ليطلّع معلومات تشخيص معينة للـ system log أو ExceptionList. نفس السلوك بدالة ESQL THROW في Compute أو Filter أو Database nodes. حالة الـ database ممكن تتجاب بدوال ESQL بس لو Compute وDatabase nodes مظبوطين صراحة ما يرموش exceptions على أخطاء database. للأخطاء التشخيصية تقدر تستخدم message catalog اللي جاي مع ACE أو تبني catalog خاص بيك.

في JavaCompute node مش لازم تمسك الاستثناءات: الـ integration node بيعالجها تلقائيًا. لو مسكتها في الكود ارمها تاني ليبني exception list ويبعت الرسالة لـ Failure terminal لو موصول. للأخطاء الخاصة بالتطبيق استخدم class اسمه MbService اللي فيه logError() وlogWarning() وlogInformation() للكتابة في event log أو syslog. نص الرسالة في Java resource bundles.

مثال TryCatch

flow فيه TryCatch node بفرع Try وفرع Catch موصولين. كل التغييرات اللي حصلت على الـ logical message في فرع Try بتتصفّر لما الاستثناء يتمسك، لكن أي database updates أو MQPut calls حصلت قبل الاستثناء مش بتتراجع. لفرض rollback لازم ترمي exception صراحة في فرع Catch. ساعتها ترتيب المعالجة مهم، فاستخدم FlowOrder node (First وSecond) لفرض الترتيب.

نصايح للأخطاء

  • الـ flows بتشتغل زي logic diagrams: فكّر في كل النتايج الممكنة
  • الرسايل بتتجاهل عند الخطأ في flows non-transactional لو: Failure terminal للـ node اللي حصل فيه الخطأ مش موصول، أو Catch terminal للـ input node مش موصول أو حصل خطأ تاني
  • افهم سلوك الـ nodes: السلوك الافتراضي مش دايمًا زي ما تتوقع
  • لو هتعتمد على السلوك الافتراضي (سيبت terminals من غير توصيل) اتأكد إنك فاهمه

القسم 8.3: Logs

Local error log (syslog)

  • أكتر من رسالة لكل runtime error، لازم تراجعهم كلهم
  • بيعرض: حالة الـ integration node، وأخطاء وقت التشغيل، وبعض أخطاء الـ database
  • افحصه دايمًا بعد تشغيل النظام وبعد النشر وأثناء اختبار الـ flows
Windows
Event Viewer > Application log (Administrative Tools > Event Viewer > Windows Logs > Application). ممكن يبقى فيه أكتر من رسالة للخطأ الواحد وكل واحدة بتفصّل
UNIX / Linux
مكانه حسب entry في /etc/syslog.conf. لازم يتظبط صراحة، ويحتوي أول سطر من الرسالة بس. باقي الرسالة تتشوف في Knowledge Center
z/OS
address space job log وz/OS SYSLOG

الـ local error log هو المصدر الأول لمعلومات problem determination لمكونات ACE والـ flows، فيه كل الأخطاء والتحذيرات. أخطاء ممكن تحصل كمان في تطبيقات تانية زي DB2 وIBM MQ. افحصه بانتظام: الأخطاء ممكن تملّاه لو ما تصرفتش.

Activity logs

  • راجعها كواحدة من أول نقط التحقيق لما يحصل شيء غير متوقع
  • مفعّلة افتراضيًا
  • بتدي معلومات فورية وأساسية عن اللي بيحصل في الـ flows وتفاعلها مع الموارد الخارجية. مثلًا ليه الـ flow مش بيعالج رسايل من مورد بعيد
  • للاستخدام الطويل ممكن تكتبها في ملف
  • ممكن تتولد لـ flows معينة أو أنواع موارد. وتتحفظ كـ CSV أو تنسخ جزء منها

لأنها مفعّلة افتراضيًا، بتدي إشارة مبكرة لتغير السلوك مثل انقطاع الاتصال بمورد خارجي.

كتابة Activity logs في ملفات

عرّف ActivityLog policy. في الـ Toolkit: File > New > Policy، واختار Policy Project وادخل اسم الـ policy واضغط Finish. تقدر تحدد في الـ policy:

  • هل الـ file logging شغال
  • أقصى عدد ملفات لكل log
  • أقصى حجم للملف قبل التدوير
  • أقصى عمر للملف قبل التدوير
  • فلاتر لمحتوى الـ logs
  • مستويات severity
  • مسار واسم الملف
  • هل الرسايل تتنسق بالـ inserts داخل النص
ترقية

Logs تانية

  • Eclipse log: أخطاء الـ Toolkit والـ plug-ins. من Plug-in Development perspective: Window > Show view > Other > General > Error Log. الأخطاء بتظهر في Problems view
  • TDS log: أخطاء رسايل tagged/delimited. قواعد TDS بتتفحص وقت النشر، وبتظهر BIP1836 في الـ Toolkit، والتفاصيل في TDS.log في install_dir/log

القسم 8.4: User trace

لو الـ logs ما فيهاش معلومات كفاية، الخطوة اللي بعدها هي الـ trace. الـ trace بيعطي تفاصيل أكتر عما يحصل أثناء تشغيل الكود، وبيتبعت لـ trace record معين عشان انت أو IBM support تحللوه. نوعين: user trace وservice trace.

User trace
عادةً لـ debug تطبيقاتك: ممكن تعمل trace لـ integration nodes وintegration servers والـ message flows المنشورة
Service trace
trace أشمل للـ integration node، وبيتتبع تنفيذ كل الأوامر
الأداء
لما تبدأ trace، بتتسبب في معالجة إضافية لكل نشاط في المكوّن، وبيتولد حجم بيانات كبير، فتوقع تأثير على الأداء. قلّله باختيار اللي تعمل له trace وتحديد وقت التشغيل.

User trace بالتفصيل

  • بيسجل كل أنشطة الـ flow: الأداة القياسية لتحليل الـ flows
  • بيساعد في فهم الأنشطة وإيجاد مشاكل الـ parser والـ modeling
  • بيعرض كل الاستثناءات في stack بنصوصها الكاملة ومدخلاتها (inserts). الاستثناءات غالبًا أطول من سطر وبتيجي في مجموعات من اتنين أو تلاتة
  • بعض الـ parsers بتطلع رسايل user trace أثناء الـ parsing
Normal
بيتتبع الأحداث اللي بتأثر على الكائنات اللي بتنشئها وتمسحها (مثل nodes)
Debug
بيتتبع بداية ونهاية العملية ويراقب الكائنات المتأثرة
None
بيقفل user trace

  • في الـ Toolkit: كليك يمين على الـ server > Trace > Start user trace

الـ Trace node

  • بيدي snapshot من (جزء من) logical message
  • الوجهة: ملف أو User Trace log أو local system error log
  • المحتوى: نص من تحديدك ومحتوى الرسالة ومعلومات التاريخ والوقت
  • ممكن تشغّله وتطفيه (on/off)

ممكن تحسّن أداء flow فيه Trace nodes كتير بإطفائها. لو الـ flow بيعالج رسايل كبيرة اتفحص أجزاء صغيرة بالـ Trace node. ممكن تحطه في أي نقطة. لو اخترت الكتابة في ملف، الملف نص مقروء بسهولة.

ضبط الـ Trace node

  • خاصية Pattern هي ESQL pattern بيحدد المعلومات المكتوبة
  • النص العادي بيتنسخ زي ما هو
  • لتحديد أجزاء من الرسالة اكتب مسارها بين ${ و }. مثال: my_text ${ESQL-expression}
  • لتسجيل الرسالة كلها: ${Root}
  • ممكن تستخدم دوال ESQL زي CURRENT_DATE
  • مفعّل افتراضيًا
mqsichangetrace IntNode -e IntServer -n [on|off] [-f flow -k application]

تتحكم في الـ Trace nodes بالأمر ده أو بالـ web UI أو بخصائص server.conf.yaml، على مستوى الـ flow أو الـ integration server. لو إعداد الـ Trace node للـ integration server = off فكل الـ Trace nodes في كل الـ flows بتتطفي.

القسم 8.5: الضبط بملفات YAML

  • لما تنشئ integration node بيتنشأ تلقائيًا node.conf.yaml افتراضي
  • تقدر تضبط عمل الـ node والموارد بتعديل الخصائص فيه
  • بيتنشأ كمان overrides subdirectory فيه node.conf.yaml تاني فيه قيم الخصائص اللي بتتضبط بأوامر ACE (زي mqsicreatebroker)، وبتلغي أي قيم لنفس الخصائص في الملف الأساسي
  • لما تنشئ integration servers تابعة للـ node، بيتنشأ server.conf.yaml لكل واحد
  • خصائص node.conf.yaml بتتورث للـ integration servers، لكن تقدر تغير أي خاصية في server.conf.yaml
ليه؟
المنتج اتبنى على أسلوب unzip-and-go الأنسب للـ containers، فمهام ضبط كتير كانت محتاجة سكربتات أوامر بقت أسهل بتعديل node.conf.yaml وserver.conf.yaml.

ضبط الـ server

  • تضبط الـ integration server بتعديل server.conf.yaml
  • مكان الملف بيعتمد على: integration server مستقل أو تحت integration node
  • لو استخدمت أوامر تعدّل الـ server بيتنشأ overrides directory تحت working directory فيه server.conf.yaml: <work directory>/overrides/server.conf.yaml
  • قيم الـ overrides بتلغي القيم في <work directory>/server.conf.yaml

تعديل ملف YAML

  1. افتح الملف بـ YAML editor. لو ما معاكش، استخدم plain text editor لكن تأكد إنك مش بتحط tab characters لأن YAML ما بيقبلهاش
  2. عدّل الخصائص المطلوبة
  3. اعمل restart. الخصائص تسري لما الـ node أو الـ server يتعاد تشغيله، وكل تعديل جديد يحتاج restart

  • لكن Toolkit واحد بس يقدر يعمل debug لـ integration server واحد في نفس الوقت

Figure 8-56 Integrated Help

Integrated Help: دوس F1 (Windows) أو Shift+F1 (Linux) أو Help > Dynamic Help. بيعرض وصف العنصر اللي اخترته (view أو node) ومواضيع مرتبطة.
نص الكتاب الأصلي
• A Help view is provided in the IBM App Connect Enterprise Toolkit. To view the Help view, press F1 in Windows, press SHIFT+F1 in Linux, or click Help > Dynamic Help in the IBM App Connect Enterprise Toolkit. • The default view for Help contains Related Topics. In the top section, there is a small description of the interface element (such as a view) or an object (such as a node) that you last selected with the mouse. This description also contains links to topics in the IBM Knowledge Center. Click a link to open any topic in the Help view. Right-click the topic link and click Open in Help Contents to open the topic in the IBM Knowledge Center. The topic Help opens in a separate window. • The bottom section of the Help View contains relevant links from the IBM Knowledge Center. These links are generated by using a search on the values of the perspective you are in and the name of the interface element that you selected. • Context-sensitive help is also available for node properties, as indicated by the “Information” icon.

You can right-click the link to a topic and click Open in Help Contents to open the topic in the IBM Knowledge Center.
