القسم 12.1: JMS

Java Message Service (JMS)

  • API لـ messaging بلغة Java مستقل عن الـ vendor
  • Oracle بتملك المواصفة، وبتتدار من Java Community Process، وIBM ضمن الـ expert group
  • بيضمن provider independence لكن مش interoperability
  • بيدعم point-to-point وpublish/subscribe
  • تسليم الرسايل asynchronous
  • الـ API ما بيحددش wire protocol
  • مفيهوش security
  • بيدعم transactions

JMS ما بيحددش غير واجهة البرمجة. تحديدًا ما بيحددش شكل البيانات على السلك بين تطبيقات بعيدة، يعني مش بيحدد إزاي JMS providers مختلفة تتواصل مع بعض (إلا على مستوى الـ API).

معمارية JMS

  • JMS client: برنامج Java بينتج ويستهلك رسايل بـ JMS
  • Messaging provider: نظام الـ messaging المؤسسي، مثلًا IBM MQ
  • Message: الـ object اللي بينقل المعلومات بين الـ client والـ provider
  • Administered objects (Connection Factory وDestination): objects جاهزة بيعملها administrator لاستخدام الـ clients

JNDI امتداد Java قياسي بيوفر API موحد للوصول لخدمات الـ naming والـ directory. الـ JMS clients بتستخدم JNDI لتصفح naming service وتجيب references للـ administered objects (connection factory وdestination، والـ destinations هي topics وqueues). الـ JMS client بيحدد JNDI InitialContext للاتصال، وهو نقطة البداية في أي JNDI lookup (زي root في file system). خصائص الـ InitialContext بتتحدد حسب الـ directory service المستخدم.

دعم ACE لـ JMS

  • بيدعم JMS API وفيه message processing nodes للتفاعل مع JMS
  • JMS Transport service بيوصّل التطبيقات اللي بتستقبل من JMS destination (في أول الـ flow أو في النص) أو بتنشئ رسالة لـ JMS destination
  • بيدعم أي JMS provider متوافق مع JMS 1.1 أو 2.0، منهم IBM MQ وWebSphere Application Server

المميزات: JMS input وoutput nodes، وnodes تحويل JMS من وإلى IBM MQ، وJMS domains لـ parsing وserialization، وJMS activity logs، ورسايل JMS بـ syncpoint coordination كجزء من XA coordinated transaction.

الـ JMS nodes

  • تخلي ACE يشتغل كـ JMS client لـ JMS provider (point-to-point وpublish/subscribe)
  • تضيف قيمة brokering لشبكة JMS: routing وtransformation
  • تبسط معالجة JMS
  • توصل شبكة JMS بشبكة IBM MQ موجودة (inbound وoutbound، وتشمل IBM MQ publish/subscribe)
  • تحول JMS message tree من وإلى IBM MQ message tree

الـ nodes بتتصرف كـ JMS clients لما ترسل وتستقبل. وبتشتغل مع IBM MQ JMS provider وWebSphere Application Server وأي provider متوافق مع JMS 1.1 أو 2.0. في ACE الـ policies هي اللي بتعرف الاتصال بـ JMS providers.

إتاحة JMS provider client للـ JMS nodes

  • استخدم JMS Providers policy لضبط تفاصيل الاتصال على الـ flows
  • فيه templates لأنواع مختلفة من providers
  • الأمر mqsicreateconfigurableservice deprecated في ACE ومتوفر كأداة ترحيل عشان السكربتات القديمة من IBM Integration Bus تفضل تشتغل (بتنشئ policy)

JMSInput node

  • بيستقبل رسايل من JMS destinations عن طريق اتصال بـ JMS provider
  • بيستقبل ويبعت الرسايل بـ JMS message tree
  • لما بيستقبل topics للـ publications، بيحدد داخليًا خاصية Additional Instances بصفر عشان يمنع استقبال publications مكررة

الـ node بيشتغل كـ JMS message consumer وبيستقبل الأنواع الستة اللي حددتها مواصفة JMS. موجود في JMS drawer في الـ palette.

Parsing الـ JMS payload

  • JMS domains لنمذجة الرسايل من JMS 1.1 أو 2.0
  • استخدم JMSMap domain مع MapMessage
  • استخدم JMSStream domain مع StreamMessage
  • BytesMessage وTextMessage وObjectMessage: الـ payload بيتمرر كـ bit stream لـ parser
  • MapMessage وStreamMessage: الـ payload بيتستخرج كعناصر منفردة بس

ObjectMessage: الـ node بينادي getObject() ويرجع object بعد deserialization من الـ class الأصلي. تعريف الـ class لازم يتاح للـ node عن طريق Java class path بتاع الـ integration node. بعدين بينادي BLOB parser اللي بيعمل الـ body من bit stream مبني من الـ object. الـ Java object ممكن يتعمل له reserialize في JavaCompute node ويتعدل بـ method calls.

JMSMap مرادف لـ XML parser بتاع الـ integration node، اللي بيتوقع stream من XML، لكن MapMessage بتتستخرج كأزواج name-value بـ JMS API. الـ node بيضيف كل زوج كـ XML element مع قيمته ويحافظ على نوع القيمة بـ attribute اسمه dt=. البيانات ما بترجعش بنفس ترتيب استقبالها. StreamMessage: سلسلة حقول لكل حقل نوع بدون اسم، فالـ node بيستخدم اسم element افتراضي elt لكل XML element، ويستخرج الحقول فرادى ويضيفها لـ bit stream بصيغة XML.

الـ JMS message tree

شجرة JMS خاصة بتدي رؤية JMS للرسالة. مع Properties وBody القياسيين، فيه JMSTransport folder فيه معلومات خاصة بالرسالة، بعناصر مألوفة لمطور JMS. الشجرة نفس الشكل بغض النظر عن الـ provider.

Message_MetaData
معلومات عن payload type للرسالة. الـ JMSOutput node بيستخدمه
Header_Values
قيم الـ JMS message headers (إلى أو من الرسالة)، كأزواج name-value (مثل JMSDestination وJMSDeliveryMode وJMSExpiration وJMSTimeStamp وJMSMessageID وJMSCorrelationID وJMSReplyTo وJMSType وJMSRedelivered)
Application_Properties
folder اختياري بمعلومات خاصة بالتطبيق، مثلًا معلومات context محفوظة من رسالة الإدخال (correlation ID وReplyTo)
Provider_Properties
معلومات خاصة بالـ JMS provider المستخدم. الـ client أو الـ provider ممكن يحطها. أسماؤها تبدأ بـ JMS_ ثم اسم الـ vendor، مثلًا IBM MQ JMS client بيحط JMS_IBM_MsgType
Standard_Properties
بيحطها الـ provider لما يرسل. أسماؤها تبدأ بـ JMSX، مثل JMSXUserID وJMSXAppID وJMSXDeliveryCount وJMSXGroupID وJMSGroupSeq. الـ vendor يختار يدعم أي منها أو بعضها أو كلها

الـ domains اللي ممكن تبقى Body: DFDL وXMLNS وXMLNSC وJSON وBLOB وMIME وMRM وJMSMap وJMSStream. الـ JMS message processing nodes المختلفة بتستخدم بعض أو كل folders في JMSTransport حسب عملياتها.

JMSOutput node

  • بيبعت رسايل لـ JMS destinations
  • بيشتغل كـ message producer
  • بيبعت datagram يحمل معلومات كفاية للتوجيه من المصدر للوجهة
  • أو reply message يتوجه حسب JMSReplyTo في الـ request
  • أو request message لـ JMS destination مع توقع رد من الـ consumer
  • لو الـ flow مفيهوش JMSInput node، بيتضاف MQJMSTransform node لتحويل الرسالة للشكل اللي بيتوقعه JMSOutput

الـ node بيشتغل كـ JMS message producer وبينشر الأنواع الستة. في الـ JMS message tree، حقل PayloadType في Message_MetaData بيمثل نوع الرسالة. للتحكم في نوع JMS message اللي ينشئها JMSOutput استخدم ESQL لضبط PayloadType:

SET OutputRoot.JMSTransport.Transport_Folders.Message_MetaData.PayloadType = <payload value>;

Serialization للـ JMS output message

  • لما JMSOutput node يستقبل رسالة JMS بينادي JMSTransport parser اللي يرجع XML bit stream فيه JMSTransport folder بتاع الـ message assembly
  • بياخد payload type من Message_MetaData عشان يحدد نوع JMS message
  • بيملّي الـ JMS header data من الـ XML
  • بيملّي قيم الـ properties من الـ XML، بما فيها descriptors اللي بتحدد نوع Java object لكل property
  • الـ payload بيتاخد كـ bit string وبينادي JMS API methods لعرض حقول الرسالة

TextMessage وBytesMessage: الـ bit stream بيتمرر مباشرة لـ JMS API. MapMessage وStreamMessage: لازم تتستخرج العناصر المنفردة من XML bit stream. ObjectMessage: الـ node بيعمل reserialize للـ payload باستخدام الـ object class. وده نفس الطريقة لـ JMSReply node.

JMSReceive node

  • بيستقبل رسايل من JMS destinations
  • زي JMSInput لكن ممكن يتستخدم في نص الـ flow
  • شجرة الـ output بتدمج شجرة الإدخال (على In terminal) مع شجرة النتيجة من الرسالة المستقبلة
Output Data Location
فين في شجرة الـ output تحط القيمة المحددة في Result Data Location. الإدخال بيتنسخ للـ output الأول وبعدين النتيجة تتنسخ للمكان المحدد. الافتراضي $OutputRoot بيستبدل الشجرة المنسوخة ببيانات الـ provider، فما بيبعتش رسالة الإدخال. ممكن ESQL أو XPath expression
Result Data Location
أنهي جزء من الشجرة المستقبلة من JMS provider تتنسخ لـ Output Data Location. الافتراضي $ResultRoot بيحط الرسالة الناتجة كاملة. ممكن ESQL أو XPath expression

مثال الكتاب: لو Output Data Location = $OutputRoot/XMLNSC/JMSRecvMsg وResult Data Location = $ResultRoot/JMSMap، بعد استقبال الرسالة الـ node بينسخ الجزء المحدد بـ $ResultRoot/JMSMap لمكان $OutputRoot/XMLNSC/JMSRecvMsg في الـ message assembly.

JMSReply node

  • بيبعت رسالة لـ JMS destination المحددة في JMSReplyTo header
  • شبه JMSOutput لكن بيبعت لـ JMSReplyTo destination بس
  • شبه MQOutput: الـ output (JMSReplyTo) destination ممكن تكون list

الفرق الأساسي: JMSOutput تقدر تحدد فيه وجهات بقيم تانية (منها أماكن في message tree)، لكن JMSReply بس لـ JMSReplyTo.

JMS transformation nodes

JMSHeader
بيضبط أو يعدل محتوى Header_Values وApplication_properties في شجرة JMS، بقيم جاهزة أو من المستخدم أو XPath expressions. وفي Application_Properties بتضيف أو تعدل أو تحذف أزواج name-value
JMSMQTransform
بيحول رسالة فيها JMS message tree لرسالة متوافقة مع الـ IBM MQ JMS provider
MQJMSTransform
العكس: بيحول رسالة بصيغة IBM MQ JMS provider لرسالة فيها JMS headers تتبعت لـ JMS destinations

الـ 3 nodes دي helper nodes بتقلل الكود: تعدل header values من غير compute-type node. تفاصيل الحقول اللي بتتعمل لها map في IBM Knowledge Center.

JMS transactional processing

  • syncpoint coordination مع flows بتستقبل JMS في JMSInput، أو بتبعت في JMSOutput، كجزء من XA coordinated transaction
  • JMS nodes لازم تكون متصلة وفي session مع JMS provider
  • أي input node في الـ flow ممكن يبلغ الـ syncpoint coordinator الخارجي ببداية ونهاية الـ transaction وهل commit أو rollback
  • الـ coordinator بيبعت طلبات XA/Open compliant لكل resource managers المشاركين يستعدوا (prepare)، وبعدها التغييرات تتعمل commit أو rollback
  • Resource managers (IBM MQ وDB2 وأي XA-compliant JMS provider) ممكن يشاركوا

بتفرض transactional control بـ XA-compliant transaction coordinator. تفاصيل التحكم واسترجاع in-doubt transactions خاصة بالـ transaction manager المستخدم.

تأمين الـ JMS message flows

تقدر تأمّن اتصالات JMS أو JNDI bindings lookups أو الاتنين.

  • لتأمين اتصالات JMS: حدد خاصية Connection Factory Name على كل node في الـ flow بيستخدم JMS transport، واستخدم mqsisetdbparms لتفويض user ID وpassword للـ connection factory
  • لتأمين JNDI: حدد خاصية Initial Context Factory على كل node، واستخدم mqsisetdbparms لتفويض user ID وpassword للـ context factory
mqsisetdbparms nodename -n jms::connectionFactoryName -u userid -p password
mqsisetdbparms nodename -n jndi::initialContextFactoryName -u userid -p password

بديل لـ mqsisetdbparms: الأمر mqsicredentials بيشفر credentials ويخزنها في ACE vault (بيتضبط بالأمر mqsivault)، وintegration server مستقل يقدر يستخدمها للوصول لموارد مؤمنة.

القسم 12.2: HTTP وSOAP

نظرة عامة على الـ web services

  • طريقة قياسية لاستدعاء functions أو methods بـ web protocols قياسية زي HTTP
  • للتفاعل بين المؤسسات، وداخل المؤسسة (مثلًا بين channel servers وline-of-business servers)
  • بعض الـ transports بتدي reliable messaging

الـ web services نموذج اتصال برنامج لبرنامج مبني على معايير HTTP وXML وSOAP وWSDL وUDDI. الـ web service هو interface بيوصف مجموعة عمليات متاحة على الشبكة عبر XML messaging قياسي، ووصفه بصيغة XML اسمها service description، فيها formats الرسايل والـ transport protocols والمكان. الـ interface بيخفي تفاصيل التنفيذ، فممكن يتستخدم باستقلال عن الـ hardware والـ software ولغة البرمجة. ده بيشجع loosely coupled وcomponent-oriented وcross-technology. تقدر تستخدمها لوحدها أو مع غيرها لـ aggregation أو business transaction.

SOAP

  • بروتوكول XML-based مكون من SOAP envelope بيحدد إطار لوصف محتوى الرسالة وإزاي تتعالج
  • SOAP header فيه معلومات لأي SOAP receiver في مسار الرسالة (header blocks)
  • SOAP body فيه صفر أو أكتر من element information items موجهة لـ ultimate SOAP receiver
  • الطلبات ممكن تتبعت بـ transports كتير زي HTTP وJMS

SOAP لغة XML لإرسال البيانات بين التطبيقات، محايدة للـ transport والـ platform. مش كل web services بتستخدم SOAP، لكنه غالبًا الأكثر استخدامًا. الـ envelope فيه header اختياري (فيه header blocks) وbody إلزامي. الـ WSDL عادةً بيحدد محتوى الـ header والـ body.

WSDL

  • وثيقة metadata بصيغة XML بتعرف web service وإزاي توصل له
  • بتسمح للبرامج تكتشف الخدمات وتناديها من غير إعداد إداري
  • بتوفر معلومات functional وtechnical
  • استورد ملفات WSDL وأي XML schema files مشار لها مباشرة في Toolkit application أو library
  • اسحب الـ WSDL على Message Flow editor canvas لتعريف وضبط web services flows وsubflows: لاستدعاء web service أو لعرض الـ flow كـ web service، ولعمل wrap أو unwrap للـ SOAP envelope

الـ WSDL بيعرف الخدمة بمجموعة ports (WSDL V1.1) أو endpoints (WSDL V1.2) اللي بتحدد فين الخدمة متاحة. كل port مسمي له binding (آلية الوصول)، وفيه binding منفصل لكل protocol مدعوم (مثلًا SOAP over HTTP أو SOAP over JMS). كل binding بيشير لـ portType (V1.1) أو interface (V1.2) مسمي. الـ binding بيحدد wire format وتفاصيل الـ transport، والـ portType/interface هو الواجهة المنطقية. كلاهما بيحدد operations. كل operation فيها input وoutput elements معرفة بـ messages أو message parts. الـ message بتعرف رسالة منطقية بجزء واحد أو أكتر (كل part ممكن يقابل parameter في method call). الـ part معرف إما كـ XML schema element أو type، ومحدد بالكامل بـ قسم WSDL types أو imported schema (.xsd) files.

ACE وweb services: requester وprovider

  • يعمل كـ front end لعدة service providers لتوفير failover وجودة خدمة أعلى
  • يوفر logging للرسايل للـ audit
  • يعمل map لرسايل SOAP لصيغ صناعية قياسية تانية
  • يختار service provider بناءً على سياق ومحتوى الرسالة

ACE نقطة مركزية مناسبة لـ web services brokering: تقدر تغلف خدمات أو توصل لـ web services من التطبيقات. وكمان بيشتغل كـ SOAP intermediary بوظائف first point-of-contact: إخفاء أو تغيير تنفيذ الخدمة، وتحويل بين تعريفات WSDL، ومراقبة، وdata warehousing، وauditing.

الـ flow كـ HTTP/HTTPS client

  • legacy clients بتوصل لـ web services
  • ACE كـ buffer بين مجموعة متغيرة من service providers
  • aggregation لـ web services

الـ HTTPRequest node بيتفاعل مع web service بإرسال كل أو جزء من رسالة الإدخال كطلب. ويقدر ينشئ output من محتوى الإدخال ويكمله برد الخدمة قبل ما يبعت للـ nodes اللي بعده. بيبني طلب HTTP أو HTTPS من المحتوى المحدد، ويبعته، ويستقبل الرد ويعمل parse له للـ output tree. بيولد HTTP headers لو الضبط يحتاجها. خاصية Default web service URL بتحدد الوجهة، وممكن Compute node قبله يتخطى القيمة.

الـ flow كـ service provider

  • ACE بيشتغل كوسيط لـ web service ويعمل routing
  • تركيبات كتير تانية

كل integration node له TCP/IP port واحد بيقبل عليه طلبات HTTP. العملاء بيعملوا post لـ URL محدد مسبقًا أو تم جلبه قبل كده، وفيه attribute على كل HTTPInput node بيحدد الطلبات المسؤول عنها. الـ flow ممكن يعمل transform أو route أو aggregate لطلبات web services: بيعمل parse للطلب وبيبعته لوجهة أو أكتر حسب المحتوى (ممكن بعد transformation)، والرد من الوجهات بيرجع للـ client الأصلي بعد transformation أو aggregation محتملة.

ضبط web services في ACE

  • الـ message flows ممكن تتعرض كـ web services، وممكن تنادي web services
  • WSDL: ممكن يتولد من message model فيه namespaces، أو يتستورد مباشرة كـ application أو library، وبيتستخدم لتوليد artifacts كتير تلقائيًا
  • HTTP وSOAP nodes
  • SOAP parser

الـ flow ممكن يكون requester أو client: input node بيشغل flow ينادي web service (عبر HTTP أو JMS bindings) والنتيجة بتكمل الرسالة المرسلة بـ output node. وممكن يكون service provider فيسمح لـ clients بنداء flow موجود.

HTTP nodes

HTTPInput
Web service URL، بيستخدم HTTPS، أقصى وقت ينتظر فيه الـ client رد HTTPReply (عند timeout بيبعت SOAP fault)، HTTP Proxy location، Follow HTTP redirection
HTTPReply
Reply send timeout لانتظار acknowledgment من الـ client، توليد default HTTP headers من HTTPResponseHeader في الرسالة الداخلة
HTTPRequest
Web service URL، timeout للردود (الافتراضي 120 ثانية)، استخدام InputBody كـ request أو path زي InputRoot.x، واستخدام رد الخدمة كـ OutputBody أو path زي OutputRoot.x، توليد default HTTP headers من الإدخال

لما رسالة تتستقبل من web service client أو web server، الـ HTTPInput أو HTTPRequest node بيعمل parse للـ HTTP headers لإنشاء عناصر في الشجرة. وبالعكس عند الإرسال. الـ nodes بتنشئ HTTPInput وHTTPResponse headers من bit stream الأصلي. المطور عادةً بيضبط HTTPReply وHTTPRequest headers في Compute node، أو بضبط default في خصائص الـ node.

تذكير
ضيف MQMD headers المناسبة لما رسالة جاية من HTTPInput node تتوجه لـ MQOutput node.

SOAP nodes

SOAP Input وSOAP Reply
لما الـ flow هو web services provider
SOAP Request وSOAP AsyncRequest وSOAP AsyncResponse
لما الـ flow هو web services consumer
SOAP Extract
يشيل SOAP envelopes ويعالج الـ body بس، أو يوجه رسالة SOAP حسب اسم الـ operation
SOAP Envelope
يضيف SOAP envelope لرسالة موجودة. بيتستخدم مع SOAPExtract

الـ nodes بتدعم WS-Addressing وWS-Security. بتعالج رسايل SOAP مباشرة. في سيناريو الـ consumer مدعوم synchronous وasynchronous: الـ consumer جوه الـ flow يا يستنى الرد (block) أو يكمل في الـ flow. بتدعم provider وconsumer بـ request/response.

SOAP over JMS

  • JMS ممكن يتستخدم كـ transport لرسايل SOAP
  • مواصفة SOAP over Java Message Service 1.0 بتوصف ربط SOAP بنظام messaging بيدعم JMS
  • SOAP مستقل عن الـ transport وممكن يتربط بأي protocol، وSOAP 1.1 وSOAP 1.2 كلاهما بالـ SOAP 1.2 Protocol Binding Framework
  • ACE بيدعم JMS transport على SOAP nodes، بضبط عن طريق استيراد WSDL فيه SOAP/JMS bindings

SOAP over JMS بديل لـ SOAP over HTTP القياسي. تطبيقات JMS بتبعت لـ destinations (queues أو topics): queues لـ point-to-point وtopics لـ publish/subscribe.

Figure 12-5 Java Message Service (JMS)

JMS واجهة Java قياسية للـ messaging (Oracle مالكة المواصفة وبتتدار عبر Java Community Process). بتحدد الـ API بس، مش الـ protocol، فالتطبيق ممكن يتكلم مع أي provider (زي IBM MQ) من غير ما يتغير الكود.

Figure 12-6 JMS architecture

معمارية JMS: الـ JMS client (برنامج Java) بيجيب ConnectionFactory وDestination (queue أو topic) من الـ JNDI namespace، وبعدها يفتح connection للـ messaging provider ويبعت ويستقبل Messages.
نص الكتاب الأصلي
• This slide provides an overview of the JMS architecture. JMS messaging applications can consist of the following parts: ▪ JMS client: Java program that produces and uses messages by using JMS ▪ Messaging provider: The enterprise messaging system, for example, IBM MQ ▪ Message: The object that communicates information between the client and the provider ▪ Administered objects (Connection Factory and Destination): Preconfigured JMS objects that an administrator creates for the use of clients • Java Naming and Directory Interface (JNDI) is a standard Java extension that provides a uniform API for accessing various directory and naming services. JMS clients use JNDI to browse a naming service to obtain references to administered objects. Administered objects are the JMS connection factory and JMS destination objects, where JMS destination objects are topics and queues. A system administrator creates and configures administered objects. • A JMS client specifies a JNDI InitialContext to obtain a JNDI connection to the JMS messaging server. The InitialContext is the starting point in any JNDI lookup and acts like the root of a file system. The JMS directory service that is being used determines the properties that are used to create an InitialContext.

نص الكتاب الأصلي
• IBM App Connect Enterprise supports the JMS version 1.1 and 2.0 standard. It uses the IBM App Connect Enterprise JMS Transport service to connect to JMS messaging providers. • IBM App Connect Enterprise also provides message processing nodes that are designed to send messages to and receive messages from JMS providers.

نص الكتاب الأصلي
• The JMS nodes can be used in applications in which messages are produced and used from various JMS destinations. In sending and receiving messages, the JMS nodes behave like JMS clients. • The JMS nodes work with the IBM MQ JMS provider, WebSphere Application Server, and any JMS provider that conforms to JMS V1.1 or 2.0. • In IBM App Connect Enterprise, policies define connections to the JMS providers.

Figure 12-10 JMSInput node

JMSInput: بيستقبل رسايل من JMS destination وبيشتغل كـ consumer، ويقدر يستقبل الأنواع الستة (Bytes وText وObject وMap وStream وMessage عادية)، وبيبدأ بيها الـ flow.
نص الكتاب الأصلي
• Use the JMSInput node to receive messages from JMS destinations. JMS destinations are accessed through a connection to a JMS provider. • The JMSInput node acts as a JMS message consumer and can receive all six message types that are defined in the JMS specification. Messages are received by using method calls, which are described in the JMS specification. • The JMSInput node is contained in the JMS drawer of the palette. • The JMSInput node receives and propagates messages with a JMS message tree. You can set the properties of the JMSInput node to control how the JMS messages are received.

Figure 12-11 Parsing the JMS message payload

تحليل الـ payload حسب النوع: Bytes وText وObject بتتاخد كلها وتتعمل لها parse بالـ parser المحدد في الـ node، أما Map وStream فبتتحول لـ XML تحت Body.
نص الكتاب الأصلي
• The parsing process for the payload of JMS messages depends on the type of incoming JMS message. • The payload for messages of the JMS message types BytesMessage, TextMessage, and ObjectMessage are extracted as a whole from the message object by using the JMS API. The payload is passed as a bit stream to an integration node parser. • For ObjectMessage types, the JMSInput node obtains the payload by calling getObject( ) on the message. The getObject( ) method returns a de-serialized object of the original class. This class definition must be made available to the JMSInput node, and you should ensure that it is accessible through the integration node Java class path. (For more information about how to specify the class path, see the IBM Knowledge Center.) The JMSInput node calls the BLOB parser, which creates the message body by using a bit stream that is created from the object. The Java Object can then be reserialized in a JavaCompute node (or a user-defined extension), and is updated by using its method calls. • The JMSInput node must reformat the payload for MapMessage and StreamMessage as follows: ▪ The JMSMap domain is a synonym for the integration node XML parser, which expects a stream of XML data. However, MapMessage payload data is extracted as sets of name-value pairs from the message object. The JMS API is used to obtain the name-value pairs. The JMSInput node appends each name-value pair to a bit stream as an XML element and value, and preserves the type of the value by using the dt= attribute. The map data is not returned from the JMS API in the order in which it was received. ▪ The StreamMessage payload data is a sequence of fields, where each field has a specific type. The fields do not have associated names and so a default element name elt is used to generate the XML elements. Like MapMessage messages, the JMS API allows for fields only to be retrieved individually. The JMSInput node extracts fields from the JMS message and appends each to a bit stream in XML format.

Figure 12-12 JMS message tree

شجرة رسالة JMS: Root فيها Properties وفولدر JMSTransport (بيحتوي Transport_Folders: Header_Values وApplication_Properties وغيرها بمعلومات JMS الخاصة) ثم الـ Body كآخر child.
نص الكتاب الأصلي
• The JMS nodes use a special message tree that provides a JMS view of the message. With the standard Properties and Body folders, a JMS message contains a JMSTransport folder that contains information that is specific to the JMS message. It contains elements (tags) that are familiar to a JMS developer. Header values are stored as name-value pairs in the Header_Values folder. The JMS message tree has the same form regardless of the JMS provider that the message flow uses. • The JMS message tree includes the following folders: ▪ Message_MetaData contains information about the payload type of the JMS message. The JMSOutput node uses this folder. ▪ Header_Values contains values for (or from) the JMS message headers. ▪ Application_Properties is an optional folder that contains application-specific information. For example, it might message context information (for example, correlation ID and ReplyTo destination information) that is being preserved from the input message. ▪ Provider_Properties can contain information that is specific to the JMS provider that is being used. The client can set these properties, or the provider can supply them automatically. Provider-related properties are prefixed with JMS_ appended with the vendor name and the specific property name. For example, the IBM MQ JMS client sets the provider property to JMS_IBM_MsgType. The JMS provider sets Standard_Properties when it sends a message. A JMS provider vendor can choose not to support any standard properties to support some standard properties, or to support all standard properties. Standard property names start with JMSX; for example: JMSXUserid or JMSXDeliveryCount. • The various JMS message processing nodes use some or all of these JMSTransport folders, depending on their operations.

Figure 12-13 JMSOuput node

JMSOutput: بيشتغل producer ويبعت رسايل لـ destination. بيبعت datagram فيه معلومات كفاية للتوجيه، وبيستخدم الـ destination اللي في الـ node أو في الـ LocalEnvironment.
نص الكتاب الأصلي
• The JMSOutput node acts as a JMS message producer, and can publish all six message types that are defined in the JMS specification. Messages are published by using method calls, which are described in the JMS specification. • The JMSOutput node is contained in the JMS drawer of the palette. • In the JMS message tree, the PayloadType field of the Message_MetaData subfolder represents the JMS message type. To control the type of JMS message that the JMSOutput node creates, use ESQL code to set the PayloadType value, as shown in the following example: SET OutputRoot.JMSTransport.Transport_Folders.Message_MetaData.PayloadType=Payload value

Figure 12-14 Serializing the JMS output message

لما JMSOutput أو JMSReply يستلم رسالة، بينادي الـ JMSTransport parser يعمل serialize لـ XML bit stream فيه الـ header data، فيطلّعها منه ويعبّي بيها حقول JMS header، والباقي يتبعت كـ payload.
نص الكتاب الأصلي
When a JMSOutput (or JMSReply) node receives a JMS message, it calls the JMS Transport parser to serialize the message assembly. • Header data: The JMSOutput node extracts the JMS header data from the XML string, and uses this data to populate the values for the JMS header fields in the message. • Property data: The JMSOutput node extracts the property values from the XML string. The XML elements contain type information that identifies which Java Object type to create for each property value. • Message payload data: The message payload is obtained from the JMS message as a bit stream. For TextMessage and BytesMessage payloads, the bit stream can be passed to the JMS API directly to create the appropriate payload. For MapMessage and StreamMessage payloads, the individual elements must be extracted from the XML bit stream. The output node calls the appropriate JMS API method to create the map or stream fields in the message. For an ObjectMessage payload, the JMSOutput node reserializes the bit stream payload by using the object class.

Figure 12-15 JMSReceive node

JMSReceive: زي JMSInput بس ممكن يتحط في نص الـ flow. الـ assembly الداخلة بتتدمج مع الرسالة اللي استقبلها.
نص الكتاب الأصلي
• The JMSReceive node works like the JMSInput node, but you can use the JMSReceive node in the middle of a message flow. The message assembly that comes into the node on the In terminal is merged with the message assembly that the node creates when it receives a message from the JMS destination. You control which data from the input message is combined with the result tree by configuring the Result property tab on the node. • The two main properties in the Result property tab that control the construction of the output tree are: ▪ Output Data Location specifies where in the output message tree to place the value that is specified in the Result Data Location message. The input root is first copied to the output root, and then the result data is copied to the location on the output tree that the Output data location property specifies. The default value, $OutputRoot, replaces the copied message tree with the data that is retrieved from the JMS provider; it does not propagate the input message. You can use an ESQL or XPath expression for this property. ▪ Result Data Location specifies what part of the message tree that was retrieved from the JMS provider to copy to the Output Data Location. The default, $ResultRoot, inserts the result message into the output tree at the location that the Output data location property specifies. You can use an ESQL or XPath expression for this property. • For example, suppose that you set Output Data Location to $OutputRoot/XMLNSC/JMSRecvMsg and you set Result Data Location to $ResultRoot/JMSMap. After the JMSReceive node receives the message from the JMS provider, it copies the part of the message that $ResultRoot/JMSMap defines to the $OutputRoot/XMLNSC/JMSRecvMsg location in the message assembly.

Figure 12-16 JMSReply node

JMSReply: زي JMSOutput بس بيبعت فقط للـ destination المحدد في حقل JMSReplyTo في الـ header (للـ request/reply).
نص الكتاب الأصلي
The JMSReply node is similar to the JMSOutput node. The primary difference is that the JMSReply node sends a message only to the destination specified in the JMSReplyTo header. With the JMSOutput node, you can specify message destinations by using other values (including other locations that are specified in the message tree).

Figure 12-17 JMS transformation nodes

ثلاث nodes مساعدة: JMSHeader (يعدل Header_Values وApplication_Properties من غير Compute)، وJMSMQTransform (يحول رسالة JMS لـ MQ والعكس)، وهكذا تقلل الكود المكتوب.
نص الكتاب الأصلي
You can use three "helper" nodes to accelerate development and reduce the amount of application code that you must write when working with JMS messages. By using these nodes, you can modify message header values without using a compute-type node to modify the values. • With the JMSHeader node you can set, copy, or modify the Header_Values properties in the JMS tree by using a set of fields. You can modify the properties by using predefined values, user-defined values, or XPath expressions. You can also set Application_Properties in the JMS tree by adding, modify, or deleting name-value pairs of application properties. • The JMSMQTransform node transforms a message that contains a JMS message tree to a message that is formatted to be compatible with the IBM MQ JMS provider. • The MQJMSTransform node does the opposite. It transforms a message that is formatted for the IBM MQ JMS provider to a message that contains JMS headers that can be sent to JMS destinations. For more information about the fields that the JMSMQTransform and MQJMSTransform nodes map, see the IBM Knowledge Center.

Figure 12-18 JMS transactional processing

الـ transactions: باستخدام XA transaction coordinator تقدر تعمل syncpoint للـ flow اللي بيستقبل ويبعت JMS. تفاصيل التعافي من in-doubt transactions تعتمد على الـ transaction manager.
نص الكتاب الأصلي
• By using of an XA-compliant transaction coordinator, you can enforce transactional control in a message flow that uses JMS. • The details of transactional control and how in-doubt transactions are recovered are specific to the transaction manager that is used. For more information, see the product documentation.

Figure 12-19 Securing JMS message flows

تأمين JMS: تأمن الـ connection أو الـ JNDI lookup أو الاتنين، بتحديد الـ properties على كل JMS node وبتحديد user ID وpassword للاتصال (عن طريق security identity).
نص الكتاب الأصلي
• When you include JMS nodes in a message flow, you can secure the JMS connection resources and the JNDI binding lookups. To do so, you need to specify the appropriate properties on every JMS node in the message flow. You must also specify the user ID and password for the connection factory or initial context factory (or both) by using the mqsisetdbparms command. • As an alternative to using the mqsisetdbparms command, you can use the mqsicredentials command to encrypt credentials and store them in the IBM App Connect Enterprise vault, which is configured by using the mqsivault command. These credentials can then be used by an independent integration server to access secured resources.

Figure 12-21 Web services overview

Web services: طريقة قياسية لاستدعاء functions عبر بروتوكولات الويب (HTTP) بين تطبيقات مختلفة، مبنية على XML وSOAP وWSDL (وUDDI قديماً). الخدمة هي interface بيوصف مجموعة عمليات.
نص الكتاب الأصلي
• Web services provide a common program-to-program communications model, which is built on existing and emerging standards such as HTTP, XML, SOAP, WSDL, and Universal Description, Discovery, and Integration (UDDI). • A web service is an interface that describes a collection of operations that are network-accessible through standardized XML messaging. A web service is described by using a standard, formal XML notation, which is called its service description. It covers all the details necessary to interact with the service, including message formats (that detail the operations), transport protocols, and location. The interface hides the implementation details of the service. This interface allows it to be used independently of the hardware or software on which it is implemented, and also independently of the programming language in which it is written. • Independence allows and encourages web-services-based applications to be loosely coupled, component-oriented, cross-technology implementations. Web services fulfill a specific task or a set of tasks. They can be used alone or with other web services to do complex aggregation or a business transaction.

Figure 12-22 SOAP

SOAP: لغة XML لتبادل البيانات، محايدة للـ transport والمنصة. الرسالة فيها Envelope وفيها Header اختياري (معلومات إضافية زي security) وBody (البيانات الفعلية أو fault).
نص الكتاب الأصلي
• SOAP is an XML-based language for sending data between applications. SOAP is transport-neutral and platform-neutral. Not all web services use SOAP, but it is probably the most commonly used message format. • A SOAP message contains an envelope with an optional header (containing one or more header blocks) and a mandatory body. A WSDL typically defines the content of the header and body.

Figure 12-23 Web Services Description Language (WSDL)

WSDL: وثيقة XML بتوصف الخدمة: النوع (types/schema) والرسايل والعمليات (portType) والـ binding (SOAP over HTTP مثلاً) والـ endpoint address. بتخلي الـ client يعرف يكوّن الطلب.
نص الكتاب الأصلي
• WSDL is an XML-based language for describing an interface between applications. A WSDL definition tells a client how to compose a web services request and describes the server-provided interface. • The WSDL document defines a service in terms of a number of ports (WSDL V1.1) or endpoints (WSDL V1.2). The ports define where the service is available. • Each named port also defines a mechanism (binding) for accessing it. There is a separate binding for each protocol that is supported, for example, SOAP over HTTP or SOAP over JMS. Each binding refers to a named portType (WSDL V1.1) or interface (WSDL V1.2). • A binding defines the message wire format and transport details. A portType/interface is the logical interface to the web service. Both binding and portType/interface define operations. • Each operation comprises input and output elements that are defined in terms of messages or message parts. • The message elements define a logical message in terms of one or more parts. (Each part might correspond to a parameter on a method call.) • A part is defined either as an XML schema element or as an XML schema type. Either or both of the following items fully define these elements and types: ▪ WSDL <types> section ▪ Imported schema (.xsd) files that provide the definitions for the WSDL part definitions See the W3C at http://www.w3.org and in particular the WSDL 1.1 document at http://www.w3.org/TR/wsdl

Figure 12-24 IBM App Connect Enterprise and web services

ACE نقطة مركزية (brokering) للـ web services: ممكن يلف خدمات أو يوصلها لتطبيقات، ويشتغل SOAP intermediary (يخفي مكان الخدمة الحقيقية، ويوجه، ويحول بين الـ protocols).
نص الكتاب الأصلي
• IBM App Connect Enterprise is a convenient central point for web services brokering. You can wrap services or access web services from applications. • IBM App Connect Enterprise can act as a SOAP intermediary by providing first point-of-contact functions, such as hiding or changing a service implementation, transformation between WSDL definitions, monitoring, data warehousing, and auditing.

Figure 12-25 Message flow as HTTP/HTTPS client

الـ flow كـ HTTP client: HTTPRequest بيستدعي web service بكل أو جزء من الرسالة كطلب، ويبني رسالة الخرج من الرد. مفيد مع legacy clients ولعزلهم عن تغيّر مقدمي الخدمة.
نص الكتاب الأصلي
• The HTTPRequest node can interact with a web service by using all or part of the input message as the request sent to that service. The node can also be configured to create an output message from the contents of the input message. You can augment the output message with the contents of the web service response before the message is propagated to subsequent nodes in the message flow. • Depending on the configuration, the HTTPRequest node constructs an HTTP or an HTTP over SSL (HTTPS) request from the specified contents of the input message. It sends the request to the web service, receives the response from the web service, and parses the response for inclusion in the output tree. The HTTPRequest node generates HTTP headers if the configuration requires them. • The Default web service URL property can be set on the HTTPRequest node to determine the destination URL for a web service request. A Compute node can be included before the HTTPRequest node within the message flow to override the value that is set in the property.

Figure 12-26 Message flow as service provider

الـ flow كـ service provider: كل integration node ليه port واحد للـ HTTP، وHTTPInput بيحدد الـ URL path اللي يرد عليه، فتوجه لـ flows مختلفة بحسب الـ URL.
نص الكتاب الأصلي
• Each integration node has a single TCP/IP port on which incoming HTTP requests are accepted. Client applications can post to a predefined URL or a URL that was already retrieved. An attribute on each HTTPInput node is used to qualify the requests for which the node is responsible. • A message flow can act as an intermediary and transform, route, or aggregate web service requests. A message flow parses the request, and forwards it on to one or more destinations that are based on content, perhaps after transformation. Reply data from the destinations is returned to the original client after further possible transformation or aggregation.

Figure 12-27 IBM App Connect Enterprise web services configuration

ACE web services: الـ flows تتعرض كخدمات أو تستدعي خدمات، والـ WSDL ممكن يتولد أو يتستورد، والـ flow ممكن يكون requester (input node يشغّل flow يستدعي خدمة) أو provider.
نص الكتاب الأصلي
• A message flow can be a requester or a client. An input node drives a flow that calls a web service (over HTTP or JMS bindings). The result of the call is used to augment the message that is sent back by using an output node. • A message flow can be a service provider, allowing web service clients to call an existing message flow. • The web service that the WSDL defines can be directly imported into the IBM App Connect Enterprise Toolkit and used to generate message flows. • IBM App Connect Enterprise includes nodes for HTTP and SOAP. It also includes a parser for SOAP messages.

Figure 12-28 HTTP nodes

HTTP nodes: HTTPInput (الـ URL وHTTPS وأقصى وقت انتظار الـ client للـ HTTPReply وبعده SOAP fault)، وHTTPReply، وHTTPRequest. الـ HTTP headers بتتحول لعناصر في شجرة الرسالة.
نص الكتاب الأصلي
• When a message is received from a web service client or a web server, the HTTPInput or HTTPRequest node that receives that message must parse the HTTP headers to create elements in the message tree. When an HTTPReply or HTTPRequest message sends a message to a web service client or web server, it parses the HTTP headers from the message tree into a bit stream. • The HTTPInput and HTTPRequest nodes normally create HTTPInput and HTTPResponse headers from the original client/server bit stream. • The developer normally sets the HTTPReply and HTTPRequest headers in a Compute node, or by setting a default on the properties of the HTTPReply or HTTPRequest node. • Remember to add appropriate MQMD headers when a message that originates from HTTPInput node is routed to the MQOutput node.

Figure 12-29 SOAP nodes

SOAP nodes: للـ provider: SOAPInput وSOAPReply. للـ consumer: SOAPRequest (sync: ينتظر الرد) وSOAPAsyncRequest وSOAPAsyncResponse (async: يكمل الـ flow). بتدعم WS-Addressing وWS-Security وMTOM.
نص الكتاب الأصلي
• SOAP nodes process SOAP messages directly. For the consumer scenario, both synchronous and asynchronous capability is supported allowing the consumer within the flow to either block, wait for the response, or alternatively continue down the flow. • SOAP nodes support web service provider and consumer scenarios with request/response.

Figure 12-30 SOAP over JMS

SOAP over JMS: بديل للـ HTTP، بيستخدم JMS كـ transport لرسايل SOAP (queues للـ point-to-point وtopics للـ pub/sub).
نص الكتاب الأصلي
• You can use SOAP over JMS to use the JMS transport with SOAP messages, and is an alternative messaging mechanism to the standard SOAP over HTTP messaging. • JMS applications send messages to JMS destinations, which can be queues or topics. Queues are used in point-to-point messaging, and topics are used in publish/subscribe messaging.
